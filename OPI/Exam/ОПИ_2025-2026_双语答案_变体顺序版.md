## Билет 1. 变体 1

### 第1题：ISO/IEC 12207:2010: Жизненный цикл ПО. Группы процессов ЖЦ.

## 1. ISO/IEC 12207:2010: Жизненный цикл ПО. Группы процессов ЖЦ.

**俄语 / Русский ответ**

Жизненный цикл ПО — это период от появления идеи до вывода системы из эксплуатации. Основные стадии:

- разработка требований;
- анализ;
- проектирование архитектуры;
- разработка;
- тестирование;
- внедрение в эксплуатацию;
- эксплуатация (багфиксы, поддержка, обновления);
- вывод из эксплуатации (перенос данных и т.д.).

Группы процессов ISO/IEC 12207:

- процессы соглашения;
- процессы организационного обеспечения;
- процессы проекта;
- технические процессы;
- процесс реализации программного средства;
- процессы поддержки ПО;
- процессы повторного использования ПО.

**中文 / 中文翻译**

软件生命周期指从产生想法到系统退役的整个过程，主要阶段包括：需求开发、分析、架构设计、开发、测试、投入运行、运行维护（修复缺陷、用户支持、更新）以及退役（如迁移数据）。

ISO/IEC 12207 的过程组包括：协议过程、组织保障过程、项目过程、技术过程、软件实现过程、软件支持过程以及软件复用过程。

### 第2题：Требования. Иерархия требований. Примеры формулировок на разных уровнях.

## 23. Требования. Иерархия требований. Примеры формулировок на разных уровнях.

**俄语 / Русский ответ**

Требование — условие или возможность, которой должна соответствовать система. Оно формулируется однозначно и описывает **что** нужно реализовать, а не **как**.

Подход RUP образует иерархию: потребность заказчика → системное/пользовательское требование → конкретное требование к ПО.

**Примеры по уровням:**

- Заказчик: «Мне нужна сковородка, чтобы еда не пригорала».
- Аналитик (системное требование): «Сковородка должна иметь антипригарное покрытие и термоизолирующую ручку».
- Реализация (требование к ПО): конкретные параметры, материалы и условия эксплуатации.

*需求层次 / Иерархия требований*

**中文 / 中文翻译**

需求是系统必须满足的条件或能力，须表述无歧义，说明系统**要做**什么，而非**如何**实现。

按 RUP 可分为层级：客户/业务需求 → 系统或用户需求 → 具体软件需求。

**示例**：客户说"我需要一个不粘锅"；分析人员转化为"平底锅须有防粘涂层和隔热手柄"；最终再细化出关于材料、尺寸等的具体实现要求。

### 第3题：Рецепты повышения производительности при высоком %IO wait. + Рецепты повышения производительности при высоком %User.

#### A. 78. Рецепты повышения производительности при высоком %IO wait.

**俄语 / Русский ответ**

Высокий `%IO wait` — CPU ждет I/O. Решения:

1. **Проблемы приложения** — меньше/реже читать-писать, обмениваться большими порциями; согласовать блок приложения с ОС и дисками (напр. stripe 16 КБ, читать по 8 КБ дает двойное чтение и теряет выгоду RAID).
2. **Нехватка буферов/кэшей** — расширить память или настроить системные кэши.
3. **Проблемы с аппаратурой** — заменить подсистему на SSD или flash-карты (PCI-e), особенно для случайного доступа.

### 补充图示（来自 GitHub 旧答案）

![高 IO wait / Высокий %IO wait](https://raw.githubusercontent.com/alex-grandson/edu/main/MISPI/img/high_io.png)

*高 IO wait / Высокий %IO wait*

**中文 / 中文翻译**

`%IO wait` 高表示 CPU 在等待 I/O。对策：1）**优化应用层**——减少读写次数、尽量大块传输，并让应用/OS/磁盘块大小对齐（若 stripe 16KB 却按 8KB 读，会双重读取、RAID 优势丧失）；2）**缓冲/缓存不足**——增加内存或调整系统缓存；3）**硬件**——换用 SSD 或 PCI-e 闪存卡，随机访问尤其见效。

#### B. 80. Рецепты повышения производительности при высоком %User.

**俄语 / Русский ответ**

Высокий `%User` — CPU занят пользовательским кодом. Сначала профилирование находит самые затратные функции/объекты. Затем:

1. Алгоритмы с меньшей сложностью.
2. **Повторное использование объектов** (как структуры процессов в Unix: "зомби" повторно используются).
3. На микроархитектуре — устранение **cache/TLB miss**: работа над структурами данных (группировка, padding), большие страницы памяти; **закрепление потоков** за CPU (affinity).
4. В экстремальных случаях — переписать на ассемблере, использовать GPU/криптопроцессоры.

**应用程序的问题：**

- 算法复杂度更低的算法。
- 对象的重复使用。
- 消除循环中的主动轮询和等待。
- 查找缓存和TLB的未命中。
- 考虑缓存的大小和组织：
  - 缓存大小有限。
  - 对象的填充和对齐。
  - 使用更弱的同步原语。
- 将进程/线程绑定到处理器。
- 在汇编器/编译器层面进行优化。
- 提高处理器频率，增加核心数量，使用GPU/加密处理器。

### 补充图示（来自 GitHub 旧答案）

![高 User / Высокий %User](https://raw.githubusercontent.com/alex-grandson/edu/main/MISPI/img/high_user.png)

*高 User / Высокий %User*

**中文 / 中文翻译**

`%User` 高表示 CPU 忙于用户态代码。先用剖析定位最耗时函数/对象，再：1）用更低复杂度算法；2）**对象复用**（如 Unix 进程结构，"僵尸"进程被复用）；3）微架构上减少 **cache/TLB miss**——优化数据结构（分组、填充）、用大页内存，并**绑定线程到 CPU（affinity）**；4）极端情况采用汇编、GPU 或密码协处理器。

### 第2题：Системы автоматической сборки: предпосылки появления. + Сервера сборки/непрерывной интеграции.

#### A. 41. Системы автоматической сборки: предпосылки появления.

**俄语 / Русский ответ**

1. **Рутинный процесс** — при сборке многократно повторяются команды; у модулей и внешних зависимостей последовательность сложна. Скрипты ОС трудно поддерживать, современные средства генерируют команды автоматически.

**中文 / 中文翻译**

### 第3题：Мониторинг производительности: процессы.

## 69. Мониторинг производительности: процессы.

**俄语 / Русский ответ**

Для мониторинга CPU важны: число процессов уровня пользователя, затраты CPU на них, время простоя, параметры `ctxt_sw` (переключение контекста), `interrupts` (прерывания), `load average` (средняя длина очереди исполнения).

Процессы наблюдают с помощью `top`, `ps`, `pidstat`. В Linux `top` показывает приоритет (PR), виртуальную память (VIRT), физическую (RES), совместно используемую (SHR). Профилировщики исследуют время функций и конкуренцию потоков.

**中文 / 中文翻译**

监控 CPU 需关注：用户态进程数、CPU 占用、空闲时间、`ctxt_sw`（上下文切换）、`interrupts`（中断）、`load average`（运行队列长度）。

进程可用 `top`、`ps`、`pidstat` 查看。Linux 的 `top` 显示优先级（PR）、虚拟内存（VIRT）、物理内存（RES）、共享内存（SHR）。进一步可用 profiler 分析函数耗时和线程竞争。

### 第2题：Системы сборки: Make и Makefile.

## 42. Системы сборки: Make и Makefile.

**俄语 / Русский ответ**

Make — низкоуровневое средство сборки из Unix. Файл `Makefile` задает цели, зависимости и команды; по умолчанию ищется `Makefile`, указать другой — `make -f MyMakefile`. Make анализирует время модификации: цель пересобирается, если она новее зависимостей.

**Состав файла:** явные правила (`цель: зависимости` + команды), неявные правила, определения переменных, директивы, комментарии (`#`).

**Важное:** `.PHONY` (чтобы цель, не создающая файл, всегда выполнялась, напр. `clean`); автоматические переменные `$@` (цель), `$<` (первая зависимость), `$?` (зависимости новее цели), `$^` (все зависимости без повторов); шаблон `%.o: %.c`.

**中文 / 中文翻译**

Make 是源自 Unix 的底层构建工具。`Makefile` 定义目标、依赖和命令；默认读取 `Makefile`，可用 `make -f MyMakefile` 指定其他文件。Make 根据文件修改时间判断是否需要重建目标。

**文件组成**：显式规则（`目标: 依赖` + 命令）、隐式规则、变量定义、指令、注释（`#`）。**要点**：`.PHONY` 用于像 `clean` 这样不生成文件的伪目标；自动变量 `$@`（目标）、`$<`（第一个依赖）、`$?`（比目标新的依赖）、`$^`（全部依赖、去重）；模板规则 `%.o: %.c`。

#### B. 74. Создание тестовой нагрузки и нагрузчики.

**俄语 / Русский ответ**

Критичные бизнес-системы обычно нельзя нагружать экспериментами, поэтому создают отдельную тестовую систему — полную копию реальной. Нагрузка должна быть максимально приближена к реальной.

Способы: **синтетическая нагрузка** (гибко настраивается, но всегда отличается от реальной) или **запись реальной нагрузки** и ее воспроизведение. В тестовой системе допустимы интрузивные средства мониторинга.

**中文 / 中文翻译**

真实关键业务系统通常不宜做负载实验，因此搭建独立、与真实环境一致的测试系统，并使负载尽量贴近真实。

可选用**合成负载**（参数可调，但终归不同于真实）或**录制真实负载**再回放。测试系统中可以使用侵入式监控工具。

- лаконичный DSL на Groovy или Kotlin;
- инкрементальная и параллельная сборка — запускает плагины только при необходимости.

Файл сборки описывает задачи, зависимости и конфигурацию проекта.

Являясь преемником Ant и Maven, Gradle предлагает два основных преимущества: **языковую независимость** (не ограничиваясь Java) и **описание зависимостей и пользовательские репозитории** (включая репозитории Maven). Кроме того, он использует **DSL Groovy/Kotlin** для лаконичного описания сборок и поддерживает **инкрементальные и параллельные сборки** — выполняя задачи плагинов только при необходимости, что экономит больше времени, чем Maven. Задачи, зависимости и конфигурации проекта определяются в файле сборки.

**中文 / 中文翻译**

Gradle 作为 Ant 与 Maven 的后继者，两大优点：**语言无关**（不限 Java）、**依赖描述与自定义仓库**（含 Maven 仓库）。此外用 **Groovy/Kotlin DSL** 简洁描述构建，支持**增量与并行构建**——仅在必要时执行插件任务，比 Maven 更省时间。构建文件中定义任务、依赖和项目配置。

### 第3题：Профилирование приложений. Основные подходы. + Компромиссы (trade-offs) в производительности.

应用程序性能分析。主要方法。+ 性能权衡（trade-offs）。

#### A. 75. Профилирование приложений. Основные подходы.

**俄语 / Русский ответ**

Профилировщики позволяют узнать время выполнения метода, объем созданных объектов, состояние потоков и борьбу за блокировки (lock contention).

**Два подхода:**

1. **Инструментирование** — внедрение диагностических точек в начало/конец функции; интрузивно, поэтому ставят в проблемные места.
2. **Периодические прерывания** — профилировщик прерывает программу через заданный интервал и снимает стек (для времени функций) и кучу (для памяти).

Примеры: Performance Analyzer (Oracle Solaris Studio), NetBeans Profiler. Утечка памяти — когда растет занимаемое место и GC не может освободить объект (сохраняются ссылки).

**中文 / 中文翻译**

性能剖析器能测量方法执行时间、创建对象数、线程状态与锁竞争（lock contention）。

**两种方法**：1）**插桩**——在函数首尾加入诊断点，较侵入，应只放在疑似热点；2）**周期性中断**——按固定间隔打断程序，采集调用栈（用于耗时）和堆信息（用于内存）。示例工具：Performance Analyzer、NetBeans Profiler。**内存泄漏**表现为占用持续增长且 GC 无法回收（引用仍被持有）。

#### B. 76. Компромиссы (trade-offs) в производительности.

**俄语 / Русский ответ**

Оптимизация почти всегда требует компромиссов. Примеры:

- индексация ускоряет поиск, но требует дополнительной памяти (linear search vs indexing);
- больший кэш ускоряет чтение/запись, но уменьшает память для других задач;
- меньшие требования к памяти часто приводят к большей трате CPU, и наоборот.

Правильный выбор алгоритма с учетом архитектуры может ускорить приложение на порядки.

**中文 / 中文翻译**

性能优化几乎总是需要权衡。例如：索引可加速查找但占用额外内存（线性查找 vs 索引）；更大的缓存更快但挤占其他任务内存；内存需求降低往往导致 CPU 增加，反之亦然。综合考虑算法与架构，可让程序提速成百上千甚至更多。

Высокий `%SYS` означает много времени CPU в ядре. Причины и решения:

3. **Избыточная подкачка** — дать больше памяти или запретить выгрузку критичных процессов.
4. **Прочие системные процессы/дефекты ядра** — найти и исключить лишние процессы, настроить параметры ядра.

## 34. Системы контроля версий. Одновременная модификация файлов.

### 第2题：Системы сборки: Ant. Команды Ant. + Системы сборки: Ant-ivy.

#### A. 43. Системы сборки: Ant. Команды Ant.

**俄语 / Русский ответ**

Apache Ant — **императивная** система сборки, применявшаяся для Java. По принципу близка к Make; управляется файлом `build.xml` в формате XML. **Свойства** задаются прямым значением, из переменной окружения или из файла `build.properties`; подстановка — синтаксис `${...}`.

**Команды (примеры):** файловые `copy`, `delete`, `mkdir`, `move`, `patch`, `checksum`, `chmod`; упаковк1а `jar`, `war`, `ear`, `zip`, `tar`, `gzip`, `bzip2`, `rpm`; Java `javac`, `javadoc`, `rmic`, `depend`; исполнение `java`, `exec`, `parallel`, `sequential`, `sleep`, `waitfor`; прочее `echo`, `mail`, `sql`, `ftp`, `telnet`, `taskdef`, `tstamp`, `junit`.

**中文 / 中文翻译**

Apache Ant 是**命令式（声明执行步骤）**构建系统，曾广泛用于 Java。核心文件是 XML 格式的 `build.xml`，用命名 **target** 表示构建目标并显式声明依赖（构成树），target 内定义要执行的命令。可用 `antcall` 显式调用目标，甚至跨文件调用。

**属性**可从直接赋值、环境变量或 `build.properties` 文件中获得，用 `${...}` 引用。**常见命令**：文件操作 `copy/delete/mkdir/move`；打包 `jar/war/ear/zip/tar/gzip`；Java 相关 `javac/javadoc/depend`；执行与并发 `java/exec/parallel/sleep/waitfor`；以及 `echo/mail/sql/ftp/junit` 等。

### 第3题：Интеграционное тестирование. Стратегии интеграции.

## 60. Интеграционное тестирование. Стратегии интеграции.

**俄语 / Русский ответ**

Интеграционное тестирование проверяет **межмодульное взаимодействие** (последовательность вызовов, соответствие протоколов). Бывает **компонентное** (после модульного) и **системное** (между системами или с аппаратурой).

**Стратегии интеграции:**

1. **Сверху вниз** — сначала бизнес-логика (драйвер + заглушки), затем UI, в конце блоки хранения; быстро показывает результат заказчику, но требует много заглушек.
2. **Снизу вверх** — с нижних (близких к аппаратуре) блоков; используется при сильной связи с железом.
3. **Функциональная** — наращивание по пользовательским функциям/сценариям.
4. **Ядро** — сначала минимально работающий набор функций.
5. **Большой взрыв** — все компоненты сразу; сложно локализовать дефекты.

**中文 / 中文翻译**

集成测试验证**模块间交互**（调用顺序、协议一致性），分**组件级**（模块测试后）和**系统级**（系统间或与硬件间）。

**策略**：1）**自顶向下**——先测业务逻辑（驱动＋桩），再接 UI，最后接数据层；能给客户早看效果，但需大量桩。2）**自底向上**——从贴近硬件的底层块开始，适合强硬件相关项目。3）**功能式**——按用户功能逐步增长。4）**核心式**——先做最小可用功能集。5）**大爆炸**——一次性集成全部，缺陷定位难。

#### A. 39. GIT: Организация ветвей репозитория.

**俄语 / Русский ответ**

### 第3题：Тестирование системы в целом. Альфа- и бета-тестирование. Приемочное тестирование.

## 64. Тестирование системы в целом. Альфа- и бета-тестирование. Приемочное тестирование.

**俄语 / Русский ответ**

Подходы в рамках тестирования системы в целом:

- **Системное** — внутри организации-разработчика, без сторонних лиц.
- **Альфа** — пользователи под контролем разработчика, в окружении разработчика.
- **Бета** — в реальном пользовательском окружении, но все еще под контролем разработчика.
- **Приемочное** — пользователь в собственном окружении, без контроля разработчика; решается вопрос о выплате гонорара.

Методики схожи, различается строгость интерпретации. Альфа/бета дают отзывы и выявляют нестандартные пути. Некоторые продукты работают в режиме "вечной беты".

**中文 / 中文翻译**

整体系统测试可分为：**系统测试**（开发组织内部，无外部人员）；**Alpha 测试**（开发方环境，用户在开发者控制下参与）；**Beta 测试**（真实用户环境，但仍在开发者控制下）；**验收测试**（用户在自己的环境中，无开发者控制，据此决定是否付款/交付）。

方法类似，只是结果判读严格程度不同。Alpha/Beta 能提供改进反馈、发现非标准使用路径；部分互联网产品处在"永远 Beta"状态，便于灵活迭代和提前发布。

### 第3题：Тестирование системы в целом. Системное тестирование. Тестирование производительности.

## 63. Тестирование системы в целом. Системное тестирование. Тестирование производительности.

**俄语 / Русский ответ**

Системное тестирование начинается после интеграции и проверяет заявленные характеристики системы целиком, обычно внутри организации-разработчика. Идет от простых сценариев к сложным: заявленные возможности → устойчивость при параллельной работе/сбоях → совместимость (кроссбраузерность, стороннее ПО) → работа под нагрузкой.

**Тестирование производительности** — характеристики **CARAT**:

- **Capacity** — соответствие заявленному объему данных;
- **Accuracy** — точность расчетов;
- **Response Time** — время ответа (интерактивные системы 1–5 с);
- **Availability** — готовность: `Availability = (MTBF − MTTR) / MTBF`;
- **Throughput** — пропускная способность.

Инструменты: HP LoadRunner, Apache JMeter (популярен для Java), The Grinder, Tsung и др.

**中文 / 中文翻译**

系统测试在集成完成后进行，由开发组织内部验证系统整体是否满足声明特性；由简单场景逐步到复杂：功能 → 并发与稳定性 → 故障注入 → 兼容性（跨浏览器、第三方软件）→ 高负载下的性能极限。

**性能测试**关注 **CARAT**：**Capacity**（容量）、**Accuracy**（准确性）、**Response Time**（响应时间，交互系统通常 1–5 秒）、**Availability**（可用性，`用=(MTBF−MTTR)/MTBF`）、**Throughput**（吞吐量）。

常用工具有 HP LoadRunner、Apache JMeter（Java 常用）、The Grinder、Tsung 等。

## 33. Изменение. Общая модель управления изменениями.

**俄语 / Русский ответ**

Изменение — контролируемое, журналируемое обновление системы. СКВ — пример систем учета изменений: по журналу видно историю правок и их влияние на поведение системы. Каждое изменение имеет атрибуты: идентификатор, дата, ответственный, описание, связанный журнал изменения.

Общая модель состоит из трех этапов (гибрид UML-диаграммы деятельности и классов):

Проводятся тестирование (**Test Report**), обновление документации (**Documentation**) и выпуск версии (**System Release**).

**3. Проверка и закрытие.** Изменение передается менеджеру проекта/заказчику, создается **Change Verification**, и оно формально утверждается.

### 第3题：Основные понятия тестирования. Цели тестирования. + Понятие полного тестового покрытия и его достижимость. Пример.

#### A. 52. Основные понятия тестирования. Цели тестирования.

**俄语 / Русский ответ**

Основные понятия: **Mistake** — человеческая ошибка; **Fault** — дефект/изъян (неверный шаг в алгоритме); **Failure** — отказ, внешнее проявление дефекта; **Error** — невозможность выполнить задачу из-за отказа; **Bug** — общий термин для некорректности.

**Цели тестирования:** обнаружение дефектов; повышение уверенности в качестве; предоставление информации для решений; предотвращение дефектов. Главная цель — увеличить приемлемый уровень доверия к тому, что ПО корректно работает в необходимых условиях.

**中文 / 中文翻译**

**基本概念**：Mistake 是人为错误；Fault 是缺陷（算法中的错误步骤）；Failure 是故障（缺陷的外部表现）；Error 是由于故障而无法完成任务；Bug 是对所有程序错误的统称。

**测试目标**：发现缺陷、增强质量信心、为决策提供信息、预防缺陷。核心目标是提升对软件在必要场景下正确工作的信任程度。

#### B. 53. Понятие полного тестового покрытия и его достижимость. Пример.

**俄语 / Русский ответ**

Тестовое покрытие — метрика, показывающая процент покрытых тестами кода/сценариев. Полное покрытие означает покрытие всех строк и всех возможных сценариев — практически недостижимо.

**Пример:** умножение двух 32-битных чисел. Если 1 операция = 1 такт, а процессор 3 ГГц, то полный перебор займет около 181,5 лет. Хранение всех эталонных случаев (каждая строка = пара множителей и результат) потребует около 8192 йоттабайт — это невозможно даже представить.

**中文 / 中文翻译**

测试覆盖率是衡量代码/场景被测试覆盖百分比的指标。**"完整覆盖"**指覆盖所有代码行和所有可能场景，通常不现实。

**示例**：两个 32 位整数相乘。若每次运算 1 个时钟周期、CPU 为 3 GHz，则穷举约需 **181.5 年**；若把每对乘数与结果存成一行，约需 **8192 个明太字节（йоттабайт）**，无法实现。

#### A. 66. Ключевые характеристики производительности.

**俄语 / Русский ответ**

- **Latency (время отклика)** — от выдачи запроса до первых результатов.
- **Throughput (пропускная способность)** — max запросов за единицу времени.
- **Utilization (%util)** — доля времени, когда ресурс занят полезной работой; **%wait** — средняя длина/непустота очереди.
- Наличие **точки насыщения** — нагрузки, после которой производительность резко падает.

- **Эффективность**, ускорение/прирост производительности; в Java важны "memory footprints".

**中文 / 中文翻译**

**延迟（Latency）**：从发送请求到获得首批结果的耗时。**吞吐量（Throughput）**：单位时间最多能处理的请求数。**利用率（%util）**：资源用于有效工作的时间比例；**%wait**：平均队列长度/队列非空时间。存在**饱和点**——超过后性能急降。**可扩展性**衡量系统可扩展、可承压的程度；还有**效率**、加速/性能增益；Java 中需关注"内存占用（memory footprints）"。

#### B. 67. Нисходящий метод поиска узких мест.

1. Ищут ошибки аппаратуры и конфигурации (системные журналы, файлы конфигурации, сбойные блоки диска, кабели).

**中文 / 中文翻译**

自顶向下从整体到局部定位瓶颈：1）排查硬件与配置错误（系统日志、配置、坏盘/线缆）；2）用操作系统工具观察系统（整体、节点间、虚拟机）；3）观察应用本身（算法、API、多线程、锁、同步），借助监控与性能剖析；4）下探到微架构层（每周期指令数、数据对齐、缓存优化、流水线气泡、分支预测），这需要汇编与处理器知识。

## 49. Системы сборки: GNU autotools. Создание конфигурации проекта.

**俄语 / Русский ответ**

**GNU Autotools** （常简称为  **Autotools** ），官方名称是 **GNU 构建系统（GNU Build System）**。它是一套软件构建工具，核心目标是解决一个古老而头疼的问题：**让同一份C/C++等语言的源代码，能在各种不同的Unix-like系统（如Linux、macOS）上，无需用户手动修改，就能成功编译和安装**

### 第3题：Понятие тестового случая и сценария. + Выбор тестового покрытия и количества тестов. Анализ эквивалентности.

#### A. 57. Понятие тестового случая и сценария.

**俄语 / Русский ответ**

**Тестовый сценарий** — последовательность тестовых случаев. **Тестовый случай** — конкретные входные данные, действие и ожидаемый результат.

Пример (банкомат, снятие денег): готовность к приему карточки → вставка карты → проверка карты → ввод PIN → проверка PIN → выбор операции → снятие суммы → выдача денег → возврат в исходное состояние. Каждая строка — отдельный тестовый случай.

Сценарии должны покрывать и отрицательные пути: например, три неверных ввода PIN подряд приводят к блокировке карточки, банкомат возвращается в исходное состояние. Баланс между качеством и скоростью: больше тестов — выше покрытие, но больше время и ресурсы.

**中文 / 中文翻译**

**测试场景**是一串**测试用例**的序列；**测试用例**规定具体输入、动作与预期结果。

示例（ATM 取款）：就绪收卡 → 插卡 → 验卡 → 输入 PIN → 校验 PIN → 选择交易 → 输入取款额 → 出钞 → 回到就绪状态；每行是一个测试用例。

场景还要覆盖异常路径：例如连续 3 次输错 PIN 导致卡片被锁，系统最终回到初始状态。测试规划要在质量与速度间平衡：用例越多覆盖越高，但耗时与资源也越多。

#### B. 58. Выбор тестового покрытия и количества тестов. Анализ эквивалентности.

**俄语 / Русский ответ**

Методы определения достаточного покрытия: **эквивалентное разбиение** (+ анализ граничных значений), **таблица решений**, **таблица переходов**, а также **сценарии использования**.

**Анализ эквивалентности** разбивает входное пространство на участки, где функция ведет себя эквивалентно. Внутри каждого участка выбирается несколько представительных значений, а границы тестируются отдельно.

**Пример:** функция удовлетворения от количества съеденного холодца. Участки: "не съел", "линейный рост", "насыщение (замедление)", "переедание (резкий спад)". Внутри каждого берется 3–5 точек, границы между участками — отдельными тестами.

**中文 / 中文翻译**

确定合理测试覆盖的方法包括：**等价类划分**（配合边界值分析）、**决策表**、**状态转换表**，以及**用例场景**。

**等价类分析**把输入空间划分成函数行为相同的区域；每个区域取少量代表值，并单独测试各区域的边界。

**示例**：满意度随吃冻肉量变化的曲线可分为"未吃""线性上升""接近饱""吃撑后骤降"等区间，每段取 3–5 个点，段与段之间的边界点单独测试。

#### A. 36. Subversion: Основной цикл разработчика. Команды.

**俄语 / Русский ответ**

#### B. 37. Subversion: Конфликты. Слияние изменений.

**俄语 / Русский ответ**

Конфликты содержания возникают, когда локальная и серверная версии изменены по-разному (например, одна и та же строка). При `svn update` чаще выбирают **(p) postpone** — отложить и согласовать правки с автором изменений.

При postpone создаются три файла: `filename.mine` (локальный), `filename.rOLDREV` (до правок в репо), `filename.rNEWREV` (текущий в репо); для сравнения используют **triple diff**.

**Конфликты структуры** — когда файлы в репозитории переименованы/перемещены/удалены, а в локальной копии отредактированы. Для слияния параллельных веток используется `svn merge`.

### 补充图示（来自 GitHub 旧答案）

![SVN 冲突 / Конфликты SVN](https://raw.githubusercontent.com/alex-grandson/edu/main/MISPI/img/conflict.png)

*SVN 冲突 / Конфликты SVN*

**中文 / 中文翻译**

**内容冲突**：本地与服务器对同一处改了不同内容。`svn update` 时通常选 **(p) postpone**（暂缓），先与冲突作者协商。暂缓后生成三个文件：`.mine`（本地）、`.rOLDREV`（服务器改动前）、`.rNEWREV`（服务器当前），可用 **triple diff** 三方对比。

**结构冲突**：仓库中文件被重命名/移动/删除，而本地副本还在编辑。合并分支改动用 `svn merge`，同样可能出现上述两类冲突。

### 第3题：Аспекты быстродействия системы. Влияние средств измерения на результаты. + Пирамида памяти и ее влияние на производительность.

#### A. 65. Аспекты быстродействия системы. Влияние средств измерения на результаты.

**俄语 / Русский ответ**

На производительность влияют:

- **системный/архитектурный** — распределенная, кластерная, виртуализированная архитектура;
- **низкоуровневый аппаратный** — тактовая частота, размер кэшей, конкуренция потоков;
- **программный** — выбор алгоритмов, пулы, многопоточность, блокировки;
- **человеческий** — ошибки, неверные архитектурные решения, слабое знание предметной области.

Работа похожа на научный эксперимент: выбрать критерии → средства измерения → нагрузку → собрать и исключить влияние измерений → изменить параметр → повторить.

**Средства:** неинтрузивные, слабоинтрузивные, интрузивные. Почти любое измерение искажает результат (например, сбор счетчиков тратит процессорное время), поэтому наведенные данные исключаются из анализа.

**中文 / 中文翻译**

性能影响因素：**系统/架构**（分布式、集群、虚拟化）、**底层硬件**（主频、缓存大小、线程竞争）、**软件**（算法选择、对象池、多线程、锁）、**人为**（错误、架构决策失误、领域知识不足）。

过程如同科学实验：选评价指标 → 选测量工具 → 设计负载 → 收集结果并剔除测量本身的影响 → 调整参数 → 重复。

测量工具分非侵入、弱侵入、侵入式。几乎所有测量都会影响结果（如系统计数器会占用 CPU），因此要排除测量带来的干扰。

#### B. 68. Пирамида памяти и ее влияние на производительность.

**俄语 / Русский ответ**

Пирамида памяти: сверху — дорогая и маленькая память (регистры, кэш L1/L2), ниже — оперативная, дальше — внешняя/диск. Чем ниже уровень, тем дороже по времени обращение: обращение к ОЗУ может быть в сотни раз медленнее регистров/L1, к диску — в сотни тысяч/миллионы раз.

Минимизация обращений к нижним уровням может повысить производительность в сотни/миллионы раз. Пример: если сопоставить такт с диалогом, то L1-кэш ≈ 4 с, L2 ≈ 30 с, ОЗУ — минуты, диск — дни/месяцы.

### 补充图示（来自 GitHub 旧答案）

![内存层次结构 / Пирамида памяти](https://raw.githubusercontent.com/alex-grandson/edu/main/MISPI/img/memory_pyromid.png)

*内存层次结构 / Пирамида памяти*

**中文 / 中文翻译**

存储金字塔：最上方是昂贵、量小的寄存器、L1/L2 缓存；往下是主存；再往下是外部存储/硬盘。越往下访问代价越高——访问主存比寄存器/L1 慢数百倍，访问磁盘慢成千上万、数百万倍。

减少对下层的访问可大幅（成百上千乃至百万倍）提升性能。类比：把 CPU 时钟比作对话，L1≈4 秒、L2≈30 秒、主存需数分钟、磁盘需数天/月。

### 第3题：Автоматизация тестов и ручное тестирование. + Источники данных для тестирования. Роли и деятельности в тестировании.

#### A. 55. Автоматизация тестов и ручное тестирование.

**俄语 / Русский ответ**

Автоматизация желательна, но ручное тестирование бывает дешевле и проще для простых задач (проще нанять персонал, чем писать и сопровождать скрипты).

**Регрессионное тестирование** — при изменении программы запускаются старые тесты, чтобы убедиться, что изменения не сломали остальное. Для автоматизации нужна однозначная воспроизводимость: одинаковые входные данные дают одинаковый результат. Также важна проверка совместимости в разных окружениях.

**中文 / 中文翻译**

自动化测试有价值，但简单场景下手动测试可能更便宜、更灵活。**回归测试**在代码改动后重跑旧测试，检查是否引入新问题。为使测试可自动化，须保证可重复性：相同输入产生相同输出。此外还需跨环境测试兼容性，这会提高测试复杂度。

#### B. 56. Источники данных для тестирования. Роли и деятельности в тестировании.

**俄语 / Русский ответ**

Два классических подхода: **черный ящик** (внутренности скрыты, тесты строятся по спецификации/опыту, сравнивают с эталоном) и **белый ящик** (можно анализировать код, строить граф, вычислять цикломатическую сложность — она указывает максимально необходимое число тестов).

**Источники данных:** спецификации, требования, дизайн, исходный код, UML-модели, опыт разработчика.

**Деятельности:** проектирование тестов (высокая квалификация: предметная область, UI, дискретная математика, программирование), автоматизация (модульные пишут разработчики, интеграционные/системные — отдельные программисты), непосредственное исполнение (не требует высокой квалификации), анализ результатов (нужны и предметные, и технические знания).

**中文 / 中文翻译**

两大方法：**黑盒**——程序内部隐藏，按规格说明/经验构造测试并与已知结果比较；**白盒**——可分析源码、构建控制流图并计算**圈复杂度**，圈复杂度指出覆盖所有路径所需的最少测试数。

**测试数据来源**：规格说明、需求、设计、源代码、UML 模型与开发者经验。

**测试活动**：测试设计（需较高水平，懂领域、UI、离散数学与编程）、自动化（模块测试由开发者写，集成/系统测试由专门程序员写）、测试执行（对资质要求不高）、结果分析（需领域与技术知识）。

- `src/main/java` — основные исходники Java;

### 第3题：Модульное тестирование. JUnit 4 с примерами. + Функциональное и End-to-End тестирование. Selenium.

#### A. 59. Модульное тестирование. JUnit 4 с примерами.

**俄语 / Русский ответ**

**Модуль** — компонент, который тестируется отдельно (метод, класс или их совокупность). Для изоляции используют **драйвер** (вызывает тестируемый модуль, задает параметры) и **заглушку/ stub** (заменяет подчиненный модуль, имеет тот же интерфейс, но простую реализацию и возвращает заранее заданные значения).

**JUnit 4** построен на аннотациях. `@Test` помечает тестовый метод (находится через reflection); проверки выполняются **assertion**, напр. `assertEquals`. `@Before`/`@After` выполняются до/после каждого теста; есть аннотации для подготовки/очистки при загрузке класса. Порядок тестов не регламентирован — они независимы и могут выполняться параллельно.

Пример:

```java
@Test
public void testAdd() {
    assertEquals(5, Calculator.add(2, 3));
}
```

**中文 / 中文翻译**

**模块**是能独立测试的组件（方法、类或它们的组合），设计时先分层再分模块。测试时需隔离模块：用**驱动（driver）**调用被测模块并传入不同参数，用**桩（stub）**代替其下属模块（同接口、简化实现、按表返回预设值）。

#### B. 61. Функциональное и End-to-End тестирование. Selenium.

**俄语 / Русский ответ**

**Функциональное** тестирование проверяет, что реализованный функционал соответствует пользовательским сценариям; может быть ручным или автоматизированным, часто начинается с UI.

**功能测试**根据用户场景判断系统功能是否正确，可手动也可自动化，通常从用户界面入手。

**端到端（E2E）测试**验证从起点到终点、贯穿整个系统的完整业务链路。例如电商：登录 → 搜索商品 → 加购物车 → 下单 → 支付 → 生成订单。

### 第3题：Статическое и динамическое тестирование. + Техники статического тестирования. Статический анализ кода.

#### A. 54. Статическое и динамическое тестирование.

**俄语 / Русский ответ**

**Статическое** — без запуска тестов, проверяются спецификация, архитектурные принципы, требования и т.п. **Динамическое** — требует уже созданной программной архитектуры и выполняется с запуском кода.

**TDD** (Test-Driven Development) — тесты разрабатываются перед написанием кода: на основе требований определяется покрытие, пишутся тесты, которые сначала выполняются со сбоями.

**中文 / 中文翻译**

**静态测试**不运行程序，检查规格说明、架构原则、需求等。**动态测试**需要已实现的软件架构，通过实际运行代码完成。

**TDD（测试驱动开发）**：先根据需求确定测试覆盖并编写测试，初始测试失败，再实现代码使其通过。

#### B. 62. Техники статического тестирования. Статический анализ кода.

**俄语 / Русский ответ**

Статическое тестирование не требует запуска и выявляет причины дефектов раньше, чем динамическое. Техники: **неформальное ревью** коллегой; **технический анализ** (под руководством технического лидера); **management review** (под руководством менеджера разработки); **walkthrough** (эксперт ведет аудиторию по артефакту); **инспекции** (по Фэгану, каждый инспектор контролирует не более двух параметров/ролей).

**Преимущества:** раннее обнаружение дефектов, рост продуктивности, меньше времени и стоимости тестирования, сокращение стоимости ЖЦ, улучшение коммуникаций.

**Статический анализ кода** выполняют инструменты: **Lint** (C), **FindBugs** (Java) — строят синтаксическое дерево и ищут неопределенное поведение, неинициализированные переменные, нарушение использования библиотек (fopen без fclose) и т.д.

**中文 / 中文翻译**

静态测试不需运行程序，能在更早阶段发现缺陷原因。**技术**：非正式代码评审（找同事）；技术评审（技术负责人主持）；管理评审（开发经理主持）；走查（专家带领逐一检查制品）；检查/审查（Fagan 提出，每人只控制最多两个参数/角色）。

**优点**：更早发现并修复缺陷、提高开发效率、减少测试时间和成本、降低成本、改善团队沟通。

**静态代码分析**由工具完成：**Lint**（C）、**FindBugs**（Java）。它们构造语法树，检查未初始化变量、违反库使用规范（如 fopen 未 fclose）、跨平台性破坏等。
