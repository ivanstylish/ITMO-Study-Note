### 第1题（原题 1）：ISO/IEC 12207:2010: Жизненный цикл ПО. Группы процессов ЖЦ.

**俄语答题 / Русский ответ**

Жизненный цикл ПО — период от возникновения потребности в системе до её вывода из эксплуатации. Он включает требования, анализ, проектирование, реализацию, тестирование, внедрение, эксплуатацию, сопровождение и вывод из эксплуатации.

Семь групп процессов ISO/IEC 12207: процессы соглашения; организационного обеспечения проектов; управления проектом; технические процессы; процессы реализации ПО; поддержки ПО; повторного использования ПО. Процессы могут повторяться и выполняться параллельно: это не обязательная последовательность стадий.

**中文对应**

软件生命周期是从产生系统需求到系统退役的全过程，包括需求、分析、设计、实现、测试、部署、运行、维护和退役。

ISO/IEC 12207 的七个过程组：协议过程、组织项目保障过程、项目管理过程、技术过程、软件实现过程、软件支持过程、软件复用过程。过程可重复或并行执行，并非必须依次进行的阶段。

### 第2题（原题 23）：Требования. Иерархия требований. Примеры формулировок на разных уровнях.

**俄语答题 / Русский ответ**

Требование — условие или возможность, которой должна соответствовать система. Оно должно быть ясным, однозначным и проверяемым. Уровни: потребность бизнеса → возможность системы или пользователя → конкретное требование к ПО.

Пример: «Сократить ручную обработку заказов» → «Покупатель может оформить заказ самостоятельно» → «REQ-01: после подтверждения корзины система должна создать заказ с уникальным номером и показать этот номер покупателю». Нижний уровень уточняет верхний.

**中文对应**

需求是系统必须满足的条件或能力，应清晰、无歧义且可验证。层次为：业务需要→系统或用户能力→具体软件需求。

例：“减少人工处理订单”→“买家能够自行下单”→“REQ-01：确认购物车后，系统应创建具有唯一编号的订单，并向买家显示该编号。”下一层细化上一层。

### 第3题：Рецепты повышения производительности при высоком %IO wait. + Рецепты повышения производительности при высоком %User.

#### A（原题 78）：Рецепты повышения производительности при высоком %IO wait.

**俄语答题 / Русский ответ**

Высокий `%iowait` означает значительную долю простоя CPU при наличии незавершённого I/O; это сигнал для проверки, а не прямое измерение скорости диска.

Проверяют `iostat`, `vmstat` и активность процессов. Меры: уменьшить объём и частоту I/O, объединять запросы, использовать кэш и последовательный доступ; устранить подкачку; при подтверждённом ограничении устройства использовать более подходящее хранилище, например SSD. Выравнивание и размер блоков выбирают по устройству и нагрузке, а не по универсальному правилу.

**中文对应**

`%iowait` 高表示存在未完成 I/O 时，CPU 空闲时间比例较高。它是需要排查的信号，不是对磁盘速度的直接测量。

使用 `iostat`、`vmstat` 并查看进程活动。措施：减少 I/O 总量和频率，合并请求，使用缓存和顺序访问；消除换页压力；确认设备成为瓶颈后，采用更合适的存储，例如 SSD。块大小和对齐方式取决于设备及负载，没有统一规则。

#### B（原题 80）：Рецепты повышения производительности при высоком %User.

**俄语答题 / Русский ответ**

Высокий `%User` означает, что CPU занят пользовательским кодом. Если производительность недостаточна, сначала профилируют приложение и находят горячие функции.

Меры: улучшить алгоритмы; убрать повторные вычисления и активное ожидание; сократить ненужные выделения и копирования; улучшить локальность данных и уменьшить cache/TLB misses; уменьшить конкуренцию потоков. Повторное использование объектов полезно, если оно снижает измеренные затраты. Затем рассматривают параллелизм, векторизацию, GPU или более мощный CPU и проверяют результат измерениями.

**中文对应**

`%User` 高表示 CPU 忙于用户态代码。性能不足时，先剖析应用并找到热点函数。

措施：改进算法；消除重复计算和忙等待；减少无必要的分配与复制；改善数据局部性，减少缓存／TLB 未命中；降低线程竞争。对象复用只有在确实降低开销时才有价值。之后再考虑并行、向量化、GPU 或更强 CPU，并通过测量确认结果。

### 第1题（原题 2）：Модели ЖЦ (последовательная, инкрементная, эволюционная).

**俄语答题 / Русский ответ**

- Последовательная модель: стадии проходят последовательно; основные требования определяются заранее.
- Инкрементная модель: продукт поставляется частями; каждый инкремент добавляет готовые функции и проходит разработку и тестирование.
- Эволюционная модель: решение и требования уточняются по результатам предыдущих версий и обратной связи.

Главное различие: последовательное выполнение стадий, поэтапное добавление функций или постепенное уточнение решения.

**中文对应**

- 顺序模型：按阶段依次推进，主要需求预先确定。
- 增量模型：分批交付产品，每个增量增加可用功能，并经过开发和测试。
- 演化模型：根据前一版本的结果与反馈，逐步明确需求和改进方案。

主要区别是：依次完成阶段、分批增加功能，或逐步明确解决方案。

CI 强调频繁集成小规模修改，并及时反馈失败。服务器保证检查可重复、结果可获取。例：Jenkins、GitLab CI、GitHub Actions。

### 第3题（原题 69）：Мониторинг производительности: процессы.

**俄语答题 / Русский ответ**

Процессы наблюдают командами `top`, `ps`, `pidstat`. Проверяют CPU, память, состояние процесса, число потоков и переключения контекста. В `top`: PR — приоритет, VIRT — виртуальное адресное пространство, RES — резидентная память, SHR — разделяемая память.

Load average в Linux учитывает выполняемые/готовые к выполнению задачи и задачи в непрерываемом ожидании. Его сопоставляют с числом CPU и другими метриками. `pidstat -u -r -w 1` помогает найти процессы с высокой загрузкой, ошибками страниц и переключениями контекста.

**中文对应**

通过 `top`、`ps`、`pidstat` 监控进程，查看 CPU、内存、进程状态、线程数和上下文切换。`top` 中 PR 是优先级，VIRT 是虚拟地址空间，RES 是驻留内存，SHR 是共享内存。

Linux 的 load average 包含运行中／可运行任务和不可中断等待任务。应结合 CPU 数量及其他指标判断。`pidstat -u -r -w 1` 可定位 CPU 占用、缺页和上下文切换较高的进程。

### 第1题（原题 3）：Водопадная (каскадная) модель.

**俄语答题 / Русский ответ**

Водопадная модель организует разработку по стадиям: требования → анализ → проектирование → реализация → тестирование → внедрение. Результат каждой стадии документируется и служит основой следующей; возможны возвраты для исправления ошибок.

Плюсы: понятные этапы, удобство планирования и контроля. Минусы: работающий продукт появляется поздно, изменения на поздних стадиях дороги. Подходит для стабильных и понятных требований.

**中文对应**

瀑布模型依次进行：需求→分析→设计→实现→测试→部署。各阶段的成果形成文档，作为下一阶段的依据；发现错误时可以返回修改。

优点：阶段清晰，便于规划和管理。缺点：可运行产品出现较晚，后期修改成本高。适用于稳定、明确的需求。

### 第2题（原题 42）：Системы сборки: Make и Makefile.

**俄语答题 / Русский ответ**

Make строит цели по правилам Makefile: `цель: зависимости`, затем команды с начальным TAB. Цель пересобирается, если отсутствует или хотя бы одна обычная зависимость новее неё.

Файл содержит правила, переменные, директивы и комментарии. `$@` — цель, `$<` — первая зависимость, `$^` — все зависимости без повторов, `$?` — зависимости новее цели. `.PHONY` объявляет цель без выходного файла, например `clean`. Пример правила: `main.o: main.c`, команда `$(CC) -c $< -o $@`. `make -f file` выбирает Makefile.

**中文对应**

Make 根据 Makefile 规则构建目标：`目标: 依赖`，下一行命令以 TAB 开头。目标不存在，或至少一个普通依赖比目标更新时，重新构建。

文件包含规则、变量、指令和注释。`$@` 是目标，`$<` 是首个依赖，`$^` 是去重后的全部依赖，`$?` 是比目标更新的依赖。`.PHONY` 声明不产生文件的伪目标，例如 `clean`。规则例：`main.o: main.c`，命令为 `$(CC) -c $< -o $@`。`make -f file` 指定 Makefile。

#### B（原题 74）：Создание тестовой нагрузки и нагрузчики.

**俄语答题 / Русский ответ**

Тестовая нагрузка должна отражать операции пользователей, интенсивность запросов, параллелизм, объём данных и длительность работы. Заранее задают ожидаемые метрики и критерии успешности.

方法：合成负载生成器便于配置场景，但可能偏离真实情况；记录并重放实际负载更接近运行环境。工具例：JMeter、LoadRunner。逐步提升负载，考虑预热，并确认生成器本身没有成为瓶颈。

### 第3题：Профилирование приложений. Основные подходы. + Компромиссы (trade-offs) в производительности.

#### A（原题 75）：Профилирование приложений. Основные подходы.

**俄语答题 / Русский ответ**

Профилирование определяет, где приложение тратит CPU и память, какие методы наиболее дороги и где потоки ждут блокировки.

Профилируют под представительной нагрузкой, находят горячие точки, изменяют код и повторяют измерение.

**中文对应**

#### B（原题 76）：Компромиссы (trade-offs) в производительности.

**俄语答题 / Русский ответ**

Оптимизация требует компромиссов между временем, памятью, ресурсами и сложностью.

Примеры: кэш ускоряет повторные запросы, но занимает память и требует обновления; индекс ускоряет поиск, но увеличивает размер данных и стоимость записи; сжатие уменьшает I/O, но расходует CPU; параллелизм повышает throughput, но добавляет синхронизацию.

Выбор зависит от узкого места и требований. Улучшение подтверждают измерениями на той же нагрузке, проверяя и побочные затраты.

**中文对应**

优化需要在时间、内存、资源和复杂度之间权衡。

### 第3题：Ключевые характеристики производительности. + Нисходящий метод поиска узких мест.

#### A（原题 66）：Ключевые характеристики производительности.

**俄语答题 / Русский ответ**

Основные характеристики:

- Время отклика/latency — задержка от запроса до оговорённого результата; границы измерения должны быть заданы.
- Throughput — число завершённых операций за единицу времени.
- Utilization — доля времени занятости ресурса; очередь показывает накопление ожидающей работы.
- Насыщение — рост нагрузки перестаёт давать сопоставимый рост throughput, а задержки растут.
- Масштабируемость — изменение производительности при добавлении ресурсов; эффективность — результат относительно затрат ресурсов.

Метрики оценивают вместе при известной нагрузке.

**中文对应**

主要特征：

- 响应时间／latency：从请求到约定结果的延迟，必须明确测量起止点。
- Throughput：单位时间完成的操作数。
- Utilization：资源忙碌时间比例；队列体现等待任务的积累。
- 饱和：负载增加不再带来相应吞吐量增长，而延迟上升。
- 可扩展性：增加资源后性能如何变化；效率：产出相对于资源消耗的水平。

应在已知负载下结合这些指标判断。

#### B（原题 67）：Нисходящий метод поиска узких мест.

**俄语答题 / Русский ответ**

Нисходящий поиск узкого места идёт от системы к деталям:

2. Измерить CPU, память, диски, сеть и очереди средствами ОС.
3. Найти проблемный процесс и исследовать алгоритмы, I/O, потоки и блокировки профилировщиком.

Узкое место ограничивает производительность всей системы. Исправляют подтверждённую причину и повторяют измерения с той же нагрузкой.

### 第3题（原题 71）：Мониторинг производительности: буферизированный файловый ввод-вывод.

**俄语答题 / Русский ответ**

`iostat -x 1`: `r/s`, `w/s` — операций в секунду; `rkB/s`, `wkB/s` — объём передачи; `await` — среднее время запроса, включая очередь; `%util` — доля времени занятости устройства. Рост ожидания и очереди указывает на возможное ограничение I/O. Случайный доступ особенно дорог на HDD.

**中文对应**

`iostat -x 1`：`r/s`、`w/s` 是每秒操作数；`rkB/s`、`wkB/s` 是传输量；`await` 是包含排队时间的平均请求耗时；`%util` 是设备忙碌时间比例。等待和队列增长可能表明 I/O 成为限制。随机访问在 HDD 上尤其昂贵。

3. 用 `svn status` 和 `svn diff` 检查变化；`svn revert` 撤销本地修改。

**俄语答题 / Русский ответ**

### 第3题：Аспекты быстродействия системы. Влияние средств измерения на результаты. + Пирамида памяти и ее влияние на производительность.

#### A（原题 65）：Аспекты быстродействия системы. Влияние средств измерения на результаты.

**俄语答题 / Русский ответ**

Производительность зависит от архитектуры системы, аппаратуры, алгоритмов и реализации, а также решений разработчиков. Важны распределение работы, память, I/O, конкуренция потоков и блокировки.

Измерение тоже потребляет ресурсы: меняет загрузку CPU, память и время выполнения. Средства бывают неинтрузивными, слабоинтрузивными и интрузивными. Нужно оценить накладные расходы, использовать одинаковую нагрузку и повторять измерения. Эксперимент: метрика → исходное измерение → одно изменение → повторная проверка результата.

**中文对应**

性能受系统架构、硬件、算法与实现以及开发决策影响。重点包括任务分配、内存、I/O、线程竞争和锁。

测量本身也消耗资源，会改变 CPU 负载、内存和执行时间。工具可分为非侵入、弱侵入和侵入式。应评估测量开销，使用相同负载并重复测量。实验流程：确定指标→测量基线→改变一个因素→再次验证结果。

#### B（原题 68）：Пирамида памяти и ее влияние на производительность.

**俄语答题 / Русский ответ**

Иерархия памяти: регистры → кэши L1/L2/L3 → RAM → SSD/HDD. Ниже по иерархии обычно больше объём и меньше стоимость хранения единицы данных, но выше задержка доступа.

Производительность повышает локальность: временная — повторное использование недавно прочитанных данных; пространственная — обращение к соседним адресам. Последовательный обход массива, компактные структуры и повторное использование данных уменьшают промахи кэша и медленные обращения. Подкачка на диск значительно увеличивает задержки.

**中文对应**

内存层次：寄存器→L1/L2/L3 缓存→RAM→SSD/HDD。层次越低，通常容量越大、单位存储成本越低，但访问延迟越高。

局部性有助于提升性能：时间局部性是复用最近访问的数据；空间局部性是访问相邻地址。顺序遍历数组、紧凑数据结构和数据复用可以减少缓存未命中及慢速访问。换页到磁盘会显著增大延迟。

### 第3题：Автоматизация тестов и ручное тестирование. + Источники данных для тестирования. Роли и деятельности в тестировании.

#### A（原题 55）：Автоматизация тестов и ручное тестирование.

**俄语答题 / Русский ответ**

Ручное тестирование выполняет человек; оно удобно для исследовательских проверок, оценки удобства и редко повторяемых сценариев. Автоматизированное тестирование выполняют инструменты; оно удобно для повторяемых проверок, регрессии и нагрузки, но требует затрат на создание и сопровождение тестов.

**中文对应**

手工测试由人执行，适合探索性检查、易用性评价和很少重复的场景。自动化测试由工具执行，适合重复检查、回归和负载测试，但需要编写和维护成本。

回归测试检查修改是否破坏了原有功能。可靠的自动化需要可控的数据和环境、可重复的操作及可检查的预期结果。兼容性需要在多个目标环境中验证。

**俄语答题 / Русский ответ**

В белом ящике граф потока управления помогает выбирать пути. Цикломатическая сложность характеризует число линейно независимых путей и используется для базисного тестирования, а не для подсчёта всех возможных сценариев.

Maven 标准结构：`pom.xml` 是项目描述；`src/main/java` 是主代码；`src/main/resources` 是资源；`src/test/java` 是测试；`src/test/resources` 是测试资源；`target` 是构建结果。

GAV 是制品坐标：`groupId:artifactId:version`。GroupId 表示组织或分组，artifactId 表示项目或制品，version 表示版本。例如 `org.example:shop:1.0`。项目本身及其依赖都使用坐标标识。

#### B（原题 47）：Maven: Зависимости. Жизненный цикл сборки. Плагины.

**俄语答题 / Русский ответ**

Зависимости объявляются в POM. Транзитивность: если A зависит от B, а B от C, A может получить C косвенно; это зависит от scope и исключений. Scope: `compile` — по умолчанию; `provided` — доступна при компиляции, предоставляется средой выполнения; `runtime` — выполнение; `test` — тесты; `system` — явно заданный локальный файл.

Жизненные циклы: clean, default, site. Основные фазы default: validate → compile → test → package → verify → install → deploy. Вызов фазы выполняет предыдущие фазы этого цикла. Плагин содержит цели (goals), которые выполняют работу и могут быть привязаны к фазам.

**中文对应**

依赖在 POM 中声明。传递性：若 A 依赖 B、B 依赖 C，A 可能间接获得 C，具体受 scope 和排除规则影响。Scope：`compile` 为默认；`provided` 在编译时可用，运行时由环境提供；`runtime` 用于运行；`test` 用于测试；`system` 使用明确指定的本地文件。

生命周期有 clean、default、site。Default 主要阶段：validate→compile→test→package→verify→install→deploy。调用某阶段会执行同一周期中此前的阶段。插件提供执行具体工作的目标（goals），目标可绑定到阶段。

### 第3题：Модульное тестирование. JUnit 4 с примерами. + Функциональное и End-to-End тестирование. Selenium.

#### A（原题 59）：Модульное тестирование. JUnit 4 с примерами.

**俄语答题 / Русский ответ**

Модульное тестирование проверяет отдельный метод, класс или компонент в изоляции. Драйвер вызывает модуль, заглушка (stub) заменяет его зависимость и возвращает подготовленные значения.

В JUnit 4 `@Test` отмечает тест, `assertEquals` проверяет результат. `@Before/@After` выполняются перед/после каждого теста, `@BeforeClass/@AfterClass` — один раз до/после тестов класса; последние методы должны быть `public static void`. Тесты не должны зависеть от порядка выполнения. Пример:

```java
import org.junit.Test;
import static org.junit.Assert.assertEquals;

public class SumTest {
    static int add(int a, int b) { return a + b; }
    @Test public void addsTwoNumbers() {
        assertEquals(5, add(2, 3));
    }
}
```

**中文对应**

单元测试隔离检查一个方法、类或组件。驱动（driver）调用被测模块，桩（stub）替代其依赖并返回预设值。

JUnit 4 用 `@Test` 标记测试，用 `assertEquals` 检查结果。`@Before/@After` 在每个测试前后执行；`@BeforeClass/@AfterClass` 在整类测试前后各执行一次，后两者的方法必须是 `public static void`。测试不应依赖执行顺序。

上方完整例子定义加法函数，并断言 `add(2, 3)` 的结果为 `5`。

#### B（原题 61）：Функциональное и End-to-End тестирование. Selenium.

**俄语答题 / Русский ответ**

Функциональное тестирование проверяет соответствие функций требованиям: при заданном вводе получается ожидаемый результат. Оно возможно на уровне API и интерфейса пользователя, вручную или автоматически.

End-to-End проверяет полный бизнес-процесс через все участвующие компоненты. Пример: вход → выбор товара → корзина → оплата → подтверждение заказа.

Selenium WebDriver управляет браузером: открывает страницы, находит элементы, вводит данные и нажимает кнопки. В тесте затем проверяется ожидаемый результат, например появление номера заказа.

**中文对应**

功能测试检查功能是否符合需求，即给定输入是否产生预期结果。可在 API 或用户界面层开展，既可手工也可自动化。

端到端测试检查贯穿所有参与组件的完整业务流程。例如登录→选商品→购物车→付款→确认订单。

Selenium WebDriver 控制浏览器，打开页面、定位元素、输入数据并点击按钮。之后在测试中检查预期结果，例如是否出现订单编号。

### 第3题：Статическое и динамическое тестирование. + Техники статического тестирования. Статический анализ кода.

#### A（原题 54）：Статическое и динамическое тестирование.

**俄语答题 / Русский ответ**

Статическое тестирование проверяет артефакты без выполнения программы: требования, модели, документацию и код. Методы — рецензирование и автоматический статический анализ.

Динамическое тестирование запускает код с заданными данными и сравнивает фактический результат с ожидаемым. Пример: выполнить функцию и проверить возвращённое значение.

TDD: написать падающий тест → реализовать минимальный код для его прохождения → выполнить рефакторинг и повторить тесты (Red–Green–Refactor).

**中文对应**

静态测试不执行程序，而是检查需求、模型、文档和代码。方法包括评审和自动静态分析。

动态测试使用指定数据运行代码，将实际结果与预期结果比较。例如执行函数并检查返回值。

TDD：先编写失败的测试→实现使测试通过的最少代码→重构并重新测试，即红—绿—重构循环。

#### B（原题 62）：Техники статического тестирования. Статический анализ кода.

**俄语答题 / Русский ответ**

Статическое тестирование проверяет артефакты без выполнения программы. Основные техники: неформальное ревью, техническое и управленческое ревью, walkthrough (автор проводит участников по материалу), формальная инспекция с ролями, чек-листами и регистрацией дефектов.

Статический анализ автоматически исследует код или байткод: ищет неинициализированные значения, недостижимый код, нарушения типов и неправильное использование ресурсов. Примеры: Lint, FindBugs. Преимущество — раннее обнаружение дефектов и снижение стоимости исправлений; результаты требуют проверки.

**中文对应**

静态测试不运行程序，而是检查制品。主要技术：非正式评审、技术评审、管理评审、走查（作者带领参与者检查材料），以及包含角色、检查表和缺陷记录的正式审查。

静态分析自动检查源码或字节码，查找未初始化值、不可达代码、类型问题及资源使用错误。工具例：Lint、FindBugs。优点是尽早发现缺陷、降低修复成本；分析结果仍需核实。
