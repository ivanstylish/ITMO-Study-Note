# 实验二学习指南：GoF 与 GRASP 设计模式

本指南帮助你完成实验二的模式选择、场景设计与局限性分析。以本地实验要求和课程教材为基础，用中文解释概念，保留英文及常用俄文名称以便查阅和答辩。文中的业务场景为学习示例，不是教材原例，也不是已经完成验证的系统设计。

## 1. 先明确实验要交什么

依据 [实验二原始要求](readme.md)：

1. 从 GoF 和 GRASP 两份列表中，**合计选择 3–4 种模式**。
2. 每种模式构思 **2–3 个应用场景**。
3. 对**每个场景**分析采用该模式可能带来的限制或代价。
4. 必须同时覆盖 GoF 和 GRASP。

因此可以选择 4 种模式，每种 2 个场景，共 8 个场景。题面没有明确要求编程、运行测试或提交 UML 图。类关系和调用过程有助于说明设计，但不要将它们误认为题面额外规定。

完成实验需要回答：**这里有什么具体问题？模式如何解决？为什么适用？为了得到这些收益，需要付出什么代价？**

## 3. 必须先懂的基础知识

### 3.1 对象、状态、行为与职责

对象包含状态，也执行行为。例如订单有订单项、状态和金额，可以添加订单项、计算总价、变更状态。

**职责（responsibility / ответственность）**是一个对象应该知道什么、应该完成什么。例如：

- 订单项知道购买数量和成交单价。
- 订单项负责计算自己的小计。
- 订单知道有哪些订单项，负责汇总金额。
- 页面负责展示金额。

先把职责说清楚，再决定由哪个类承担，这是学习 GRASP 的起点。

### 3.2 接口与多态

接口描述“可以做什么”，具体实现描述“怎么做”。

例如 `ShippingPolicy.calculate(shipment)` 表示计算运费，普通配送和加急配送分别实现它。调用者通过统一接口使用不同实现，这就是多态的典型用法。

你需要理解：调用方为什么可以依赖接口，替换实现时哪些地方不用改，以及谁负责选择具体实现。Session 03 第 3–5 页是这个知识点的直接材料。

### 3.3 继承、组合与委托

- **继承**：子类扩展父类行为。
- **组合**：对象持有另一个对象，用它完成一部分工作。
- **委托**：对象将某项工作交给协作对象执行。

策略模式通常采用组合与委托，例如配送报价器持有一个运费策略，再把计算交给该策略。不要为了替换一个算法就给整个业务对象建立很深的继承树。教材第 125 页对比了 Strategy 与基于继承的 Template Method。

### 3.4 耦合与内聚

**耦合（coupling / связанность）**：一个部分对其他部分的依赖程度。订单直接调用每一个通知服务的具体实现，新增通知渠道就可能要改订单，说明两者依赖紧密。

**内聚（cohesion / связность）**：一个类内部职责的相关程度。订单处理自己的业务规则较为集中，如果它同时负责邮件、报表、数据库连接和页面绘制，职责就过于分散。

设计通常追求较低耦合与较高内聚，但不能只看类数量。增加接口可能降低对具体实现的依赖，同时也增加理解和配置成本。

### 3.5 模式与架构的层次

GoF 主要讨论对象创建、结构和协作中的常见设计问题。GRASP 主要帮助判断职责应该分配给谁。两者可以一起使用。

例如：用 GRASP 决定订单负责管理订单项，用 GoF Strategy 封装可替换的运费算法。这是不同角度的设计决定。

不要直接用分层架构、微服务或 MVC 替代本实验要求的 GoF/GRASP 选项。Session 03 第 6–7 页区分了设计模式与范围更大的架构模式。

## 4. 两套模式列表需要了解多少

### 4.1 GoF：认识分类，重点学选中的模式

GoF 常见的 23 种模式分为三类。下表作为检索地图，不要求在实验前全部熟练掌握。

| 类别 | 解决的问题 | 模式名称 |
| --- | --- | --- |
| 创建型 | 对象如何创建 | Abstract Factory、Builder、Factory Method、Prototype、Singleton |
| 结构型 | 类和对象如何组成结构 | Adapter、Bridge、Composite、Decorator、Facade、Flyweight、Proxy |
| 行为型 | 对象如何协作与分配行为 | Chain of Responsibility、Command、Interpreter、Iterator、Mediator、Memento、Observer、State、Strategy、Template Method、Visitor |

本指南重点选择 **Strategy 和 Observer**，因为本地教材对两者的适用性与代价都有直接讲解。

### 4.2 GRASP：先知道它们分别回答什么

下面是 GRASP 的九项常见模式或原则的速查说明，依据前述 [Larman 教材摘要](https://www.rose-hulman.edu/class/cs/csse374/Resources/larmanCovers.pdf)。

| 名称 | 学习时要问的问题 |
| --- | --- |
| Information Expert，信息专家 | 谁掌握完成这项职责所需的信息？ |
| Creator，创建者 | 谁与目标对象的包含、记录、使用或初始化最相关，适合负责创建？ |
| Controller，控制器 | 谁接收界面层之外的系统操作并协调处理？ |
| Low Coupling，低耦合 | 怎样分配职责可以减少不必要的依赖？ |
| High Cohesion，高内聚 | 怎样让每个对象的职责保持集中？ |
| Polymorphism，多态 | 能否让不同类型自行实现各自的变化行为？ |
| Pure Fabrication，纯虚构 | 是否需要引入不对应业务实体的类来保持良好设计？ |
| Indirection，间接层 | 能否通过中介减少对象间的直接依赖？ |
| Protected Variations，受保护变化 | 能否用稳定接口隔离预期的变化？ |

本指南重点选择 **Information Expert 和 Creator**。低耦合、高内聚则用于评价这两种职责分配是否合理，不另算选中的模式。

## 5. 推荐组合：四种模式、八个场景

| 模式 | 所属列表 | 解决的主要问题 | 两个学习场景 |
| --- | --- | --- | --- |
| Strategy，策略，Стратегия | GoF，行为型 | 同一类任务的算法如何替换 | 运费计算、路线规划 |
| Observer，观察者，Наблюдатель | GoF，行为型 | 状态变化如何通知多个依赖者 | 订单状态通知、传感器监测 |
| Information Expert，信息专家，Информационный эксперт | GRASP | 计算或判断职责应放在哪里 | 订单总额、借阅逾期判断 |
| Creator，创建者，Создатель | GRASP | 哪个对象应该负责创建另一个对象 | 订单创建订单项、编辑器创建图形 |

### 5.1 Strategy：把可替换的算法独立出来

**教材依据：**`gof-frameworks.pdf` 第 123–125 页。

核心思想：把同一类任务的多种算法封装在统一接口后，让使用算法的对象可以选择或替换具体算法。

主要角色：

- `Context`：需要算法的业务对象。
- `Strategy`：统一算法接口。
- `ConcreteStrategy`：具体算法实现。
- 选择策略的调用方或配置逻辑：决定何时使用哪一种。

#### 场景 S1：配送运费计算

**背景与问题：**同一配送报价功能支持普通配送和加急配送，两者价格规则不同，未来还会加入其他配送方式。若所有规则混在报价器中，它就会随着每一种规则变化而修改。

**方案：**`ShippingQuote` 持有 `ShippingPolicy`，具体实现为 `StandardShippingPolicy` 和 `ExpressShippingPolicy`。接口统一接收重量、距离、目的地等报价数据，返回同一币种的运费。

**调用过程：**用户选择配送方式 → 调用方选择策略 → 报价器调用 `policy.calculate(shipment)` → 返回运费。

**收益：**每一种计费规则可以独立修改和检验，报价器只依赖统一接口。

**局限与适用边界：**

- 加急配送若需要额外的时段或容量信息，原接口可能不足。强行添加大量可选参数，会使接口变得难用。
- 策略不会自动决定“选哪个”。方式与策略的映射仍然需要维护。
- 若系统始终只有一个简单且稳定的公式，增加策略接口可能没有实际收益。

#### 场景 S2：导航路线规划

**背景与问题：**用户可以选择驾车、步行或骑行，各方式允许通行的道路和路径成本不同。

**方案：**`RoutePlanner` 使用 `RoutingStrategy`，由 `DrivingStrategy`、`WalkingStrategy`、`CyclingStrategy` 实现规划方法，统一返回路线结果。

**调用过程：**输入起终点和出行方式 → 选择具体策略 → 策略筛选可用道路并计算路线 → 返回路线。

**收益：**不同出行方式的规则隔离，增加方式时可以扩展实现。

**局限与适用边界：**

- 各方式需要的数据可能不同，统一接口必须明确哪些数据可用，不能依靠隐含假设。
- 切换策略不能保证地图准确、路况实时，也不保证所有算法都具有相同的性能。
- 同时考虑换乘、驾车和步行的组合路线，可能需要更高层的规划协调，单纯切换一种策略不足以完成。

**学会的标志：**你能说清楚不变的业务入口、变化的算法、统一接口和策略选择者。

### 5.2 Observer：让多个对象订阅状态变化

**教材依据：**`gof-frameworks.pdf` 第 10–14 页，尤其是第 14 页的更新开销、意外更新、引用与推送/拉取问题。

核心思想：建立一对多依赖。被观察对象发生相关变化时，通知已经注册的观察者。

角色包括被观察对象 `Subject`、观察者接口 `Observer` 和具体观察者。基本动作是订阅、取消订阅、通知。

推送方式在通知里携带数据。拉取方式让观察者收到通知后读取所需状态。选择时要考虑通知粒度、数据量和读取时状态是否已经变化。

#### 场景 O1：订单状态变化通知

**背景与问题：**订单进入“已发货”状态后，用户通知模块和运营看板都需要响应。若订单直接调用两个模块，以后每增加一个接收者就要修改订单。

**方案：**将订单状态变化发布者作为 `Subject`，通知模块和看板通过 `OrderStatusObserver` 注册。在状态变更成功后通知订阅者。

**调用过程：**订单状态成功变更 → 发布包含订单编号和新状态的通知 → 各观察者分别处理。

**收益：**发布者通过观察者接口发通知，无需依赖每个具体接收模块。

**局限与适用边界：**

- 同步调用观察者时，发送邮件等慢操作会拖慢业务调用，异常处理不当还可能阻断后续通知。
- 普通进程内观察者不会自动保证崩溃后重发，也不会提供持久化、跨进程可靠投递或恰好一次处理。
- 异步化后，需要另外考虑顺序、重复通知和状态版本。业务需要可靠投递时，应另外设计事务边界及消息机制。

#### 场景 O2：温度传感器监测

**背景与问题：**同一温度采集模块需要更新实时曲线和告警模块，后续可能增加其他监测视图。

**方案：**`TemperatureSource` 作为 `Subject`，`ChartObserver` 和 `AlarmObserver` 分别订阅温度事件。

**调用过程：**获得读数 → 通知观察者 → 曲线更新 → 告警模块独立判断是否超限。

**收益：**采集模块与具体展示、告警逻辑分离。

**局限与适用边界：**

- 高频读数逐条通知可能造成界面卡顿或处理积压，需要按实际需求采样、过滤或合并。
- 读数在阈值附近抖动可能导致重复告警，告警规则仍需设计滞回或去重。
- 观察者关闭后若不取消订阅，可能仍接收更新或因被引用而无法释放。

**学会的标志：**你能明确谁订阅谁、何时通知、通知包含什么，以及慢观察者或失败观察者会产生什么影响。

### 5.3 Information Expert：让掌握信息的对象承担相应职责

**补充依据：**[Larman 教材摘要](https://www.rose-hulman.edu/class/cs/csse374/Resources/larmanCovers.pdf)中的 Information Expert。下面是对原则的应用推演。

先列出一项职责所需的信息，再看哪个对象已经掌握它。信息可能由几个协作对象分别持有，因此职责也可以分解并委托。

#### 场景 E1：计算订单总额

**背景与问题：**需要汇总订单金额。如果界面取出所有内部数据自己计算，同一业务规则容易在不同界面重复。

**方案：**`OrderLine` 持有数量与成交单价，计算自己的小计。`Order` 持有订单项，负责汇总这些小计。这里假定讨论商品合计，不混入额外的税费和运费规则。

**调用过程：**界面请求 `order.total()` → 订单向各订单项请求 `subtotal()` → 汇总并返回金额。

**收益：**计算靠近所需信息，调用方不必知道订单内部计算过程。

**局限与适用边界：**

- 订单项应保存成交时的价格，直接读取商品当前价格可能使历史订单金额随调价变化。信息专家原则本身不会自动解决数据建模错误。
- 如果加入外部税务、跨订单促销等规则，不应把所有外部依赖都塞进订单，应结合内聚和耦合重新分配职责。
- 订单项尚未加载或数量很大时，逐项汇总可能涉及加载和性能成本，需要结合数据获取方式判断。

#### 场景 E2：判断图书借阅是否逾期

**背景与问题：**界面与提醒服务都需要判断借阅是否逾期，不能各写一套不同规则。

**方案：**`Loan` 持有到期时间和归还状态，负责 `isOverdue(asOf)`。以传入的判断时刻为基准，本场景规定到期时间之前或相等不算逾期，超过且未归还才算逾期。

**调用过程：**调用方传入判断时刻 → 借阅记录检查归还状态及到期时间 → 返回判断结果。

**收益：**判断依赖的信息集中在借阅对象内，界面与提醒服务复用同一规则。

**局限与适用边界：**

- 如果借阅政策使用“到期日当天闭馆前”而不是精确时间，需要先明确时区、营业日和时间边界。
- 续借、特殊读者豁免或节假日政策需要额外信息，不能仅凭一个时间比较覆盖全部业务。
- 把系统当前时间直接写死在对象内部会影响可重复检验，传入判断时刻能让边界更明确。

**学会的标志：**你能画出“职责需要的信息 → 信息所在对象 → 最终职责分配”的对应关系，并解释例外。

### 5.4 Creator：让创建职责靠近包含关系和初始化信息

**补充依据：**[Larman 教材摘要](https://www.rose-hulman.edu/class/cs/csse374/Resources/larmanCovers.pdf)中的 Creator。下面是对原则的应用推演。

如果 B 包含、记录、紧密使用 A，或掌握 A 的初始化信息，可以考虑让 B 创建 A。存在多个候选者时，应同时衡量内聚、耦合与生命周期。

**它与 Factory Method 的区别：**Creator 帮助决定“创建职责交给谁”。GoF Factory Method 通过可被子类重定义的创建方法，允许改变具体产品类型。一个类里出现 `new` 并不意味着实现了 Factory Method。

#### 场景 C1：订单创建订单项

**背景与问题：**新增订单项必须关联正确的订单，并记录数量和成交价格。如果界面直接创建并修改订单内部集合，就容易绕过订单状态约束。

**方案：**由 `Order.addItem(productSnapshot, quantity)` 校验订单是否允许修改、数量是否有效，再创建并保存 `OrderLine`。订单包含订单项，也掌握必要的上下文。

**调用过程：**调用方请求添加商品 → 订单验证输入和状态 → 创建订单项 → 纳入订单。

**收益：**创建与归属关系集中，容易保持“已确认订单不能随意修改”等约束。

**局限与适用边界：**

- 订单依赖订单项的具体构造方式，构造规则变复杂时会增加订单职责。
- 如果创建过程必须访问远程定价、库存和权限服务，全部放进订单会增加外部依赖，可能需要由应用服务先协调再传入已确认的数据。
- 创建成功不等于持久化成功，也不自动解决并发、事务和库存一致性。

#### 场景 C2：图形编辑器创建图形对象

**背景与问题：**编辑器需要在当前文档内创建矩形和圆形，并赋予文档标识、坐标及默认样式。多个工具若各自操作内部集合，初始化容易不一致。

**方案：**`DrawingDocument.addRectangle(...)` 或 `addCircle(...)` 根据文档的默认设置创建图形并记录。文档保存这些图形，也掌握初始化上下文。

**调用过程：**绘图工具传入几何参数 → 文档验证参数并补充默认值 → 创建并纳入图形集合。

**收益：**归属关系、默认值和基本约束由文档统一维护。

**局限与适用边界：**

- 图形类型大量增加时，文档可能积累许多创建方法，并依赖每种具体类型。
- 插件动态提供新图形时，文档不宜持续写死全部类型，可能需要把具体构造委托给注册的工厂。
- 创建接口本身不提供撤销、重做或文件保存，这些能力需要分别设计。

**学会的标志：**你能指出创建者为什么比界面或任意工具类更适合，并说明何时应委托专门的构造机制。

## 6. 怎样写出合格的“局限性”

教材第 9 页把后果和权衡列为模式的基本部分。实验要求你把这一部分落到每个场景。

只写“增加复杂度”不够明确。建议按下面的因果链写：

> 当【具体条件】出现时，由于模式采用了【具体机制】，会导致【可观察的问题】。可以通过【处理办法】缓解，但仍要承担【代价或边界】。

例如：

> 当订单观察者同步调用邮件服务时，外部邮件响应慢会延长订单处理时间。可以把通知交给异步任务，但需要另外处理重复投递、重试和消息顺序。

分析时可检查这些方向，但每个场景只写真正相关的：

| 方向 | 要检查的问题 |
| --- | --- |
| 复杂度 | 多了哪些接口、类、注册关系或配置？ |
| 性能 | 是否多了调用、数据复制、重复计算或广播？ |
| 可靠性 | 一个协作者失败后，其他工作是否还能继续？ |
| 一致性 | 状态是否可能过期，是否可能乱序或重复处理？ |
| 生命周期 | 谁创建、持有和释放对象，是否需要取消订阅？ |
| 扩展边界 | 新需求是否仍符合原接口和职责划分？ |
| 不适用条件 | 简单函数、直接调用或现有对象是否已经足够？ |

注意：模式带来的设计代价，与该模式没有承诺解决的问题，应分别说清。例如观察者的更新开销是其直接代价，而跨进程可靠投递是需要额外机制满足的需求。

## 7. 整理实验内容时可以使用的结构

以下是建议结构，不是题面规定的报告格式。

### 每种模式先写一次

1. 名称、所属列表与基本意图。
2. 适用条件和主要角色。
3. 教材或补充参考出处。

### 每个场景分别写

1. **背景**：哪一种系统、谁要完成什么操作？
2. **问题**：当前设计哪里难修改、重复或依赖过多？
3. **角色映射**：具体业务对象分别对应模式的哪些角色？
4. **交互**：按先后顺序说明对象如何配合。
5. **收益**：哪个变化点被隔离，哪个职责变清楚？
6. **局限性**：触发条件、具体后果及必要时的缓解办法。

不必为了展示 UML 画完整系统。需要图时，只画本场景相关类及其依赖、实现或包含关系。时序图则用于解释“谁先调用谁”，尤其适合 Observer。

## 8. 建议学习顺序与自测

### 第一遍：建立概念

阅读教材第 7–9 页和 Session 03 第 3–7 页。尝试解释：为什么模式需要上下文？接口与具体实现有什么区别？降低耦合需要付出什么代价？

### 第二遍：掌握两种 GoF 模式

先学 Strategy，再学 Observer。分别用自己的话写出角色和一次调用过程，再对照第 5 节检查。重点阅读教材第 14、124–125 页的代价分析。

### 第三遍：掌握两种 GRASP 模式

把订单场景拆成“谁算小计、谁算合计、谁创建订单项”，分别用 Information Expert 与 Creator 解释。再用高内聚、低耦合检查这一分配是否会让订单承担过多职责。

### 第四遍：独立写场景

可以参考本指南，但建议替换至少一个业务背景，独立写出角色与限制，确认自己理解了模式。如果继续使用实验一的系统，可以沿用其业务背景，但实验二题面没有强制要求与实验一使用同一系统。

### 答辩自测题

| 问题 | 回答要点 |
| --- | --- |
| GoF 和 GRASP 有什么区别？ | GoF 给出常见对象设计问题的协作方案，GRASP 帮助分配对象职责，两者可以共同使用。 |
| Strategy 和普通分支有什么区别？ | 策略把算法实现分离到共同接口之后，调用方委托执行。简单稳定的分支也可能已经足够。 |
| Strategy 与 State 有什么区别？ | 策略强调可替换算法，状态模式强调对象随内部状态变化而改变行为及状态转换。 |
| Observer 能保证所有订阅者可靠收到消息吗？ | 普通实现不能自动保证，可靠性取决于具体通知机制、持久化、重试和处理逻辑。 |
| Information Expert 是否意味着所有逻辑都放进实体？ | 需要看信息归属，同时检查内聚与耦合，跨对象或外部系统规则可能需要其他协作者。 |
| Creator 和 Factory Method 是不是同一个模式？ | 不是。前者分配创建职责，后者通过创建方法及子类扩展具体类型。 |
| 为什么不用 Singleton 作为最容易的选项？ | 可以选，但要认真解释唯一实例的范围、共享状态及测试代价。Session 03 第 13 页还提醒了线程安全与隐藏耦合。 |
| 为什么每个场景都要写局限性？ | 同一模式在不同约束下代价不同，这是题面明确要求，也是评价适用性的必要部分。 |
