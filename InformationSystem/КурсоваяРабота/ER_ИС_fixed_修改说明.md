## 实际修改

| 项目 | 修订结果 |
|---|---|
| 关系可选性 | 每笔库存变动可以关联 0 或 1 个生产批次；一次物流操作可以对应 0 或 1 个原料批次，而每个原料批次恰好来自一次物流操作；投诉可以暂未关联生产批次。为支持尚未定位订单的投诉，也同步允许其销售关系暂缺 |
| 员工任务 | 新增 `task`，保存描述、地点、状态、期限、创建／完成／确认时间及完成说明；分别关联 `employee` 为 `created_by`、`assigned_to`、`confirmed_by`，并关联 `solid_waste`。创建者和执行者必需，确认者在未确认时允许不存在 |
| 服务类型 | 新增 `service_type`，保存名称、说明和启用状态；每次 `visit` 必须属于一个服务类型，一个类型可用于多次来访 |
| 资产成交 | 新增 `buyer` 和 `asset_sale`，以实际 `total_amount` 记录一笔成交收入；一笔成交包含一件或多件资产，未售资产可没有成交关系。资产上的销售日期及买方姓名移到成交／买方结构中，资产估值保留 |
| 员工多角色 | 新增 `role`、`employee_role`，移除单值的 `employee.role`；通过关联实体表达员工与角色的多对多 |
| 生产损耗简化 | 删除 `production_waste` 及其与员工、库存项、生产批次的三条关系；损耗通过 `stock_movement` 的 `movement_type = loss` 表示。保留 `solid_waste` 及其任务关联，用于废弃物和处置管理 |

相对最初的图，新增 6 个实体、删除 1 个实体，当前共 **24 个实体、35 条关系**。保留的 18 个原有实体框位置及宽度不变；删除属性的实体高度相应缩短。新增实体安排在原布局空白处，受影响的路径重新绕行。

## 保留的建模约定

1. 本次交付为概念 ER 图，不添加 PK/FK 属性。关系模型阶段再确定键、SQL 类型、可空性及约束。
2. 一次来访选择一种服务；理发与剃须组合可作为一个服务类型。
3. `recipe` 的一条记录表示一版不可变的配方，历史批次保持关联原版本；本次不拆出 `recipe_version`。
4. `sales_transaction` 的一条记录表示销售一个生产批次的产品；本次不增加多行小票结构。
5. 已删除 `production_waste`。仍在库存中的原料发生损耗时，以 `stock_movement` 记录 `loss`、正数损耗数量、原因和时间，关联库存项、经办员工及适用的生产批次。此前已领料扣减的数量不能再重复扣库；`solid_waste` 登记和任务完成本身不再次减少库存。
6. 一项处置任务关联一条废弃物记录；一条废弃物记录可有多项任务。未完成确认时，任务确认关系可以不存在。
7. `asset_sale` 表示已确认成交，至少包含一件资产；一件资产最多属于一笔成交。实际总金额保存在成交实体，估值不替代收入。

这些约定来自此次选择的简化方案，不代表第一阶段所有需求都已在数据库中实现。独立处置操作、批次召回、通知、完整审计字段及其他扩展仍属于此前评审中提出的后续完善项，本次没有全部加入。
