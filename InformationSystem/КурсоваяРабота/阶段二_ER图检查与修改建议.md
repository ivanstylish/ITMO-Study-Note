# 阶段二 ER 图检查与修改建议

检查日期：2026-10-20。依据：本文件夹中的 `ER_ИС.drawio`、`Этап_1_v1_5—_Флит_Стрит_Мануфактура_—монолит.docx` 和 `readme.md`。以下是现有模型的评审意见和建议方案，尚不代表教师已确认的模型。本次未修改原 drawio 或 Word。

## 1 结论

**现有图可以作为修改基础，已满足实体数量与多对多关系的形式要求，但业务覆盖、关系可选性和标识符尚不完整，不能直接认定为正确的最终 ER 模型或据此直接实现数据库。**

实际读取 drawio 源文件后统计：

| 检查项 | 结果 | 判断 |
|---|---|---|
| 实体及关联实体框 | 19 个 | 满足至少 10 个的要求 |
| 配方与库存项之间的多对多 | `recipe` — `recipe_ingredient` — `stock_item` | 已通过关联实体表达，满足多对多要求 |
| 生产批次与原料批次之间的多对多 | `production_batch` — `batch_raw_material` — `raw_material_batch` | 设计方向合理，但关联实体到生产批次的一端未绑定对象 |
| drawio 连线 | 29 条，其中 10 条至少一端未绑定；另有 1 条物流记录自身指向自身的连线 | 需要修复绘图结构；不能仅根据截图判定每条线都正确连接 |
| 第一阶段业务覆盖 | 已覆盖主要业务链；缺少任务、处置记录、服务类型、实际资产销售金额等关键事实 | 需要补齐 |
| 主键、候选键和关系模型约束 | 图中未明确标出 | 概念 ER 可以不列 SQL 类型，但应标识如何区分实体；转关系模型时必须落实 PK、FK 等 |

这里的多对多已经被拆成两条一对多，这是正确做法，不需要为了课程要求再额外画一条直接的多对多线。

数据库表的数量与微服务数量无关。补齐必要实体后，应用仍可按上一阶段方案作为一个单体部署。

## 2 优先修改的问题

### 2.1 库存变动错误地强制关联生产批次

**位置：**`stock_movement` 与 `production_batch`。drawio 第 98 行的连线，生产批次一端为 `ERmandOne`，表示每条库存变动必须属于一个生产批次。

**为什么不成立：**UC04 的原料接收入库、UC05 的采购、盘点调整和非生产损耗都可能发生在没有生产批次的时候。

**建议关系：**

- 一条库存变动必须属于一个库存项。
- 一个库存项可以有零到多条库存变动。
- 一条库存变动可以关联零或一个生产批次，生产领料时才要求有批次。
- 一个生产批次可以关联零到多条库存变动，具体最低数量由批次状态和启动操作约束。

在关系模型中，`stock_movement.production_batch_id` 应允许为空。生产领料必须有关联批次的规则，可以按 `movement_type` 另外约束。原料接收还应能关联原料批次或接收记录，避免“知道数量增加，却找不到来源”。

### 2.2 物流与原料之间的一对一遗漏了等待状态

**位置：**`chlie_log` 与 `raw_material_batch`，当前连线两端均为必须有一个。

**为什么不成立：**UC03 只登记发出，UC04 确认接收后才创建原料。在“В пути／Затор／Ошибка”状态，物流记录可以没有原料入库记录。

**建议：**每个原料批次恰好来自一次物流操作；一次物流操作对应 **0 或 1** 个原料批次。完成接收后才要求恰好一个。

转关系模型时，可用 `raw_material_batch.chute_log_id NOT NULL UNIQUE` 表示“原料必须有来源、同一操作不能创建两份原料”。但“已送达必须有原料”仍需要接收事务或触发器保证，单个外键不能覆盖整个状态流程。

### 2.3 缺少任务与处置操作，无法完成 UC11、UC12

**位置：**只有 `solid_waste(waste_type, quantity, disposal_method, disposal_time)`，没有独立任务及执行、确认状态。

**为什么不成立：**现有字段不能区分“已分配”“员工已完成、待确认”“管理者已确认”；也无法完整保存负责人、截止时间、完成时间、确认人。单个员工关联无法表达创建人、执行人、确认人三种不同职责。

**建议增加：**

- `task`：任务描述、地点、创建者、执行者、截止时间、状态、员工完成时间、确认者、确认时间、完成说明。
- `disposal_operation`：关联任务／废弃物、实际处理时间、方法、数量、执行者、确认结果。

简单实现可规定“一项任务处理一条废弃物记录”；若一项任务允许处理多种废弃物，再加关联实体。先选定业务规则，再确定是否需要额外关联表。

另外，图中 `solid_waste` 强制属于生产批次，但阶段一还包含衣物、头发等非批次生产来源。应允许关联来访等其他来源，或先明确限定此实体只记录生产废弃物，并为其他废弃物另行建模。

### 2.4 资产只有估值，无法计算实际销售收入

**位置：**`side_asset` 仅有 `estimated_value`、`sale_date`、`duyer_name` 等属性。

**为什么不成立：**估值不等于成交收入。UC13 要选择收购方、多个资产、日期和实际金额；UC14 要按成交收入汇总。当前模型无法可靠表示同一笔交易出售多个资产，也没有实际成交金额。

**建议：**

- `fence`／`buyer`：收购方基础资料及归档状态。
- `asset_sale`：收购方、成交日期、实际总金额、登记员工。
- `side_asset`：保留估值及来源，通过可空的 `asset_sale_id` 关联成交记录。一笔成交关联多件资产，每件资产最多属于一笔已确认成交。

如果只需要整笔交易总金额，上述结构已足够，不必再添加交易明细表；需要每件资产的独立成交价格时才增加明细。保留资产来源的来访关系，可通过来访追溯到客户，不必为同一事实再保存一个容易冲突的客户字段。

### 2.5 来访记录没有服务类型

**位置：**`visit` 只有 `start_time`、`end_time`、`outcome`。

**为什么不成立：**UC02 要选择服务类型并保存服务，UC16 要维护服务类型字典；现有图无法区分理发、剃须或组合服务。

**建议：**增加 `service_type`。若每次来访只选一种服务，可以在 `visit` 中添加服务类型关系并明确此限制；若每次来访能包含多项服务，增加 `barber_service`，记录来访、服务类型、执行者和服务时间。阶段一对象清单已列出 `ServiceType` 与 `BarberService`，采用后者更容易保持文档一致。

### 2.6 员工单个 role 字段与多角色要求不一致

**位置：**`employee.role`。

阶段一明确员工可绑定一个或多个角色，并按角色合并权限。单个普通字段不适合表达此关系。

建议使用 `role` 与 `employee_role(employee_id, role_id)`。关联实体采用复合主键或复合唯一约束，防止重复授予同一角色。不要把多个角色拼成一个字符串。

同时，`password` 应在物理设计中明确为 `password_hash`，保存加盐密码哈希；`login` 应唯一。这里的命名不能证明现在已经存了明文，但需要消除设计歧义。

## 3 已有结构可以保留，但需要补充规则

### 3.1 recipe 带 version 并非天然错误

图中只有 `recipe(name, version, created_at)`。如果每行就是不可变的一版配方，这可以成立；问题在于图中没有说明“同一个配方的多个版本如何归组、哪个版本当前有效、历史组成能否更改”。

建议明确建模：

- `recipe`：配方身份、名称、归档状态。
- `recipe_version`：所属配方、版本号、创建时间、适用原料质量、配方产出基准。
- `recipe_ingredient`：关联具体版本与库存项，保存正数用量和计量依据。
- `production_batch`：关联具体版本，而不是随着版本更新而改变的配方头记录。

`recipe_ingredient` 的唯一组合应为 `(recipe_version_id, stock_item_id)`。同一配方同一版本号应唯一；“每个配方只有一个当前版本”也要有明确实现。

如果为简化继续使用单张 `recipe` 存版本，至少增加稳定的配方分组标识、版本唯一性、当前版本规则，并规定被批次引用的版本及其组成不能原地改写。

### 3.2 销售单与销售行需要明确粒度

现有 `sales_transaction` 有 `quantity`、`total_price`，关联一个生产批次。**这可以表示“每笔记录只卖一种批次”**，不必仅凭缺少销售明细就认定完全错误。

不过，阶段一对象清单列出了 `SaleItem`，UC08 也提到保存销售及其位置。建议选择并写明：

- 推荐方案：`sale` 保存收银员与销售时间；`sale_item` 保存批次、数量和成交单价。一次销售可包含多个批次。
- 简化方案：保留 `sales_transaction`，明确一条销售记录只属于一个批次；对阶段一清单中的销售明细简化，需要统一说明并与教师确认。

`sales_return` 应优先关联原销售行／原单批次销售记录。当前又直接关联批次，会出现“退货说批次 B，原销售却是批次 A”的风险；可以由原销售推导批次，或显式约束二者一致。

还需要保存实际退款金额和必要的经办信息。退款数量累计不得超过已售未退数量；退款是否重新增加可售库存必须明确，不能默认将投诉退回的食品直接上架。

### 3.3 投诉必须允许尚未确定批次

当前图中投诉指向销售和批次的端点都是必须一个，而 UC09 明确“尚未找到批次时，投诉保持开放”。

因此，销售／批次关系应允许在受理阶段未确定，并增加投诉状态及处理时间等信息。阶段一要求最终有可追溯关系，不等于第一次创建投诉就必须知道全部来源。

推荐做法是投诉可以暂时不关联销售行或批次；关联销售行后可以推导批次，若还直接保存批次则必须校验一致性。办结或作出特定处理决定时，再检查对应必填条件。

### 3.4 召回需要自己的业务记录

`production_batch.status` 可以禁止后续销售，但不能独立回答谁在何时因什么原因召回、关联哪次投诉、处理多少未售数量。

UC10 明确要求创建召回记录。建议增加 `batch_recall`，包含批次、发起人、时间、原因及可选投诉关系；同时关联实际成品核销记录。按现有“一批次只召回一次”的流程，可以给批次关联加唯一约束。若允许多次召回事件，则应另行说明规则。

### 3.5 审计字段不足，且必须覆盖失败登录

现有 `audit_log(action_type, target_entity, details)` 缺少明确的事件时间、目标记录标识和执行结果。仅有实体名称无法准确区分同一表中的不同对象。

建议增加：`occurred_at`、`actor_employee_id`、`target_type`、`target_id`、`result`，`details` 用于附加上下文。未知登录名的失败登录没有可关联的有效员工，因此执行员工应允许为空，并单独保存尝试登录名等必要上下文。

审计历史不应随员工删除而级联删除；优先停用员工、保留历史。通用 `target_type + target_id` 不会自动成为对所有业务表都有效的普通外键，应明确这是审计引用，不能声称数据库已经对其建立了跨全部业务表的标准 FK。

### 3.6 库存来源、余量和生产损耗需要一致的口径

现有 `stock_item.current_quantity` 与 `raw_material_batch.remaining_kg` 可以分别表达汇总余量和逐批余量，**同时存在不是错误**，但应明确汇总与明细如何保持一致。

当前建议补充：

- `stock_item.name` 或业务编码。只有单位、阈值和布尔标记，不能清楚区分面粉、脂肪等库存项。
- 原料接收记录、原料批次、库存入库动作之间的来源关系。
- `batch_raw_material` 明确作为“某生产批次用了某原料批次多少千克”的关联实体；实际扣料时与库存日志一致更新。
- `production_waste` 明确计量对象。若表示原料损耗，应关联库存项、单位和对应库存变动；若表示成品报废，应关联成品数量及报废事件。不要让它与 `solid_waste`、库存核销记录重复统计同一份数量。
- `production_batch.actual_quantity` 是实际产出，不等于之后任意时点的可售余额。需要通过销售、召回核销及经确认的退货处理计算余量，或维护受同一事务保护的余额字段。

不必为每一个同质派建立一条 `finished_product` 记录。如果系统只按批次和数量销售，可以不做单件追踪；需要在关系模型和阶段一对象清单之间说明这种映射。

## 4 建议的关键关系基数

表内“每条子记录的父记录数”与“每条父记录的子记录数”分别说明两端，避免只看乌鸦脚方向产生误解。

| 父对象 → 子对象 | 每条子记录的父记录数 | 每条父记录的子记录数 | 说明 |
|---|---:|---:|---|
| client → visit | 1 | 0..N | 来访必须有客户，未知姓名不等于没有客户记录 |
| visit → chute_log | 1 | 0..1 | 普通来访不创建转运；沿用当前一次来访最多一次转运的设计 |
| chute_log → raw_material_batch | 1 | 0..1 | 尚未接收时无原料记录；接收后一个 |
| stock_item → stock_movement | 1 | 0..N | 每条变动必须说明库存项 |
| production_batch → stock_movement | 0..1 | 0..N | 采购等变动没有生产批次 |
| recipe → recipe_version | 1 | 1..N | “已保存的有效配方至少一版”另由创建流程保证；草稿是否允许零版本需说明 |
| recipe_version → recipe_ingredient | 1 | 1..N | 有效版本组成不能为空；普通 FK 本身不保证父对象至少有一条子记录 |
| stock_item → recipe_ingredient | 1 | 0..N | 一个库存项可用于多个配方版本 |
| recipe_version → production_batch | 1 | 0..N | 每个批次固定引用使用的版本 |
| production_batch → batch_raw_material | 1 | 0..N | 草稿／尚未启动阶段可无用料；启动后按规则检查 |
| raw_material_batch → batch_raw_material | 1 | 0..N | 原料批次可分配给多个生产批次 |
| sale → sale_item | 1 | 1..N | 对已确认销售；若采用单批次销售简化则合并此层 |
| production_batch → sale_item | 1 | 0..N | 销售行关联所售批次 |
| sale_item → sales_return | 1 | 0..N | 允许多次部分退款，累计数量受限制 |
| fence → asset_sale | 1 | 0..N | 每笔成交选择一个收购方 |
| asset_sale → side_asset | 0..1 | 1..N | 未售资产没有成交记录；已确认成交包含至少一件资产 |

一对多两端的“0 或至少 1”需要结合生命周期决定。创建草稿、确认交易、完成接收时的规则可以不同，不宜把所有关系统一画成强制存在。

## 5 drawio 文件本身的修复清单

这些是源文件结构问题，不是仅凭截图推测。

1. 修复 10 条至少一端未绑定的线。源文件对应行：**201、316、347、353、363、398、408、418、486、495**。例如第 201 行的 `batch_raw_material` 到生产批次连线没有绑定 source；第 316 行销售到批次的线没有绑定 target。
2. 第 504 行存在 `chlie_log → chlie_log` 的自环；如无明确递归业务含义应删除。
3. 有 12 条线至少一端绑定在属性行，而不是实体框。drawio 允许这样画，这本身不等于数据库建模错误；但当前连接到了 `version`、`status`、`is_active`、`min_threshold` 等属性，且没有标明 FK 它们的身份，容易误解。建议概念图连接实体边框；关系图则连接清楚标注的键。
4. 修正命名：`chlie_log` → `chute_log`；`segmant` → `segment`；`discription` → `description`；`duyer_name` → `buyer_name`。若采用收购方实体，后者应改为相应外键关系。
5. 增加基数符号图例；按访问权限、理发与转运、库存与生产、销售质量、资产与任务分区排列，减少跨全图的长线。

可以在 drawio 中拖动实体检查连接：实体移动后线端应跟随。已绑定到属性的线也会跟随，因此此方法只能发现悬空端点，不能代替语义检查。

`first_visit_date` 可由来访最早时间推导。保留它作为缓存时要规定维护方式；删除它并由查询得出也合理。

## 7 从 ER 模型到关系模型时必须补什么

概念 ER 图的任务是表达实体、属性、联系和基数，未写 PostgreSQL 类型不等于概念模型错误。但第二阶段的关系模型需要明确以下内容：

- 每张表的主键；业务编号、登录名等候选键的唯一性。
- 每条联系对应哪个外键，外键是否可空、是否唯一，以及删除时怎样保留历史。
- 关联实体的键。例如 `(recipe_version_id, stock_item_id)`、`(production_batch_id, raw_material_batch_id)`、`(employee_id, role_id)`；若保留多次同组合的使用事件，则改为独立事件主键并说明粒度。
- 数量、金额与时间类型：数量按单位选整数或精确小数；金额使用精确十进制；时间按报告统一时区策略。
- 正值／非负检查、开始结束时间顺序、合法状态及状态转换。
- 主数据采用停用／归档，避免级联删除已发生的销售、生产和审计记录。

以下两类规则不能混为一谈：

| 规则 | 适合的保证方式 |
|---|---|
| 单条记录的数量 > 0，结束时间不早于开始时间 | CHECK，加必要的 NOT NULL |
| 登录名唯一，接收操作不能生成重复原料 | UNIQUE、外键、必要的部分唯一索引 |
| 引用的员工、库存项、批次必须存在 | FK |
| 累计退款不超过已售未退数量，批次用料不超库存 | 跨行校验、事务化函数／过程、必要触发器和并发控制 |
| 召回与销售并发，重复提交不重复扣库存 | 一致的事务与锁定策略，以及持久化操作标识等去重规则 |

PostgreSQL 的普通 CHECK 不用于跨行／跨表累计校验，也不会代替并发控制；行锁可用于协调冲突操作。参见 [PostgreSQL 约束文档](https://www.postgresql.org/docs/current/ddl-constraints.html) 和 [显式锁文档](https://www.postgresql.org/docs/current/explicit-locking.html)。

本次没有发现此课程项目的 SQL 模型文件；其他实验目录的 SQL 不作为本 ER 图已实现的证据。因此这里评估的是图和业务映射，尚未验证数据库约束与函数的实际行为。

## 8 建议的修改顺序与教师确认要点

1. 修复悬空连线和无意义自环，统一实体名。
2. 改正库存变动、转运接收、待确定投诉等关系的可选性。
3. 补齐任务与处置、服务类型、多角色、资产成交、召回等业务事实。
4. 明确配方版本不可变、销售记录粒度、成品余量计算和退款去向。
5. 在概念 ER 中标识实体身份，导出一张清晰可读的全图，并准备关键关系的文字说明。
6. 与教师确认 ER 后，输出关系模型：表、主键、外键、唯一性、可空性、类型和业务约束；再实现 SQL。

需要明确向教师说明的简化：是否按单批次记录销售、是否省略单件成品表、是否每次来访只有一种服务，以及配方是否单表存版本。只有业务规则和第一阶段文档同步，简化才不会变成漏需求。

**最终建议：保留现有主要实体和两组关联实体，先修正基数与业务记录缺口，再做关系模型；不需要推倒重画，也不应只因实体数已经达标就停止检查。**
