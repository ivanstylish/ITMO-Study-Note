## 第一部分：操作系统与文件系统基础

### 1. 什么是操作系统？主要功能是什么？

**Вопрос:** Что такое операционная система? Каковы её основные функции?

**中文：**

操作系统是管理计算机硬件和软件资源的系统软件。主要功能包括进程管理、内存管理、文件系统管理和设备管理，并通过系统调用为应用程序提供服务。

**Русский：**

Операционная система — это системное программное обеспечение, которое управляет аппаратными и программными ресурсами компьютера. Основные функции — управление процессами, памятью, файловой системой и устройствами, а также предоставление системных вызовов.

### 2. 什么是文件系统？

**Вопрос:** Что такое файловая система?

**中文：**

文件系统是操作系统用于组织、存储和管理文件及目录的机制。它提供文件命名、路径查找、数据读写和访问权限管理等功能。

**Русский：**

Файловая система — это механизм организации, хранения и управления файлами и каталогами. Она обеспечивает поиск файлов по путям, чтение, запись и управление правами доступа.

### 3. 文件与目录有什么区别？

**Вопрос:** Чем файл отличается от каталога?

**中文：**

普通文件用于保存数据，目录用于组织文件和子目录。目录维护文件名与文件对象之间的映射关系。

**Русский：**

Обычный файл хранит данные, а каталог организует файлы и подкаталоги. Каталог содержит отображение имён файлов на соответствующие файловые объекты.

### 4. 什么是绝对路径和相对路径？

**Вопрос:** Чем абсолютный путь отличается от относительного?

**中文：**

绝对路径从根目录开始，例如 `/home/user/music.wav`。相对路径相对于当前目录或指定的基准目录，例如 `drums/music.wav`。

**Русский：**

Абсолютный путь начинается от корневого каталога, например `/home/user/music.wav`. Относительный путь задаётся относительно текущего или указанного каталога, например `drums/music.wav`.

### 5. 什么是 inode？

**Вопрос:** Что такое inode (индексный дескриптор)?

**中文：**

inode 是 Unix/Linux 文件系统中标识文件对象并关联其元数据的数据结构。它与文件权限、大小等属性相关，文件名通常保存在目录项中。

**Русский：**

Inode — это структура данных файловой системы Unix/Linux, которая идентифицирует файловый объект и связана с его метаданными, например размером и правами доступа. Имя файла обычно хранится в записи каталога.

### 6. 硬链接和符号链接有什么区别？

**Вопрос:** Чем жёсткая ссылка отличается от символической?

**中文：**

硬链接是另一个指向相同 inode 的目录项，通常不能跨文件系统。符号链接是保存目标路径的特殊文件，可以指向其他文件系统中的文件。

**Русский：**

Жёсткая ссылка — это ещё одна запись каталога, указывающая на тот же inode. Она не может пересекать границы файловых систем. Символическая ссылка — это специальный файл, содержащий путь к целевому объекту.

### 7. 什么是文件描述符？

**Вопрос:** Что такое файловый дескриптор?

**中文：**

文件描述符（fd）是进程用来访问已打开文件或其他 I/O 对象的非负整数。`open()` 可以获得描述符，`read()` 使用描述符读取数据，`close()` 关闭描述符。

**Русский：**

Файловый дескриптор (fd) — это неотрицательное целое число, с помощью которого процесс обращается к открытому файлу или другому объекту ввода-вывода. `open()` открывает файл, `read()` читает данные, а `close()` закрывает дескриптор.

### 8. Linux 文件权限 0444 和 0555 表示什么？

**Вопрос:** Что означают права доступа 0444 и 0555?

**中文：**

`0444` 表示所有者、组和其他用户只有读权限。`0555` 表示所有者、组和其他用户都有读和执行权限。对于目录，执行权限允许路径搜索和进入目录。

**Русский：**

`0444` означает право только на чтение для владельца, группы и остальных пользователей. `0555` означает права на чтение и выполнение. Для каталога право выполнения позволяет проходить через каталог и искать в нём файлы.

### 9. 什么是挂载和卸载？

**Вопрос:** Что такое монтирование и размонтирование файловой системы?

**中文：**

挂载是将文件系统连接到目录树中的指定位置，使用户能够通过挂载点访问它。卸载则是解除这种连接。

**Русский：**

Монтирование — это подключение файловой системы к определённой точке дерева каталогов. Размонтирование — это отключение файловой системы от этой точки.

### 10. 什么是系统调用？

**Вопрос:** Что такое системный вызов?

**中文：**

系统调用是用户程序请求操作系统内核提供服务的受控接口。例如读取文件、创建进程和分配某些系统资源。

**Русский：**

Системный вызов — это интерфейс, через который пользовательская программа обращается к ядру операционной системы за услугами, например для чтения файла или создания процесса.

## 第二部分：FUSE 与内核原理

### 11. 什么是 FUSE？为什么使用它？

**Вопрос:** Что такое FUSE и зачем он нужен?

**中文：**

FUSE 是用户空间文件系统机制，允许开发者在用户空间实现文件系统逻辑，而不需要编写内核模块。这降低了开发和调试的复杂度。

**Русский：**

FUSE — это механизм реализации файловых систем в пространстве пользователя. Он позволяет создавать файловые системы без разработки модулей ядра, что упрощает разработку и отладку.

### 12. 用户态和内核态有什么区别？

**Вопрос:** Чем пользовательский режим отличается от режима ядра?

**中文：**

用户态和内核态是不同的 CPU 权限模式。用户态权限受限，内核态能够执行特权操作。用户程序通过系统调用请求内核服务。

**Русский：**

Пользовательский режим и режим ядра отличаются уровнем привилегий процессора. В пользовательском режиме права ограничены, а режим ядра позволяет выполнять привилегированные операции. Программы обращаются к ядру через системные вызовы.

### 13. FUSE 和传统内核文件系统有什么区别？

**Вопрос:** Чем FUSE отличается от файловой системы, реализованной в ядре?

**中文：**

FUSE 的主要文件系统逻辑运行在用户空间，开发更方便，但通常存在额外的内核与用户空间通信开销。内核文件系统直接在内核中处理核心操作。

**Русский：**

В FUSE основная логика файловой системы работает в пространстве пользователя. Это упрощает разработку, но добавляет расходы на взаимодействие с ядром. Файловые системы ядра выполняют основную логику непосредственно в ядре.

### 14. 什么是 VFS？

**Вопрос:** Что такое VFS (Virtual File System)?

**中文：**

VFS 是 Linux 的虚拟文件系统层，为不同文件系统提供统一接口。应用程序可以通过相同的系统调用访问 ext4、tmpfs 和 FUSE 等文件系统。

**Русский：**

VFS — это виртуальный уровень файловой системы Linux, который предоставляет единый интерфейс для разных файловых систем, например ext4, tmpfs и FUSE.

### 15. 执行 cat 时，MusicFS 如何处理请求？

**Вопрос:** Как MusicFS обрабатывает команду `cat`?

**中文：**

`cat` 发起文件操作，Linux 通过 VFS 和 FUSE 将相关请求传递给 MusicFS。MusicFS 查找 inode、打开源文件、读取字节，并通过 FUSE 返回数据。

**Русский：**

Команда `cat` выполняет файловые операции. Linux через VFS и FUSE передаёт соответствующие запросы в MusicFS. MusicFS находит inode, открывает исходный файл, читает байты и возвращает данные через FUSE.

### 16. pyfuse3 和 libfuse3 的作用是什么？

**Вопрос:** Для чего используются pyfuse3 и libfuse3?

**中文：**

libfuse3 提供用户空间 FUSE 库，pyfuse3 提供 Python 绑定，使开发者能够使用 Python 实现 FUSE 回调。

**Русский：**

libfuse3 предоставляет библиотеку для работы с FUSE в пространстве пользователя. pyfuse3 предоставляет Python-интерфейс для реализации обработчиков файловых операций.

### 17. lookup() 和 readdir() 有什么区别？

**Вопрос:** Чем отличаются `lookup()` и `readdir()`?

**中文：**

`lookup()` 根据父目录 inode 和文件名查找指定节点。`readdir()` 遍历目录并返回目录项。

**Русский：**

`lookup()` ищет конкретный узел по inode родительского каталога и имени файла. `readdir()` перечисляет записи каталога.

### 18. getattr() 的作用是什么？

**Вопрос:** Для чего нужен метод `getattr()`?

**中文：**

`getattr()` 返回文件属性，包括类型、权限、大小、inode、链接数和时间戳。

**Русский：**

Метод `getattr()` возвращает атрибуты файла: тип, права доступа, размер, inode, количество ссылок и временные метки.

### 19. open()、read() 和 release() 的关系是什么？

**Вопрос:** Как связаны методы `open()`, `read()` и `release()`?

**中文：**

`open()` 打开文件并返回 FUSE 文件句柄，`read()` 使用句柄读取数据，`release()` 释放句柄及相关资源。

**Русский：**

`open()` открывает файл и возвращает файловый идентификатор FUSE, `read()` читает данные через него, а `release()` освобождает связанные ресурсы.

### 20. 什么是 errno？常见错误码有哪些？

**Вопрос:** Что такое errno? Какие коды ошибок вы знаете?

**中文：**

errno 用于表示操作系统错误类型。

**Русский：**

errno используется для обозначения типа ошибки операционной системы.

| 错误码 | 中文 | Русский |
|---|---|---|
| ENOENT | 文件或目录不存在 | Файл или каталог не существует |
| EACCES | 访问被拒绝 | Отказ в доступе |
| EROFS | 只读文件系统 | Файловая система только для чтения |
| EBADF | 无效文件描述符 | Недопустимый файловый дескриптор |
| ENOTDIR | 不是目录 | Не является каталогом |
| EISDIR | 目标是目录 | Объект является каталогом |
| EINVAL | 无效参数 | Недопустимый аргумент |

## 第三部分：MusicFS 项目与代码实现

### 21. 你的 MusicFS 实现了什么功能？

**Вопрос:** Что реализует ваша файловая система MusicFS?

**中文：**

我实现了一个基于 FUSE 的只读虚拟音乐文件系统。它根据 JSON 元数据，按 BPM、调性和素材类型组织音频文件，并提供虚拟 `.info` 文件查看元数据。

**Русский：**

Я реализовал виртуальную музыкальную файловую систему MusicFS на основе FUSE в режиме только для чтения. Она организует аудиофайлы по BPM, тональности и типу на основе JSON-метаданных, а также предоставляет виртуальные файлы `.info`.

### 22. 为什么把代码分成三个模块？

**Вопрос:** Почему программа разделена на три основных модуля?

**中文：**

- `catalog.py`：解析 JSON 和建立目录索引。
- `fs.py`：处理 FUSE 请求。
- `__main__.py`：负责程序启动、挂载和资源清理。

**Русский：**

- `catalog.py` отвечает за обработку JSON и построение индекса каталогов.
- `fs.py` обрабатывает запросы FUSE.
- `__main__.py` отвечает за запуск, монтирование и освобождение ресурсов.

### 23. Catalog 如何建立虚拟目录？

**Вопрос:** Как Catalog создаёт виртуальную структуру каталогов?

**中文：**

Catalog 读取并验证 JSON，为每个音频创建一个 Node，然后在三个分类目录中建立文件名到相同 inode 的映射。

**Русский：**

Catalog читает и проверяет JSON, создаёт один узел Node для каждого аудиофайла и добавляет записи с одним и тем же inode в три категории.

### 24. Node 类的主要字段是什么？

**Вопрос:** Какие основные поля содержит класс Node?

**中文：**

| 字段 | 作用 |
|---|---|
| inode | 虚拟节点编号 |
| parent | 父目录 inode |
| name | 节点名称 |
| children | 文件名到 inode 的映射 |
| path | 真实音频文件路径 |
| content | 内存生成文件的内容 |
| links | 虚拟链接数量 |

**Русский：**

| Поле | Назначение |
|---|---|
| inode | Номер виртуального узла |
| parent | Inode родительского каталога |
| name | Имя узла |
| children | Отображение имён на inode |
| path | Путь к исходному аудиофайлу |
| content | Содержимое файла в памяти |
| links | Количество виртуальных ссылок |

### 25. 为什么一个音频能出现在三个目录中？

**Вопрос:** Почему один аудиофайл доступен через три каталога?

**中文：**

因为 Catalog 只创建一个音频 Node，三个分类目录分别保存指向同一个 inode 的目录项，不需要复制音频数据。

**Русский：**

Потому что Catalog создаёт только один узел для аудиофайла, а три каталога содержат записи, указывающие на один и тот же inode. Копирование аудиоданных не требуется.

### 26. 为什么 BPM=125 被归类到 130？

**Вопрос:** Почему BPM 125 округляется до 130?

**中文：**

因为实验采用最接近的 10 的倍数进行分类，中点向上舍入。代码使用 `Decimal` 和 `ROUND_HALF_UP` 避免 Python `round()` 的中点取偶规则。

**Русский：**

Потому что BPM округляется до ближайшего числа, кратного десяти, с округлением середины вверх. Используются `Decimal` и `ROUND_HALF_UP`, чтобы избежать банковского округления функции `round()`.

### 27. 为什么需要验证 JSON 中的路径？

**Вопрос:** Зачем проверять пути в JSON?

**中文：**

为了防止绝对路径、`..` 和符号链接导致访问超出源目录，同时检查文件是否存在、是否为普通文件，以及是否重复。

**Русский：**

Проверка нужна для предотвращения выхода за пределы исходного каталога через абсолютные пути, `..` или символические ссылки. Также проверяются существование файла, его тип и отсутствие дубликатов.

### 28. .info 文件是怎样实现的？

**Вопрос:** Как реализованы виртуальные файлы `.info`?

**中文：**

Catalog 在内存中生成 UTF-8 文本，并保存在 Node 的 `content` 字段中。读取时直接返回字节切片，不创建真实磁盘文件。

**Русский：**

Catalog создаёт текст в кодировке UTF-8 и сохраняет его в поле `content` объекта Node. При чтении возвращается срез байтов из памяти, без создания физического файла.

### 29. 为什么不需要复制原始音频？

**Вопрос:** Почему не нужно копировать исходные аудиофайлы?

**中文：**

因为 MusicFS 只建立虚拟目录项和 inode 映射。读取时通过原始路径打开真实音频，因此三个入口共享同一份源数据。

**Русский：**

MusicFS создаёт только виртуальные записи каталогов и отображения inode. При чтении открывается исходный аудиофайл, поэтому все три пути используют одни и те же данные.

### 30. MusicFS 从启动到挂载的流程是什么？

**Вопрос:** Как происходит запуск и монтирование MusicFS?

**中文：**

`main()` 解析参数，Catalog 加载 JSON 并建立索引，然后创建 MusicFS 对象。`pyfuse3.init()` 初始化挂载，`trio.run(serve)` 启动请求循环。

**Русский：**

`main()` обрабатывает аргументы, Catalog загружает JSON и создаёт индекс. Затем создаётся объект MusicFS, `pyfuse3.init()` инициализирует монтирование, а `trio.run(serve)` запускает цикл обработки запросов.

## 第四部分：系统调用、文件读取与异步 IO

### 31. os.open() 与 Python 的 open() 有什么区别？

**Вопрос:** Чем `os.open()` отличается от встроенной функции `open()`?

**中文：**

`os.open()` 提供较底层的文件打开接口，返回整数文件描述符。Python 的 `open()` 返回文件对象，提供缓冲和更高级的读写接口。

**Русский：**

`os.open()` предоставляет низкоуровневый интерфейс и возвращает целочисленный файловый дескриптор. Встроенная функция `open()` возвращает файловый объект с более высокоуровневыми операциями и буферизацией.

### 32. 为什么使用 pread() 而不是 read()？

**Вопрос:** Почему используется `pread()`, а не `read()`?

**中文：**

`pread()` 可以从指定偏移读取数据，而不改变打开文件描述的当前偏移位置，适合随机访问和并发读取。

**Русский：**

`pread()` читает данные по заданному смещению, не изменяя текущую позицию открытого файлового описания. Это удобно для произвольного и параллельного чтения.

### 33. read() 中的 offset 和 size 是什么？

**Вопрос:** Что означают параметры offset и size в `read()`?

**中文：**

offset 是读取的起始字节偏移，size 是请求读取的最大字节数。例如 offset=100、size=50 表示从第 100 字节偏移开始最多读取 50 字节。

**Русский：**

offset — это начальное смещение чтения в байтах, а size — максимальное количество запрашиваемых байтов. Например, offset=100 и size=50 означают чтение до 50 байтов начиная со смещения 100.

### 34. 什么是 EOF？

**Вопрос:** Что такое EOF?

**中文：**

EOF（End of File）表示文件末尾。如果从文件末尾继续读取，通常返回空字节。如果请求跨越文件末尾，可能返回少于请求数量的字节。

**Русский：**

EOF означает конец файла. При чтении с позиции конца файла обычно возвращается пустой набор байтов. Если запрос выходит за конец файла, может вернуться меньше байтов, чем запрошено.

### 35. 为什么一个 inode 可以对应多个 fd？

**Вопрос:** Почему одному inode могут соответствовать несколько файловых дескрипторов?

**中文：**

inode 标识文件对象，而 fd 标识进程中的打开句柄。同一个文件可以被多次打开，每次打开可以产生不同的 fd。

**Русский：**

Inode идентифицирует файловый объект, а fd — открытый дескриптор в процессе. Один файл можно открыть несколько раз, получив разные файловые дескрипторы.

### 36. stat() 与 fstat() 有什么区别？

**Вопрос:** Чем отличаются `stat()` и `fstat()`?

**中文：**

`stat()` 根据文件路径获取属性，`fstat()` 根据已打开的文件描述符获取属性。即使文件路径被删除，已有 fd 在有效时仍可用于 `fstat()`。

**Русский：**

`stat()` получает атрибуты файла по пути, а `fstat()` — по открытому файловому дескриптору. Даже после удаления имени файла действующий дескриптор может использоваться для `fstat()`.

### 37. 为什么使用 Trio 工作线程？

**Вопрос:** Зачем используется рабочий поток Trio?

**中文：**

因为 `os.pread()` 是同步调用，可能阻塞线程。`trio.to_thread.run_sync()` 将读取操作交给工作线程，避免长时间阻塞 Trio 事件循环。

**Русский：**

`os.pread()` — синхронная операция, которая может блокировать поток. `trio.to_thread.run_sync()` выполняет чтение в рабочем потоке, чтобы не блокировать цикл событий Trio.

### 38. 什么是阻塞 IO 和异步 IO？

**Вопрос:** Что такое блокирующий и асинхронный ввод-вывод?

**中文：**

阻塞 I/O 会使调用线程等待操作完成。异步 I/O 允许程序在等待期间处理其他任务。MusicFS 使用 Trio 将阻塞读取转移到工作线程。

**Русский：**

При блокирующем вводе-выводе вызывающий поток ожидает завершения операции. Асинхронный подход позволяет выполнять другие задачи во время ожидания. MusicFS переносит блокирующее чтение в рабочий поток Trio.

### 39. 为什么需要 release() 和 close()？

**Вопрос:** Зачем нужны методы `release()` и `close()`?

**中文：**

`release()` 在 FUSE 文件句柄释放时关闭对应资源，`close()` 在文件系统退出时清理仍然打开的文件描述符，防止资源泄漏。

**Русский：**

`release()` освобождает ресурсы при освобождении файлового идентификатора FUSE. `close()` закрывает оставшиеся открытые дескрипторы при завершении файловой системы, предотвращая утечки ресурсов.

### 40. 为什么 forget() 没有实现节点回收？

**Вопрос:** Почему `forget()` не освобождает узлы?

**中文：**

因为 MusicFS 的 inode 索引在挂载期间保持固定，所有节点保留到卸载，所以不需要根据内核的 forget 通知回收节点。

**Русский：**

Потому что индекс inode в MusicFS остаётся неизменным во время монтирования. Все узлы сохраняются до размонтирования, поэтому освобождать их при уведомлении `forget()` не требуется.

## 第五部分：安全、测试与实验报告

### 41. 为什么使用只读挂载 ro？

**Вопрос:** Зачем используется режим монтирования `ro`?

**中文：**

为了禁止通过 MusicFS 修改文件。程序还通过只读权限和 `open()` 中的写入检查实现分层保护。

**Русский：**

Режим `ro` запрещает изменение файлов через MusicFS. Дополнительно используются права только на чтение и проверка режима открытия в методе `open()`.

### 42. O_RDONLY、O_NOFOLLOW 和 O_NONBLOCK 有什么区别？

**Вопрос:** Чем отличаются `O_RDONLY`, `O_NOFOLLOW` и `O_NONBLOCK`?

**中文：**

- `O_RDONLY`：只读打开。
- `O_NOFOLLOW`：禁止跟随最终路径组件的符号链接。
- `O_NONBLOCK`：请求非阻塞模式，但对普通磁盘文件通常没有非阻塞读取效果。

**Русский：**

- `O_RDONLY` открывает файл только для чтения.
- `O_NOFOLLOW` запрещает переход по символической ссылке в последнем компоненте пути.
- `O_NONBLOCK` запрашивает неблокирующий режим, но обычно не влияет на чтение обычных файлов.

### 43. 为什么必须防止路径逃出 source_root？

**Вопрос:** Почему необходимо предотвращать выход пути за пределы source_root?

**中文：**

为了防止 JSON 中的路径访问未经授权的源目录外文件。程序解析真实路径并检查其是否仍位于指定源目录中。

**Русский：**

Это необходимо для предотвращения доступа к файлам за пределами разрешённого исходного каталога. Программа разрешает путь и проверяет, находится ли он внутри source_root.

### 44. 为什么检查 st_dev 和 st_ino？

**Вопрос:** Зачем проверяются `st_dev` и `st_ino`?

**中文：**

因为不同路径可能通过硬链接或符号链接指向同一个物理文件。`st_dev` 和 `st_ino` 组合可以识别同一文件系统中的同一文件对象。

**Русский：**

Разные пути могут ссылаться на один физический файл через жёсткие или символические ссылки. Пара `st_dev` и `st_ino` позволяет определить один и тот же файловый объект в файловой системе.

### 45. 如何证明三个目录入口没有复制音频？

**Вопрос:** Как доказать, что три пути не создают копии аудиофайла?

**中文：**

可以检查三个虚拟路径的 inode 是否相同、链接数是否为 3，并验证读取内容的哈希与源文件一致。同时确认程序没有创建额外音频副本。

**Русский：**

Можно проверить, что три виртуальных пути имеют одинаковый inode и количество ссылок равно трём. Также сравниваются хеши прочитанных данных с исходным файлом и проверяется отсутствие дополнительных копий.

### 46. 为什么使用 SHA-256？

**Вопрос:** Зачем используется SHA-256?

**中文：**

SHA-256 用于验证通过虚拟文件系统读取的数据与原始文件是否一致。相同哈希为数据一致性提供很强的证据。

**Русский：**

SHA-256 используется для проверки совпадения данных, прочитанных через виртуальную файловую систему, с исходным файлом. Совпадение хешей является сильным свидетельством целостности данных.

### 47. 为什么要测试文件中间、末尾和 EOF？

**Вопрос:** Почему проверяется чтение в середине, в конце файла и после EOF?

**中文：**

为了验证随机读取、偏移处理、短读取和文件结束行为是否正确，避免只测试文件开头而遗漏边界问题。

**Русский：**

Эти тесты проверяют произвольное чтение, обработку смещений, короткое чтение и поведение в конце файла. Это позволяет обнаружить ошибки на границах данных.

### 48. 为什么修改 JSON 后需要重新挂载？

**Вопрос:** Почему после изменения JSON требуется повторное монтирование?

**中文：**

因为 Catalog 只在启动时读取 JSON 并建立固定索引，程序没有实现元数据热更新。

**Русский：**

Потому что Catalog загружает JSON и строит фиксированный индекс только при запуске. Горячее обновление метаданных не реализовано.

### 49. MusicFS 有哪些局限性？

**Вопрос:** Какие ограничения есть у MusicFS?

**中文：**

MusicFS 只支持读取，不支持修改音频或元数据，也不支持热更新。它不负责音频解码、播放和自动分析 BPM，源文件在挂载期间变化时也不保证快照一致性。

**Русский：**

MusicFS поддерживает только чтение, без изменения аудио и метаданных или горячего обновления. Она не выполняет декодирование, воспроизведение и автоматическое определение BPM. При изменении исходных файлов согласованность снимка не гарантируется.

### 50. 学校允许使用 LLM 吗？需要说明什么？

**Вопрос:** Разрешено ли использовать LLM? Что необходимо указать в отчёте?

**中文：**

学校允许使用 LLM 辅助实现，并要求在报告中说明使用方法。如果生成与外部服务交互的代码，应将其放在独立隔离的模块中。实验结果仍需要实际测试验证。

**Русский：**

Использование LLM допускается. В отчёте необходимо описать методику работы с LLM. Сгенерированный код взаимодействия с внешним сервисом должен быть выделен в отдельный изолированный модуль. Результаты необходимо проверять тестированием.

## 第六部分：高级操作系统问题

### 51. 为什么文件被删除后，已有 fd 可能仍然有效？

**Вопрос:** Почему открытый файловый дескриптор может оставаться действительным после удаления файла?

**中文：**

在 Linux 中，删除文件名通常只是删除目录项。如果文件仍被打开，内核会保留相应文件对象，直到相关引用释放，因此已有 fd 仍可能读取数据。

**Русский：**

В Linux удаление имени файла обычно удаляет запись каталога. Если файл остаётся открытым, ядро сохраняет соответствующий файловый объект до освобождения ссылок, поэтому чтение через открытый fd может продолжаться.

### 52. 两个进程同时读取同一个文件会发生什么？

**Вопрос:** Что произойдёт, если два процесса одновременно читают один файл?

**中文：**

两个进程可以同时读取同一个文件。MusicFS 每次打开源文件可以获得独立 fd，并使用 `pread()` 按指定偏移读取，避免依赖共享文件位置。

**Русский：**

Два процесса могут одновременно читать один файл. MusicFS может открывать отдельные fd и использует `pread()` для чтения по заданному смещению, не завися от общей текущей позиции файла.

### 53. 如果 MusicFS 进程崩溃，会发生什么？

**Вопрос:** Что произойдёт, если процесс MusicFS аварийно завершится?

**中文：**

FUSE 用户空间服务停止后，挂载点可能仍然存在，但文件操作可能返回错误，例如 `Transport endpoint is not connected`。此时可能需要手动卸载。

**Русский：**

После аварийного завершения пользовательского процесса FUSE точка монтирования может остаться, но файловые операции могут возвращать ошибки, например `Transport endpoint is not connected`. Может потребоваться ручное размонтирование.

### 54. 禁用 writeback cache 是否等于禁用所有缓存？

**Вопрос:** Означает ли отключение writeback cache отключение всех видов кэширования?

**中文：**

不是。writeback cache 主要涉及写入缓存机制。Linux 仍可能使用页缓存、目录项缓存等。MusicFS 将属性缓存超时设置为 0，但不代表完全禁用所有缓存。

**Русский：**

Нет. Writeback cache относится прежде всего к механизму кэширования записи. Linux всё ещё может использовать страничный кэш и кэш записей каталогов. Нулевой тайм-аут атрибутов не отключает все виды кэширования.

### 55. 为什么目录句柄可以直接使用 inode，而音频需要 fd？

**Вопрос:** Почему для каталога используется inode, а для аудиофайла нужен fd?

**中文：**

因为 MusicFS 的虚拟目录完全保存在内存索引中，不需要打开真实目录。而音频数据位于真实文件中，需要通过 fd 读取。

**Русский：**

Виртуальные каталоги MusicFS полностью представлены индексом в памяти, поэтому открывать физический каталог не требуется. Аудиоданные находятся в реальных файлах, для чтения которых нужен fd.

### 56. 为什么硬链接不能跨文件系统？MusicFS 的三个入口是什么？

**Вопрос:** Почему жёсткие ссылки не могут пересекать файловые системы? Что представляют собой три пути в MusicFS?

**中文：**

硬链接引用同一文件系统内的 inode，而不同文件系统有独立的 inode 编号空间。MusicFS 的三个入口是同一个 FUSE 文件系统中的虚拟目录项，共同引用一个虚拟 inode，并不是在源文件系统创建真实硬链接。

**Русский：**

Жёсткая ссылка ссылается на inode внутри одной файловой системы, а разные файловые системы имеют независимые пространства inode. Три пути MusicFS — это виртуальные записи каталогов одной FUSE-системы, указывающие на общий виртуальный inode, а не физические жёсткие ссылки в исходной системе.

### 57. MusicFS 是否完全避免了 TOCTOU 问题？

**Вопрос:** Полностью ли MusicFS защищена от проблемы TOCTOU?

**中文：**

没有。TOCTOU 是检查与使用之间的竞态条件。MusicFS 虽然检查了真实路径，并使用 `O_NOFOLLOW`，但如果源目录结构在检查后被并发修改，仍可能存在风险。

**Русский：**

Нет. TOCTOU — это состояние гонки между проверкой и использованием ресурса. MusicFS проверяет путь и использует `O_NOFOLLOW`, но при одновременном изменении структуры исходных каталогов риски остаются.

### 58. 如果要支持元数据热更新，需要修改什么？

**Вопрос:** Что необходимо изменить для поддержки горячего обновления метаданных?

**中文：**

需要重新加载 JSON、更新目录项与 inode 映射，并处理并发访问、节点生命周期和内核缓存失效，保证更新过程中数据结构一致。

**Русский：**

Необходимо реализовать повторную загрузку JSON, обновление записей каталогов и отображений inode, а также синхронизацию параллельных запросов, управление временем жизни узлов и сброс кэша ядра.

### 59. 如果有一百万个音频，MusicFS 可能遇到什么性能问题？

**Вопрос:** Какие проблемы производительности возникнут при миллионе аудиофайлов?

**中文：**

当前实现一次性加载所有 JSON 记录和虚拟节点，可能占用大量内存。目录遍历、属性查询和启动索引构建也可能成为性能瓶颈。可以考虑数据库索引、延迟加载和缓存优化。

**Русский：**

Текущая реализация загружает все записи JSON и виртуальные узлы в память, что может потребовать много памяти. Построение индекса, обход каталогов и запросы атрибутов также могут стать узкими местами. Возможные улучшения — база данных, ленивая загрузка и оптимизация кэширования.

### 60. 为什么 MusicFS 是文件系统，而不只是文件分类脚本？

**Вопрос:** Почему MusicFS является файловой системой, а не просто скриптом сортировки файлов?

**中文：**

因为 MusicFS 通过 FUSE 挂载到 Linux 目录树，实现了 `lookup`、`getattr`、`readdir`、`open`、`read` 等文件系统操作。普通程序可以通过标准文件接口访问它，而不需要使用专门的分类脚本。

**Русский：**

MusicFS является файловой системой, потому что она монтируется в дерево каталогов Linux через FUSE и реализует файловые операции `lookup`, `getattr`, `readdir`, `open` и `read`. Обычные программы могут обращаться к ней через стандартный файловый интерфейс.

## 补充问题：内核与系统调用

### 61. 操作系统内核与操作系统有什么区别？

**Вопрос:** Чем отличается ядро операционной системы от самой операционной системы?

**中文：**

内核是操作系统的核心部分，通常运行在特权模式下，负责进程调度、内存管理、设备管理和系统调用处理。

操作系统则包含内核、系统服务和系统工具，为应用程序提供运行环境。

**Русский：**

Ядро — это центральная часть операционной системы, которая обычно работает в привилегированном режиме и отвечает за управление процессами, памятью, устройствами и обработку системных вызовов.

Операционная система включает ядро, системные службы и утилиты, обеспечивая среду для работы приложений.

### 62. 为什么用户程序不能直接执行特权操作？

**Вопрос:** Почему пользовательская программа не может напрямую выполнять привилегированные операции?

**中文：**

CPU 和内存管理硬件限制用户态程序的权限，防止普通程序任意修改内核数据、访问受保护的内存或控制硬件设备。这种隔离保证系统的安全性和稳定性。

**Русский：**

Процессор и механизмы управления памятью ограничивают права пользовательских программ, предотвращая произвольное изменение данных ядра, доступ к защищённой памяти и управление оборудованием. Это обеспечивает безопасность и стабильность системы.

### 63. 用户态与用户空间有什么区别？

**Вопрос:** Чем пользовательский режим отличается от пространства пользователя?

**中文：**

用户态是 CPU 的一种执行权限模式。用户空间是进程虚拟地址空间中供用户程序使用的部分。前者描述执行权限，后者描述地址空间。

**Русский：**

Пользовательский режим — это режим выполнения процессора с ограниченными привилегиями. Пространство пользователя — это часть виртуального адресного пространства, доступная пользовательским программам. Первое понятие относится к привилегиям, второе — к адресному пространству.

### 64. 系统调用与普通函数调用有什么区别？

**Вопрос:** Чем системный вызов отличается от обычного вызова функции?

**中文：**

普通函数调用通常在当前权限模式下执行，不需要进入内核态。系统调用是用户程序请求内核服务的接口，通常涉及从用户态进入内核态，并在处理完成后返回用户态。

**Русский：**

Обычный вызов функции обычно выполняется в текущем режиме процессора без перехода в режим ядра. Системный вызов позволяет пользовательской программе обратиться к ядру и обычно сопровождается переходом в режим ядра с последующим возвращением в пользовательский режим.

### 65. 用户态与内核态切换是否等于进程切换？

**Вопрос:** Является ли переключение между пользовательским режимом и режимом ядра переключением процессов?

**中文：**

不是。权限模式切换改变 CPU 的执行权限，而进程上下文切换改变当前执行的进程或线程。系统调用可以发生权限模式切换，但不一定发生进程切换。

**Русский：**

Нет. Переключение режима изменяет уровень привилегий процессора, а переключение контекста изменяет выполняемый процесс или поток. Системный вызов может сопровождаться сменой режима без переключения процесса.

### 一、基础问题（Простые вопросы）

### 66. 什么是 FUSE？

**Вопрос:** Что такое FUSE?

**中文：**

FUSE（Filesystem in Userspace）是一种允许开发者在用户空间实现文件系统的机制，无须直接开发内核模块。

**Русский：**

FUSE — это механизм, позволяющий реализовывать файловые системы в пространстве пользователя без разработки модулей ядра.

### 67. 什么是文件系统挂载？

**Вопрос:** Что такое монтирование файловой системы?

**中文：**

挂载是将文件系统连接到现有目录树中的指定目录，使用户能够通过挂载点访问该文件系统中的内容。

**Русский：**

Монтирование — это подключение файловой системы к определённой точке дерева каталогов для доступа к её содержимому.

### 68. read 操作有什么作用？

**Вопрос:** Для чего используется операция read?

**中文：**

read 用于读取文件数据。在 FUSE 中，read 根据文件句柄、偏移量和请求大小返回相应的字节数据。

**Русский：**

Операция read используется для чтения данных файла. В FUSE она возвращает данные по файловому идентификатору, заданному смещению и размеру.

### 69. 什么是 Python bindings？

**Вопрос:** Что такое Python bindings?

**中文：**

Python bindings 是允许 Python 调用其他编程语言编写的库的接口。例如，pyfuse3 使 Python 程序能够使用 C 语言实现的 libfuse3 库。

**Русский：**

Python bindings — это интерфейсы, позволяющие использовать из Python библиотеки, написанные на других языках программирования. Например, pyfuse3 позволяет работать с библиотекой libfuse3 из Python.

### 70. 什么是程序模块？

**Вопрос:** Что такое программный модуль?

**中文：**

程序模块是具有相对独立功能和明确接口的程序组成部分。在 Python 中，一个 `.py` 文件通常可以作为一个模块。

**Русский：**

Программный модуль — это относительно самостоятельная часть программы, выполняющая определённую функцию и имеющая определённый интерфейс. В Python отдельный файл `.py` обычно является модулем.

### 二、理解性问题（Вопросы на понимание）

### 71. 为什么在用户空间开发文件系统比开发内核模块更简单？

**Вопрос:** Почему разработка файловой системы в userspace проще, чем разработка модуля ядра?

**中文：**

用户空间可以使用普通编程语言、标准库和调试工具，不需要直接处理复杂的内核机制。

用户空间程序出现错误时，通常只会影响该进程及其服务，而不会直接导致整个内核崩溃。

**Русский：**

В пространстве пользователя можно использовать обычные языки программирования, стандартные библиотеки и инструменты отладки.

Не нужно напрямую работать со сложными механизмами ядра. Ошибка обычно приводит к сбою отдельного процесса, а не всего ядра.

### 72. read 操作如何与外部服务请求关联？

**Вопрос:** Как операция read может быть связана с запросом к внешнему сервису?

**中文：**

当用户读取虚拟文件时，FUSE 可以向外部服务发送 API 请求，获取数据并转换为字节内容，然后根据偏移量和大小返回相应的数据。

**Русский：**

При чтении виртуального файла FUSE может отправить запрос к API внешнего сервиса, получить данные, преобразовать их в байты и вернуть нужную часть с учётом смещения и размера.

**结合 MusicFS / Применительно к MusicFS：**

我的实验没有使用远程 API，而是通过 `os.pread()` 读取本地真实音频文件。

В моей работе удалённый API не используется. MusicFS читает локальные аудиофайлы с помощью `os.pread()`.

### 73. 为什么目录结构应该符合外部服务的逻辑？

**Вопрос:** Почему структура каталогов должна соответствовать логике внешнего сервиса?

**中文：**

因为目录结构是外部服务数据模型的文件系统表示。合理的映射使用户能够通过标准文件操作直观地查找和访问服务中的对象。

**Русский：**

Структура каталогов представляет модель данных внешнего сервиса в виде файловой системы. Такое соответствие позволяет удобно находить объекты сервиса и работать с ними через стандартные файловые операции.

**结合 MusicFS / Применительно к MusicFS：**

我的目录按照 BPM、调性和素材类型组织，与音乐素材的分类逻辑相对应。

В MusicFS каталоги организованы по BPM, тональности и типу аудиоматериала, что соответствует логике классификации музыкальных данных.

### 74. 为什么文件系统可以只实现读取功能？

**Вопрос:** Почему файловая система может быть реализована только для чтения?

**中文：**

如果文件系统的目标只是展示和访问数据，就不需要实现写入功能。

只读设计可以保护原始数据、降低实现复杂度，并避免数据修改和同步问题。

**Русский：**

Если файловая система предназначена только для просмотра и получения данных, операции записи не обязательны.

Режим только для чтения защищает исходные данные, упрощает реализацию и позволяет избежать проблем синхронизации изменений.

### 75. 为什么 FUSE 文件系统可能需要缓存？

**Вопрос:** Для чего может понадобиться кэширование данных в FUSE-файловой системе?

**中文：**

缓存可以减少重复读取和外部 API 请求，降低访问延迟、网络流量及服务器负载，提高文件系统性能。

但是需要考虑缓存过期和数据一致性问题。

**Русский：**

Кэширование позволяет уменьшить количество повторных операций чтения и запросов к внешнему сервису, снизить задержки, сетевой трафик и нагрузку на сервер.

При этом необходимо учитывать актуальность и согласованность данных.

### 76. FUSE 由哪些主要部分组成？

**Вопрос:** Из каких основных компонентов состоит FUSE?

**中文：**

FUSE 主要包括内核中的 FUSE 组件、用户空间库 libfuse，以及用户自己实现的文件系统程序。

内核组件负责接收和转发文件操作请求，用户空间程序负责处理具体业务逻辑。

**Русский：**

FUSE состоит из компонента ядра, пользовательской библиотеки libfuse и программы, реализующей файловую систему.

Компонент ядра передаёт запросы, а пользовательская программа выполняет конкретную логику файловой системы.

### 77. 什么是 /dev/fuse？

**Вопрос:** Что такое `/dev/fuse`?

**中文：**

`/dev/fuse` 是 Linux 提供的字符设备接口，用于 FUSE 内核组件与用户空间文件系统程序之间的通信。

用户空间程序通过该接口接收文件系统请求并返回响应。

**Русский：**

`/dev/fuse` — это символьное устройство Linux, используемое для обмена запросами и ответами между компонентом FUSE в ядре и файловой системой в пространстве пользователя.

### 78. VFS 和 FUSE 有什么区别？

**Вопрос:** Чем VFS отличается от FUSE?

**中文：**

VFS 是 Linux 内核中为不同文件系统提供统一接口的抽象层。

FUSE 是一种允许文件系统逻辑在用户空间实现的机制。

VFS 负责统一文件访问，FUSE 负责将相关请求转交给用户空间程序。

**Русский：**

VFS — это уровень абстракции ядра Linux, предоставляющий единый интерфейс для разных файловых систем.

FUSE — это механизм реализации файловых систем в пространстве пользователя.

VFS обеспечивает единый доступ, а FUSE передаёт соответствующие запросы пользовательской программе.

### 79. FUSE 是否完全不需要内核参与？

**Вопрос:** Может ли FUSE работать без участия ядра?

**中文：**

不能。虽然文件系统业务逻辑在用户空间运行，但仍然需要 Linux 内核处理系统调用、VFS 操作和 FUSE 通信。

**Русский：**

Нет. Хотя логика файловой системы работает в пространстве пользователя, ядро необходимо для обработки системных вызовов, операций VFS и взаимодействия через FUSE.

### 80. FUSE 的主要优点和缺点是什么？

**Вопрос:** Каковы основные преимущества и недостатки FUSE?

**中文：**

优点是开发简单、调试方便、支持多种编程语言，并具有较好的故障隔离能力。

缺点是存在额外的内核与用户空间通信开销，性能可能低于直接在内核中实现的文件系统。

**Русский：**

Преимущества FUSE — простота разработки и отладки, поддержка разных языков программирования и изоляция ошибок.

Недостаток — дополнительные расходы на обмен данными между ядром и пространством пользователя, что может снижать производительность.

### 81. 什么是挂载点？

**Вопрос:** Что такое точка монтирования?

**中文：**

挂载点是现有目录树中用于连接另一个文件系统的目录。

挂载后，通过该目录访问的是新挂载的文件系统内容。

**Русский：**

После монтирования через этот каталог доступно содержимое подключённой файловой системы.

### 82. 为什么 MusicFS 要求挂载点为空？

**Вопрос:** Почему MusicFS требует пустую точку монтирования?

**中文：**

为了避免挂载后原目录中的内容被暂时遮蔽，也可以减少误操作和路径混淆。

这是 MusicFS 的安全设计要求，并不是所有 Linux 文件系统挂载都必须满足的条件。

**Русский：**

Это необходимо для предотвращения временного скрытия существующего содержимого каталога и уменьшения риска ошибок.

Это ограничение реализации MusicFS, а не обязательное условие любого монтирования в Linux.

### 83. 虚拟文件系统与磁盘文件系统有什么区别？

**Вопрос:** Чем виртуальная файловая система отличается от дисковой файловой системы?

**中文：**

磁盘文件系统通常负责在存储设备上组织和保存文件数据，例如 ext4。

虚拟文件系统的内容可以由程序动态生成，也可以来自内存、数据库或外部服务。

MusicFS 的目录和部分文件由程序构建，音频数据则来自真实磁盘文件。

**Русский：**

Дисковая файловая система организует и хранит данные на носителе, например ext4.

Содержимое виртуальной файловой системы может формироваться программой, находиться в памяти или поступать из базы данных либо внешнего сервиса.

В MusicFS каталоги формируются программой, а аудиоданные читаются из реальных файлов.

### 84. 为什么卸载文件系统前需要释放资源？

**Вопрос:** Почему при завершении работы файловой системы необходимо освобождать ресурсы?

**中文：**

因为程序可能仍然持有文件描述符、内存对象和其他系统资源。

正常退出时应该解除挂载并关闭剩余句柄，避免资源泄漏和无效挂载点。

**Русский：**

Программа может удерживать файловые дескрипторы, объекты памяти и другие системные ресурсы.

При завершении работы необходимо размонтировать файловую систему и закрыть оставшиеся дескрипторы.

### 85. SIGINT、SIGTERM 和 SIGKILL 有什么区别？

**Вопрос:** Чем отличаются SIGINT, SIGTERM и SIGKILL?

**中文：**

- SIGINT：通常由 Ctrl+C 触发，可以被程序处理。
- SIGTERM：请求程序正常终止，可以被程序处理。
- SIGKILL：强制终止进程，不能被捕获或忽略。

MusicFS 处理 SIGINT 和 SIGTERM，以便正常退出和清理资源。

**Русский：**

- SIGINT — сигнал прерывания, обычно вызываемый Ctrl+C.
- SIGTERM — запрос на корректное завершение процесса.
- SIGKILL — принудительное завершение, которое нельзя перехватить или игнорировать.

MusicFS обрабатывает SIGINT и SIGTERM для корректного завершения работы.

### 知识模块三：文件操作、read 与数据访问

#### Модуль 3. Файловые операции и чтение данных

**潜在答辩方向 / Возможные направления вопросов：**

- 随机读取 — Произвольное чтение
- 文件属性 — Атрибуты файла

### 86. FUSE 回调函数和系统调用有什么区别？

**Вопрос:** Чем обработчик FUSE отличается от системного вызова?

**中文：**

系统调用是应用程序向内核请求服务的接口。

FUSE 回调是用户空间文件系统程序实现的处理函数，由 FUSE 框架根据内核请求调用。

例如，应用程序执行 read 系统调用后，在需要访问 FUSE 服务时，可能触发 MusicFS 的 read 回调。

**Русский：**

Системный вызов — это интерфейс обращения приложения к ядру.

Обработчик FUSE — это функция пользовательской файловой системы, вызываемая в ответ на соответствующий запрос ядра.

Например, системный вызов read может привести к вызову обработчика read в MusicFS.

### 87. read 是否每次都需要访问磁盘？

**Вопрос:** Всегда ли операция read обращается к диску?

**中文：**

不一定。数据可能来自操作系统页缓存、程序内存、数据库或者远程服务。

MusicFS 的 `.info` 文件直接从内存读取，音频文件则通过底层文件接口读取，底层读取也可能命中页缓存。

**Русский：**

Нет. Данные могут поступать из страничного кэша, памяти программы, базы данных или удалённого сервиса.

В MusicFS файлы `.info` читаются из памяти, а чтение аудиофайлов может использовать страничный кэш операционной системы.

### 88. 为什么 read 返回 bytes 而不是字符串？

**Вопрос:** Почему read возвращает bytes, а не строку?

**中文：**

因为文件系统的底层数据以字节表示。音频、图片和文本都可以表示为字节序列。

字符串需要先通过指定编码转换为字节，例如 UTF-8。

**Русский：**

Потому что данные файлов представляются последовательностями байтов. Аудио, изображения и текст могут быть представлены в виде байтов.

Строки необходимо преобразовать в байты с помощью кодировки, например UTF-8.

### 89. 什么是随机访问和顺序访问？

**Вопрос:** Чем произвольный доступ отличается от последовательного?

**中文：**

顺序访问是按照文件中的数据顺序读取。

随机访问允许从任意指定偏移读取数据，不需要先读取前面的全部内容。

MusicFS 使用 `pread()` 支持随机访问。

**Русский：**

Последовательный доступ предполагает чтение данных по порядку.

Произвольный доступ позволяет читать данные с заданного смещения без предварительного чтения всех предыдущих байтов.

MusicFS использует `pread()` для произвольного доступа.

### 90. 如果 read 返回的数据少于请求大小怎么办？

**Вопрос:** Что делать, если read возвращает меньше данных, чем запрошено?

**中文：**

对于普通文件，短读取可能发生在文件末尾，也可能由其他读取条件造成。

MusicFS 使用循环继续读取剩余字节，直到达到请求大小或遇到 EOF。

**Русский：**

Короткое чтение может происходить при достижении конца файла или по другим причинам.

MusicFS продолжает чтение в цикле до получения запрошенного количества байтов или достижения EOF.

#### Модуль 4. Python bindings, библиотеки и интерфейсы

### 91. 为什么需要 Python bindings？

**Вопрос:** Зачем нужны Python bindings?

**中文：**

因为许多底层系统库使用 C 或 C++ 编写，而 Python 无法直接按照普通 Python 函数的方式调用所有原生接口。

语言绑定负责连接不同语言的调用方式和数据类型，使 Python 能够使用这些库。

**Русский：**

Многие низкоуровневые библиотеки написаны на C или C++.

Python bindings обеспечивают взаимодействие между языками, преобразование типов данных и возможность вызова функций таких библиотек из Python.

### 92. pyfuse3 是如何连接 Python 与 libfuse3 的？

**Вопрос:** Как pyfuse3 связывает Python с libfuse3?

**中文：**

pyfuse3 通过基于 Cython 的扩展接口连接 Python 和 libfuse3，将 FUSE 请求转换为 Python 可以处理的操作，并将 Python 处理结果返回给底层库。

**Русский：**

pyfuse3 использует интерфейс расширения на основе Cython для взаимодействия Python с libfuse3.

Он преобразует запросы FUSE в операции, обрабатываемые Python, и передаёт результаты обратно библиотеке.

### 93. 什么是 API？

**Вопрос:** Что такое API?

**中文：**

API（Application Programming Interface）是应用程序编程接口，规定软件组件之间如何进行交互。

API 可以是本地库的函数接口，也可以是远程服务提供的网络接口。

**Русский：**

API — это программный интерфейс, определяющий способы взаимодействия программных компонентов.

API может представлять собой набор функций локальной библиотеки или сетевой интерфейс удалённого сервиса.

### 94. API 和 ABI 有什么区别？

**Вопрос:** Чем API отличается от ABI?

**中文：**

API 定义源代码层面的接口，例如函数名称、参数和返回值。

ABI 定义二进制层面的交互规则，例如调用约定、数据布局和符号规则。

API 兼容不一定意味着 ABI 兼容。

**Русский：**

API определяет интерфейс на уровне исходного кода: имена функций, параметры и возвращаемые значения.

ABI определяет правила взаимодействия на бинарном уровне, например соглашения о вызовах и представление данных.

Совместимость API не всегда означает совместимость ABI.

### 95. 库、框架和语言绑定有什么区别？

**Вопрос:** Чем библиотека отличается от фреймворка и языковых привязок?

**中文：**

库提供可以被程序调用的功能。

框架通常提供程序结构和执行流程，并在适当的时候调用用户实现的代码。

语言绑定负责连接不同编程语言之间的接口。

在本实验中，libfuse3 是底层库，pyfuse3 提供 Python 绑定及文件系统操作接口。

**Русский：**

Библиотека предоставляет функции, вызываемые программой.

Фреймворк задаёт структуру и процесс выполнения приложения и вызывает пользовательский код.

Языковые привязки обеспечивают взаимодействие между разными языками программирования.

В данной работе libfuse3 является базовой библиотекой, а pyfuse3 предоставляет Python bindings.

### 96. Python 中模块和包有什么区别？

**Вопрос:** Чем модуль Python отличается от пакета?

**中文：**

模块是可以被导入的代码组织单位，通常对应一个 `.py` 文件。

包用于组织多个模块和子包，通常对应一个目录。普通包通常包含 `__init__.py`，命名空间包可以没有该文件。

**Русский：**

Модуль — это импортируемая единица организации кода, обычно отдельный файл `.py`.

Пакет объединяет модули и подпакеты, обычно в одном каталоге. Обычный пакет содержит `__init__.py`, а пакет пространства имён может не содержать этот файл.

### 97. 什么是模块化编程？

**Вопрос:** Что такое модульное программирование?

**中文：**

模块化编程是将程序划分为多个具有明确职责和接口的模块。

这样可以降低复杂度，提高代码可维护性、可测试性和复用性。

**Русский：**

Модульное программирование — это разделение программы на модули с определёнными обязанностями и интерфейсами.

Это уменьшает сложность и упрощает сопровождение, тестирование и повторное использование кода.

### 98. 什么是封装？

**Вопрос:** Что такое инкапсуляция?

**中文：**

封装是将数据和相关操作组织在一起，并通过明确接口访问内部功能，减少外部代码对内部实现细节的依赖。

例如 Catalog 封装了元数据解析和虚拟节点构建逻辑。

**Русский：**

Инкапсуляция — это объединение данных и связанных с ними операций с предоставлением определённого интерфейса доступа.

Например, Catalog инкапсулирует обработку метаданных и создание виртуальных узлов.

### 99. 什么是高内聚和低耦合？

**Вопрос:** Что такое высокая связность и слабая связанность модулей?

**中文：**

高内聚表示一个模块内部的功能围绕明确且相关的职责组织。

低耦合表示不同模块之间的依赖尽可能少，并通过明确接口交互。

MusicFS 将目录构建、文件操作和程序启动分开，体现了职责分离。

**Русский：**

Высокая внутренняя связность означает, что функции одного модуля относятся к общей задаче.

Слабая связанность означает минимальную зависимость между модулями и взаимодействие через определённые интерфейсы.

В MusicFS построение каталогов, файловые операции и запуск программы разделены.

### 100. 为什么学校要求隔离 LLM 生成的外部服务代码？

**Вопрос:** Почему код взаимодействия с внешним сервисом, созданный LLM, должен быть выделен в отдельный модуль?

**中文：**

因为独立模块更容易审查、测试和替换生成的代码，同时可以减少其对文件系统核心逻辑的影响。

需要注意，模块化本身并不等于安全沙箱，也不能保证生成代码一定正确。

**Русский：**

Отдельный модуль упрощает проверку, тестирование и замену сгенерированного кода, а также уменьшает его влияние на основную логику файловой системы.

Однако модульность сама по себе не является песочницей и не гарантирует корректность кода.

### 知识模块六：外部服务、HTTP、JSON 与数据映射

### 101. 什么是外部服务？

**Вопрос:** Что такое внешний сервис?

**中文：**

外部服务是独立于当前程序运行，并通过某种接口提供数据或功能的软件系统。

例如 GitHub、数据库服务、天气 API 或消息服务。

外部服务不一定在远程服务器上，也可以运行在本地的另一个进程中。

**Русский：**

Внешний сервис — это программная система, работающая отдельно от текущей программы и предоставляющая данные или функции через интерфейс.

Примерами являются GitHub, базы данных, погодные API и сервисы сообщений.

Внешний сервис может работать как удалённо, так и локально.

### 102. 什么是 HTTP 和 REST API？

**Вопрос:** Что такое HTTP и REST API?

**中文：**

HTTP 是客户端和服务器之间交换请求与响应的应用层协议。

REST 是一种面向资源的架构风格。REST API 通常使用 HTTP 方法访问和操作资源。

例如 GET 获取数据，POST 通常用于提交数据或创建资源。

**Русский：**

HTTP — это протокол прикладного уровня для обмена запросами и ответами между клиентом и сервером.

REST — это архитектурный стиль, ориентированный на ресурсы. REST API обычно использует методы HTTP для работы с ресурсами.

Например, GET получает данные, а POST используется для отправки данных или создания ресурсов.

### 103. FUSE 如何将外部服务表示为文件系统？

**Вопрос:** Как FUSE представляет внешний сервис в виде файловой системы?

**中文：**

FUSE 可以将外部服务中的对象映射为文件，将对象集合映射为目录，并将文件操作转换为 API 请求。

例如 GitHub 仓库可以表示为目录，仓库中的文件可以表示为虚拟文件。

**Русский：**

FUSE может представлять объекты внешнего сервиса как файлы, коллекции объектов — как каталоги, а файловые операции преобразовывать в запросы API.

Например, репозиторий GitHub может быть представлен каталогом, а его содержимое — виртуальными файлами.

**示例 / Пример：**

    mount/
        repositories/
            project-a/
                README.md
                main.py
            project-b/
                README.md

### 104. read 操作是否应该每次都发送 HTTP 请求？

**Вопрос:** Должна ли каждая операция read отправлять HTTP-запрос?

**中文：**

不一定。一个文件可能被分成多个 read 请求。如果每次读取都重新下载全部数据，会产生大量重复网络请求。

可以在打开文件时获取内容并保存到缓存，也可以在服务支持时使用 HTTP Range 请求获取指定字节范围。

**Русский：**

Не обязательно. Чтение одного файла может состоять из нескольких операций read.

Повторная загрузка всего содержимого при каждом чтении создаёт лишние сетевые запросы.

Можно загрузить данные при открытии файла, использовать кэш или HTTP Range при поддержке сервером.

### 105. 如果外部服务不可用，FUSE 应该如何处理？

**Вопрос:** Как FUSE должна обрабатывать недоступность внешнего сервиса?

**中文：**

应该处理网络异常、请求超时和服务错误，并将错误转换为适当的文件系统错误码。

例如超时可以对应 ETIMEDOUT，其他无法完成的 I/O 操作可以对应 EIO。

不应该让整个文件系统因一次请求失败而直接崩溃。

**Русский：**

Необходимо обрабатывать сетевые ошибки, тайм-ауты и ошибки сервиса, преобразуя их в соответствующие ошибки файловой системы.

Например, тайм-аут может соответствовать ETIMEDOUT, а ошибка ввода-вывода — EIO.

Один неудачный запрос не должен приводить к завершению всей файловой системы.

### 106. 什么是 JSON？为什么 MusicFS 使用 JSON？

**Вопрос:** Что такое JSON и почему MusicFS использует JSON?

**中文：**

JSON 是一种轻量级文本数据交换格式，可以表示对象、数组、字符串、数字等数据。

MusicFS 使用 JSON 保存音频路径、ID、BPM、调性和类型等元数据，方便程序解析并构建虚拟目录。

**Русский：**

JSON — это лёгкий текстовый формат обмена данными, поддерживающий объекты, массивы, строки и числа.

MusicFS использует JSON для хранения метаданных аудиофайлов, включая путь, ID, BPM, тональность и тип.

### 107. 如何将数据库表示为 FUSE 文件系统？

**Вопрос:** Как представить базу данных в виде FUSE-файловой системы?

**中文：**

可以将数据库表映射为目录，将记录映射为文件，将记录内容转换为 JSON 或文本。

当用户列出目录时，文件系统可以执行查询获取记录列表；读取文件时，可以查询指定记录并返回内容。

**Русский：**

Таблицы базы данных можно представить каталогами, записи — файлами, а содержимое записей преобразовать в JSON или текст.

При перечислении каталога выполняется запрос списка записей, а при чтении файла — запрос конкретной записи.

**示例 / Пример：**

    database/
        users/
            1.json
            2.json
        products/
            100.json
            101.json

**可能的操作映射 / Возможное отображение операций：**

| 文件操作 | 数据库操作 |
|---|---|
| readdir | SELECT 查询记录列表 |
| lookup | 查询指定记录是否存在 |
| read | SELECT 获取记录内容 |
| write | 在支持写入时执行 UPDATE |
| unlink | 在支持删除时执行 DELETE |

### 108. MusicFS 与基于远程服务的 FUSE 有什么区别？

**Вопрос:** Чем MusicFS отличается от FUSE-системы, работающей с удалённым сервисом?

**中文：**

MusicFS 的数据来源是本地 JSON 和音频文件，不需要发送网络请求。

基于远程服务的 FUSE 需要通过 API 获取数据，因此还需要处理网络延迟、身份认证、请求限制和远程数据一致性。

**Русский：**

MusicFS использует локальные JSON-метаданные и аудиофайлы, поэтому сетевые запросы не требуются.

FUSE-система на основе удалённого сервиса получает данные через API и должна учитывать сетевые задержки, аутентификацию, ограничения запросов и согласованность удалённых данных.

- 写入操作 — Операции записи

- 错误码 — Коды ошибок

### 109. 只读挂载和只读文件权限有什么区别？

**Вопрос:** Чем монтирование только для чтения отличается от прав доступа только на чтение?

**中文：**

只读挂载限制通过该挂载点修改整个文件系统。

只读文件权限则是针对文件或目录设置的访问权限。

MusicFS 同时使用 `ro` 挂载选项、只读权限和打开模式检查。

**Русский：**

Монтирование только для чтения запрещает изменения через соответствующую точку монтирования.

Права доступа только на чтение относятся к конкретному файлу или каталогу.

MusicFS использует параметр `ro`, права доступа и проверку режима открытия.

### 110. 为什么只读文件系统仍然需要 open 和 release？

**Вопрос:** Почему файловой системе только для чтения нужны open и release?

**中文：**

因为读取文件仍然需要建立和释放文件句柄。

只读限制的是修改操作，而不是文件打开、读取和资源管理操作。

**Русский：**

Даже при чтении необходимо создавать и освобождать файловые идентификаторы.

Режим только для чтения запрещает изменение данных, но не открытие, чтение и управление ресурсами.

### 111. 如果要将 MusicFS 改成可读写文件系统，需要实现什么？

**Вопрос:** Что необходимо реализовать для поддержки записи в MusicFS?

**中文：**

需要根据设计目标实现 `write`、`create`、`unlink`、`rename`、`setattr` 等相关操作，并处理源文件与 JSON 元数据同步、访问权限、并发修改和错误恢复。

不能只删除 `ro` 参数就认为文件系统已经支持写入。

**Русский：**

Необходимо реализовать соответствующие операции, например `write`, `create`, `unlink`, `rename` и `setattr`.

Также нужно обеспечить синхронизацию исходных файлов и JSON-метаданных, контроль доступа, обработку параллельных изменений и восстановление после ошибок.

Недостаточно просто удалить параметр `ro`.

### 知识模块八：缓存机制与数据一致性

#### Модуль 8. Кэширование и согласованность данных

> 本次考试最后一道题的核心扩展方向。

**潜在答辩方向 / Возможные направления вопросов：**

- 缓存基本原理 — Принципы кэширования
- 缓存命中与未命中 — Попадание и промах кэша
- 页缓存 — Страничный кэш
- 元数据缓存 — Кэш метаданных
- TTL — Время жизни кэша
- 缓存失效 — Инвалидация кэша
- 数据一致性 — Согласованность данных
- 缓存淘汰 — Вытеснение из кэша

### 112. 什么是缓存？

**Вопрос:** Что такое кэш?

**中文：**

缓存是保存已经获取或计算的数据的临时存储机制。

它通过重复使用已有数据，减少访问较慢的数据源所需的时间。

**Русский：**

Кэш — это механизм временного хранения ранее полученных или вычисленных данных.

Он позволяет повторно использовать данные и уменьшать время обращения к более медленному источнику.

### 113. 什么是缓存命中和缓存未命中？

**Вопрос:** Что такое попадание и промах кэша?

**中文：**

缓存命中（Cache Hit）表示请求的数据已经存在于可用缓存中，可以直接返回。

缓存未命中（Cache Miss）表示缓存中没有可用数据，需要访问原始数据源。

**Русский：**

Попадание в кэш означает, что запрошенные данные уже находятся в кэше и могут быть возвращены сразу.

Промах кэша означает отсутствие доступных данных, поэтому необходимо обратиться к исходному источнику.

### 114. FUSE 文件系统中有哪些缓存？

**Вопрос:** Какие виды кэширования существуют в FUSE-файловой системе?

**中文：**

主要包括：

- 页缓存：缓存文件数据。
- 属性缓存：缓存文件大小、权限和时间戳等属性。
- 目录项缓存：缓存文件名与 inode 的查找结果。
- 应用程序缓存：由用户空间文件系统自行实现。

**Русский：**

Основные виды кэширования:

- Страничный кэш — хранение данных файлов.
- Кэш атрибутов — хранение размера, прав доступа и временных меток.
- Кэш записей каталогов — хранение результатов поиска имён и inode.
- Кэш приложения — кэш, реализованный пользовательской программой.

### 115. 什么是 TTL？

**Вопрос:** Что такое TTL в кэшировании?

**中文：**

TTL（Time To Live）表示缓存数据的有效时间。

超过有效时间后，缓存数据需要重新获取或验证。

TTL 较长可以减少请求次数，但可能导致数据不够及时。

**Русский：**

TTL — это время жизни кэшированных данных.

После истечения TTL данные необходимо обновить или проверить.

Большой TTL уменьшает количество запросов, но может привести к использованию устаревших данных.

### 116. 什么是缓存失效？

**Вопрос:** Что такое инвалидация кэша?

**中文：**

缓存失效是将不再有效的缓存数据标记为不可用或删除，使下一次访问重新获取最新数据。

例如源文件内容变化后，旧缓存可能需要失效。

**Русский：**

Инвалидация кэша — это удаление или пометка устаревших данных как недействительных, чтобы при следующем обращении получить актуальные данные.

Например, после изменения исходного файла старый кэш может потребовать инвалидации.

### 117. 缓存是否越多越好？

**Вопрос:** Всегда ли увеличение размера кэша улучшает систему?

**中文：**

不是。缓存会占用内存，并可能引入数据过期和一致性问题。

应该根据访问频率、数据大小、更新频率和可用内存选择适当的缓存策略。

**Русский：**

Нет. Кэш занимает память и может создавать проблемы с актуальностью и согласованностью данных.

Стратегия кэширования должна учитывать частоту доступа, размер данных, частоту обновления и доступную память.

### 118. 什么是 LRU 缓存策略？

**Вопрос:** Что такое алгоритм LRU?

**中文：**

LRU（Least Recently Used）是一种缓存淘汰策略。当缓存空间不足时，优先移除最长时间没有被访问的数据。

**Русский：**

LRU — это алгоритм вытеснения из кэша, при котором при нехватке места удаляются данные, которые дольше всего не использовались.

### 119. MusicFS 是否使用缓存？

**Вопрос:** Использует ли MusicFS кэширование?

**中文：**

MusicFS 在启动时将目录结构和元数据保存在内存中，形成固定索引。

这是一种内存数据表示，并不是具有 TTL 或淘汰机制的动态缓存。

MusicFS 禁用了 writeback cache，但 Linux 仍可能使用文件页缓存。程序没有自行实现 HTTP 缓存或 LRU 缓存。

**Русский：**

MusicFS при запуске сохраняет структуру каталогов и метаданные в памяти, формируя фиксированный индекс.

Это представление данных в памяти, а не динамический кэш с TTL или вытеснением.

Writeback cache отключён, но Linux всё ещё может использовать страничный кэш. HTTP-кэш и LRU-кэш в программе не реализованы.

### 知识模块九：并发、性能与数据安全

#### Модуль 9. Параллелизм, производительность и безопасность

**潜在答辩方向 / Возможные направления вопросов：**

- 并发请求 — Конкурентные запросы
- 并发与并行 — Конкурентность и параллелизм
- 异步操作 — Асинхронные операции
- 竞态条件 — Состояние гонки
- 路径安全 — Безопасность путей
- 性能瓶颈 — Узкие места производительности

### 120. 什么是并发和并行？

**Вопрос:** Чем конкурентность отличается от параллелизма?

**中文：**

并发表示多个任务在一段时间内交替推进。

并行表示多个任务在同一时刻实际执行，例如在多个 CPU 核心上执行。

异步程序可以实现并发，但不一定实现并行。

**Русский：**

Конкурентность означает продвижение нескольких задач в течение одного периода времени.

Параллелизм означает фактическое одновременное выполнение нескольких задач, например на разных ядрах процессора.

Асинхронность обеспечивает конкурентность, но не обязательно параллелизм.

### 121. 为什么 MusicFS 使用异步函数？

**Вопрос:** Почему MusicFS использует асинхронные функции?

**中文：**

因为 pyfuse3 使用 Trio 处理文件系统请求。

异步函数可以在等待某些操作时让出执行机会，使其他请求得到处理。

同步磁盘读取则通过工作线程执行，避免阻塞 Trio 事件循环。

**Русский：**

pyfuse3 использует Trio для обработки запросов файловой системы.

Асинхронные функции позволяют другим задачам выполняться во время ожидания.

Синхронное чтение файлов выполняется в рабочем потоке, чтобы не блокировать цикл событий Trio.

### 122. 什么是竞态条件？

**Вопрос:** Что такое состояние гонки?

**中文：**

竞态条件是多个任务访问共享资源时，程序结果依赖于它们不可预测的执行顺序。

例如两个任务同时修改同一个共享目录索引，可能导致数据不一致。

**Русский：**

Состояние гонки возникает, когда результат работы программы зависит от непредсказуемого порядка выполнения нескольких задач, обращающихся к общим ресурсам.

Например, одновременное изменение общего индекса каталогов может привести к несогласованности данных.

### 123. 什么是路径遍历攻击？

**Вопрос:** Что такое атака Path Traversal?

**中文：**

路径遍历是通过构造特殊路径，例如包含 `../` 的路径，尝试访问允许目录之外的文件。

MusicFS 通过解析路径并检查其是否位于 `source_root` 中降低这种风险。

但当前实现并不能保证抵御所有并发路径替换攻击。

**Русский：**

Path Traversal — это попытка доступа к файлам за пределами разрешённого каталога с помощью специально сформированных путей, например содержащих `../`.

MusicFS разрешает путь и проверяет его принадлежность к `source_root`.

Однако текущая реализация не гарантирует защиту от всех атак с одновременной заменой путей.

### 124. 为什么 FUSE 可能比 ext4 慢？

**Вопрос:** Почему FUSE может работать медленнее, чем ext4?

**中文：**

因为 FUSE 的请求可能需要经过内核、用户空间文件系统程序和底层数据源，产生额外的通信、调度和数据传输开销。

如果数据源是远程服务，还会增加网络延迟。

实际性能取决于工作负载、缓存和具体实现。

**Русский：**

Запросы FUSE могут проходить через ядро, пользовательскую программу и нижележащий источник данных.

Это создаёт дополнительные расходы на обмен данными, планирование и передачу информации.

При работе с удалённым сервисом добавляются сетевые задержки.

Реальная производительность зависит от нагрузки, кэширования и реализации.

### 125. 如何优化 FUSE 文件系统性能？

**Вопрос:** Как можно оптимизировать производительность FUSE-файловой системы?

**中文：**

可以采用以下方法：

- 缓存重复访问的数据和元数据。
- 减少不必要的外部服务请求。
- 使用高效的目录索引。
- 避免阻塞事件循环。
- 使用适当的批量读取和并发处理。
- 通过实际性能测试定位瓶颈。

对于 MusicFS，当前可以重点考虑大型音乐库的索引内存占用和目录属性查询成本。

**Русский：**

Для оптимизации можно использовать следующие методы:

- Кэширование часто используемых данных и метаданных.
- Уменьшение лишних запросов к внешним сервисам.
- Использование эффективных индексов каталогов.
- Предотвращение блокировки цикла событий.
- Пакетное чтение и конкурентную обработку запросов.
- Измерение производительности для поиска узких мест.

Для MusicFS особенно актуальны объём памяти индекса и стоимость получения атрибутов при больших музыкальных коллекциях.

## 一、FUSE 与 Linux 文件系统原理

### 126. Что такое FUSE? Чем FUSE отличается от libc?

**什么是 FUSE？FUSE 与 libc 有什么区别？**

**中文：**

FUSE（Filesystem in Userspace）是一种允许开发者在用户空间实现文件系统的机制。

libc 是 C 语言标准库及相关系统接口的实现，提供内存管理、字符串处理、文件操作以及系统调用封装等功能。

FUSE 用于实现文件系统，而 libc 提供通用编程接口。

**Русский：**

FUSE — это механизм реализации файловых систем в пространстве пользователя.

libc — это стандартная библиотека языка C, предоставляющая стандартные функции и обёртки над системными вызовами.

FUSE предназначен для реализации файловых систем, а libc предоставляет общие программные интерфейсы.

**补充解释 / Дополнительное объяснение：**

| 对比 | FUSE | libc |
|---|---|---|
| 类型 | 文件系统机制 | C 标准库及系统接口库 |
| 作用 | 实现用户空间文件系统 | 提供通用函数 |
| 典型接口 | lookup、getattr、readdir | malloc、printf、read |
| 实验中的关系 | 实现 MusicFS | 提供部分底层系统接口 |

不要混淆 libc 和 libfuse3。libfuse3 是专门用于 FUSE 开发的用户空间库。

Не следует путать libc и libfuse3. libfuse3 — это библиотека для разработки файловых систем FUSE.

---

### 127. Что такое VFS?

**什么是 VFS？**

**中文：**

VFS（Virtual File System）是 Linux 内核中的文件系统抽象层，为不同类型的文件系统提供统一的访问接口。

应用程序不需要知道底层使用的是 ext4、FUSE、tmpfs 还是其他文件系统。

**Русский：**

VFS — это уровень абстракции в ядре Linux, предоставляющий единый интерфейс для работы с различными файловыми системами.

Приложению не нужно знать, какая конкретная файловая система используется.

**结构 / Структура：**

```text
Application (ls, cat, Python)
              |
        System Call
              |
             VFS
              |
    +---------+---------+---------+
    |         |         |         |
   ext4     tmpfs     procfs     FUSE
                                  |
                               MusicFS
```

VFS 负责提供统一接口，具体文件系统负责实现实际操作。

VFS предоставляет единый интерфейс, а конкретная файловая система реализует соответствующие операции.

---

### 128. Чем FUSE отличается от обычной виртуальной файловой системы и как FUSE работает?

**FUSE 与普通虚拟文件系统有什么区别？FUSE 如何工作？**

**中文：**

VFS 是内核中的文件系统抽象层，而 FUSE 是允许具体文件系统在用户空间实现的机制。

与 ext4 等传统内核文件系统相比，FUSE 的主要业务逻辑运行在用户空间。

**Русский：**

VFS — это уровень абстракции файловых систем в ядре.

FUSE — это механизм, позволяющий реализовывать файловые системы в пространстве пользователя.

В отличие от ext4, основная логика FUSE-файловой системы выполняется в пользовательском процессе.

**工作流程 / Принцип работы：**

```text
Userspace: Application
          |
          | System call
          v
Kernel:   VFS
          |
          v
          FUSE kernel component
          |
          | /dev/fuse
          v
Userspace: libfuse3 / pyfuse3
          |
          v
          MusicFS callback
          |
          v
          Data source
```

处理完成后，数据或错误沿相反方向返回应用程序。

После обработки запроса данные или ошибка возвращаются приложению через ядро.

**注意：**

FUSE 不是完全脱离内核运行的文件系统。内核仍然负责系统调用、VFS 和 FUSE 通信。

FUSE не работает полностью независимо от ядра. Ядро обрабатывает системные вызовы и обеспечивает взаимодействие с пользовательским процессом.

---

### 129. Что такое псевдофайловая система?

**什么是伪文件系统？**

**中文：**

伪文件系统是一种将内核状态、设备信息或其他程序数据表示为文件和目录的文件系统。

其内容不一定以普通文件的形式存储在磁盘上，可以由程序动态生成。

**Русский：**

Псевдофайловая система — это файловая система, которая представляет системную информацию или программные данные в виде файлов и каталогов без обязательного хранения этих данных на диске.

| 文件系统 | 作用 | Назначение |
|---|---|---|
| procfs | 进程和内核信息 | Информация о процессах и ядре |
| sysfs | 设备和内核对象 | Информация об устройствах и объектах ядра |
| devtmpfs | 设备节点 | Узлы устройств |
| MusicFS | 虚拟音乐分类 | Виртуальная классификация аудиофайлов |

**结合 MusicFS：**

MusicFS 具有虚拟文件系统的特征。目录结构和 `.info` 文件由程序生成，但音频内容来自真实磁盘文件。

MusicFS имеет признаки виртуальной файловой системы. Каталоги и файлы `.info` формируются программой, а аудиоданные читаются из реальных файлов.

### 130. Почему FUSE нет в списке lsmod?

**为什么 lsmod 中没有显示 FUSE？**

**中文：**

`lsmod` 只显示当前已经加载的可加载内核模块。

如果 FUSE 被直接编译进 Linux 内核，而不是作为独立模块加载，就不会出现在 lsmod 的输出中。

也可能是模块尚未加载，或者当前内核没有启用 FUSE。

**Русский：**

Команда `lsmod` показывает только загруженные модули ядра.

Если поддержка FUSE встроена непосредственно в ядро, FUSE не будет отображаться в списке `lsmod`.

Также возможно, что модуль ещё не загружен или поддержка FUSE отсутствует.

**检查命令 / Команды проверки：**

```bash
lsmod | grep fuse

cat /proc/filesystems | grep fuse

ls -l /dev/fuse

grep CONFIG_FUSE_FS /boot/config-$(uname -r)
```

| 内核配置 | 含义 |
|---|---|
| CONFIG_FUSE_FS=y | 直接编译进内核 |
| CONFIG_FUSE_FS=m | 作为可加载模块构建 |
| CONFIG_FUSE_FS 未启用 | 不支持 FUSE |

WSL2 不一定提供 `/boot/config-$(uname -r)` 文件，因此不能仅根据该命令失败判断 FUSE 不可用。

### 131. Можно ли смонтировать две разные FUSE-файловые системы в одну директорию?

**能否将两个不同的 FUSE 文件系统挂载到同一个目录？**

**中文：**

可以。Linux 在满足权限和挂载工具限制的情况下，支持在同一个挂载点叠加多个挂载。

后挂载的文件系统会遮蔽先挂载的文件系统，而不会自动合并它们的内容。

卸载上层文件系统后，下层文件系统可以重新可见。

**Русский：**

Да, Linux допускает несколько монтирований в одной точке при наличии необходимых прав.

Последняя смонтированная файловая система скрывает предыдущую, а не объединяет её содержимое.

После размонтирования верхней файловой системы нижняя снова становится доступной.

**示例 / Пример：**

```text
/mnt/music
    |
    +-- FUSE B   <- 当前可见
    +-- FUSE A   <- 被遮蔽
    +-- 原始目录
```

**结合 MusicFS：**

MusicFS 会检查挂载点是否已经被挂载，因此当前程序主动禁止重复挂载。

这是 MusicFS 自身的限制，而不是 Linux 的普遍限制。

MusicFS проверяет, используется ли точка монтирования. Поэтому повторное монтирование запрещено текущей реализацией, но не самим Linux.

## 二、inode、硬链接与符号链接

### 132. Что такое inode?

**什么是 inode？**

**中文：**

inode 是 Unix/Linux 文件系统中用于标识文件对象并保存或关联文件元数据的数据结构。

它通常包含：

- 文件类型
- 文件权限
- 文件大小
- 所有者 UID
- 所属组 GID
- 时间戳
- 硬链接数量
- 文件数据的存储位置或相关引用

文件名通常保存在目录项中，而不是 inode 中。

**Русский：**

Inode — это индексный дескриптор файловой системы, который идентифицирует файловый объект и содержит его метаданные:

- Тип файла.
- Права доступа.
- Размер файла.
- Владелец UID.
- Группа GID.
- Временные метки.
- Количество жёстких ссылок.
- Информация о расположении данных.

Имя файла обычно хранится в записи каталога, а не в inode.

**结合 MusicFS：**

```text
by_bpm/130/real01.wav ----+
                          |
by_key/D#_major/... ------+--> inode 2 --> Source audio
                          |
by_type/melody/... -------+

st_nlink = 3
```

三个虚拟目录项引用同一个虚拟 inode，因此不需要复制三份音频文件。

Три виртуальные записи каталогов указывают на один виртуальный inode, поэтому аудиофайл не копируется три раза.

**注意：**

inode 编号通常只在所属文件系统内唯一。可以结合 `st_dev` 和 `st_ino` 识别文件对象。

---

### 133. Чем символическая ссылка отличается от жёсткой ссылки?

**符号链接与硬链接有什么区别？**

**中文：**

硬链接是指向同一个 inode 的另一个目录项。

符号链接是具有独立 inode 的特殊文件，其内容保存目标路径。

**Русский：**

Жёсткая ссылка — это дополнительная запись каталога, указывающая на тот же inode.

Символическая ссылка — это специальный файл с собственным inode, содержащий путь к целевому объекту.

**硬链接 / Hard link：**

```text
a.txt ----+
          +--> inode 100 --> Data
b.txt ----+
```

**符号链接 / Symbolic link：**

```text
link.txt --> inode 200 --> Path: a.txt
                              |
                              v
                          inode 100 --> Data
```

| 特征 | Hard link | Symlink |
|---|---|---|
| inode | 相同 | 独立 |
| 是否依赖目标路径 | 否 | 是 |
| 跨文件系统 | 不支持 | 支持 |
| 指向目录 | 通常禁止 | 允许 |
| 删除原文件名 | 其他硬链接仍有效 | 可能失效 |

**创建命令：**

```bash
ln a.txt b.txt

ln -s a.txt link.txt
```

---

### 134. Какие ограничения существуют у hardlink?

**硬链接有哪些限制？**

**中文：**

硬链接不能跨文件系统。

Linux 通常禁止通过普通接口创建目录的硬链接，以避免破坏目录树结构。

文件系统还可能限制一个 inode 的最大链接数量。Linux 的安全策略也可能限制用户为其他用户拥有的文件创建硬链接。

**Русский：**

Жёсткие ссылки не могут пересекать границы файловых систем.

Linux обычно запрещает создание жёстких ссылок на каталоги.

Также существуют ограничения на количество ссылок и дополнительные ограничения безопасности.

**为什么不能随意创建目录硬链接？**

目录硬链接可能形成循环，增加目录遍历和文件系统管理的复杂度。

Жёсткие ссылки на каталоги могут создавать циклы и нарушать древовидную структуру файловой системы.

---

### 135. Как отличить оригинальный файл от хардлинка?

**如何区分原始文件和硬链接？**

**中文：**

通常无法区分。

创建硬链接后，原文件名与新文件名都是指向同一个 inode 的平等目录项。

文件系统通常不会记录哪个文件名是最初创建的。

**Русский：**

Обычно отличить исходное имя файла от жёсткой ссылки невозможно.

Обе записи каталога равноправны и указывают на один inode.

Файловая система обычно не хранит информацию о том, какое имя было создано первым.

**验证命令：**

```bash
touch a.txt

ln a.txt b.txt

ls -li a.txt b.txt

stat a.txt b.txt
```

如果两个文件具有相同的 `st_dev` 和 `st_ino`，说明它们引用同一个文件对象，但无法据此判断哪个是原始名称。

## 三、缓存、算法与数据传输

### 136. Как можно реализовать кэширование? Какие существуют алгоритмы?

**如何实现缓存？有哪些缓存算法？**

**中文：**

可以使用内存或磁盘保存已经获取的数据。

当再次请求相同数据时，优先检查缓存。如果缓存不存在或已经失效，再访问原始数据源。

缓存可以减少重复计算、磁盘访问和网络请求。

**Русский：**

Кэширование можно реализовать с помощью хранения ранее полученных данных в памяти или на диске.

При повторном запросе сначала проверяется кэш. Если данных нет или они устарели, выполняется обращение к источнику.

Кэширование уменьшает количество повторных вычислений, обращений к диску и сетевых запросов.

**常见缓存算法 / Алгоритмы кэширования：**

| 算法 | 中文解释 | Русский |
|---|---|---|
| LRU | 淘汰最久未使用的数据 | Удаление давно не использованных данных |
| LFU | 淘汰使用频率最低的数据 | Удаление наименее часто используемых данных |
| FIFO | 淘汰最早进入缓存的数据 | Удаление данных в порядке поступления |
| Random | 随机淘汰 | Случайное вытеснение |
| CLOCK | 使用访问标记近似实现 LRU | Приближённая реализация LRU |
| TTL | 根据有效时间判断缓存是否过期 | Проверка срока действия данных |

**注意：**

TTL 是缓存有效期机制，不是严格意义上的容量淘汰算法，可以与 LRU 等算法结合使用。

TTL определяет срок действия кэшированных данных и может использоваться вместе с LRU.

---

### 137. Что такое LRU Cache? Как он работает?

**什么是 LRU 缓存？如何实现？**

**中文：**

LRU（Least Recently Used）是一种缓存淘汰算法。

当缓存容量不足时，优先删除最长时间没有被访问的数据。

常见实现使用哈希表和双向链表，使查询和更新操作通常达到 O(1) 的平均时间复杂度。

**Русский：**

LRU — это алгоритм вытеснения из кэша, при котором удаляются данные, которые дольше всего не использовались.

Обычно он реализуется с помощью хеш-таблицы и двусвязного списка, обеспечивая среднюю сложность операций O(1).

**工作示例：**

缓存容量为 3，左侧为最近使用的数据。

```text
初始状态： [A, B, C]

访问 B：   [B, A, C]

访问 D：   [D, B, A]

C 被淘汰。
```

**实现方式：**

- 哈希表：快速查找缓存对象。
- 双向链表：维护访问顺序。
- 每次访问时，将对象移动到最近使用的一端。
- 容量不足时，删除最久未使用的一端。

**Python 示例：**

```python
from functools import lru_cache

@lru_cache(maxsize=128)
def get_file_content(file_id):
    return request_api(file_id)
```

这是远程 FUSE 可以采用的理论扩展方案，其中 `request_api` 需要另外实现。

当前 MusicFS 没有实现应用层 LRU 缓存。

В текущей реализации MusicFS алгоритм LRU на уровне приложения не используется.

---

### 138. Что произойдёт, если API возвращает данные быстрее, чем их читает программа, или наоборот?

**如果 API 返回数据的速度比程序读取数据的速度快，或者反过来，会发生什么？**

**中文：**

如果 API 返回数据的速度比程序消费数据的速度快，数据可能在缓冲区中积累。

如果缓冲区没有容量限制，可能导致内存占用不断增加。

如果 API 返回数据的速度比程序读取速度慢，程序需要等待数据，或者通过异步机制在等待期间处理其他任务。

可以使用有界缓冲区、背压、流式传输、异步 I/O 和超时机制解决这些问题。

**Русский：**

Если API возвращает данные быстрее, чем программа их обрабатывает, данные накапливаются в буфере, что может привести к увеличению потребления памяти.

Если API работает медленнее, программа должна ожидать поступления данных.

Для решения этой проблемы используются ограниченные буферы, обратное давление, потоковая передача данных, асинхронный ввод-вывод и тайм-ауты.

**生产者—消费者模型：**

```text
Producer           Buffer          Consumer
(API)       --->   Queue    --->   Program
```

| 情况 | 结果 | Русский |
|---|---|---|
| 生产速度大于消费速度 | 数据积累 | Накопление данных |
| 生产速度小于消费速度 | 消费者等待 | Ожидание данных |
| 两者速度相同 | 理想情况下保持平衡 | Равновесие |

**什么是背压？**

背压（Backpressure）是当消费者无法及时处理数据时，通过反馈或流量控制限制生产者继续产生数据的机制。

Обратное давление — это механизм ограничения скорости производителя, когда потребитель не успевает обрабатывать данные.

**注意：**

普通 FUSE read 通常是按需请求数据。上述问题主要适用于流式 API、预取和异步数据传输场景。

MusicFS 当前读取本地文件，不使用远程流式 API。

## 四、完整数据路径与文件操作

### 139. Опишите полный datapath чтения и записи в FUSE.

**描述 FUSE 完整的读取和写入数据路径。**

**中文：**

应用程序通过系统调用向 Linux 内核请求文件操作。

VFS 将请求交给 FUSE 内核组件，FUSE 通过 `/dev/fuse` 与用户空间文件系统通信。

用户空间程序访问底层数据源，并将结果通过内核返回应用程序。

**Русский：**

Приложение выполняет системный вызов.

Ядро через VFS передаёт запрос компоненту FUSE.

Через `/dev/fuse` запрос поступает пользовательской файловой системе, которая обращается к источнику данных и возвращает результат обратно через ядро приложению.

**读取路径 / Datapath чтения：**

```text
Application
    |
read() system call
    |
Linux VFS
    |
FUSE kernel component
    |
/dev/fuse
    |
libfuse3 / pyfuse3
    |
MusicFS.read()
    |
os.pread()
    |
Underlying filesystem / Page cache
    |
Storage device (if necessary)
```

读取完成后，数据通过 FUSE 返回内核，再返回应用程序。

**写入路径 / Datapath записи：**

```text
Application
    |
write() system call
    |
Linux VFS
    |
FUSE kernel component
    |
/dev/fuse
    |
libfuse3 / pyfuse3
    |
FUSE write callback
    |
Underlying data source
```

写入完成后，返回写入字节数量或错误。

**结合 MusicFS：**

MusicFS 是只读文件系统，因此写入请求会被拒绝，不会正常进入上述底层写入流程。

MusicFS работает только для чтения, поэтому запросы записи отклоняются.

**追问：是否每次 read 都需要调用用户空间 FUSE？**

不一定。如果内核页缓存已经包含所需数据，可能直接从缓存返回。

Не обязательно. Если данные находятся в страничном кэше ядра, чтение может выполняться без обращения к пользовательскому процессу FUSE.

### 140. Какие операции FUSE вызываются при выполнении команд ls и cat?

**执行 ls 和 cat 时会调用哪些 FUSE 操作？**

**中文：**

`ls` 主要涉及目录查找、目录打开、目录遍历以及属性查询。

`cat` 主要涉及文件查找、文件打开、数据读取和文件句柄释放。

**Русский：**

При выполнении `ls` обычно вызываются операции поиска, открытия каталога, перечисления его содержимого и получения атрибутов.

При выполнении `cat` обычно вызываются операции поиска файла, открытия, чтения данных и освобождения файлового дескриптора.

**ls 的典型流程：**

```text
lookup()
    |
getattr()
    |
opendir()
    |
readdir()
    |
releasedir()
```

**cat 的典型流程：**

```text
lookup()
    |
getattr()
    |
open()
    |
read()
    |
read() (при необходимости)
    |
release()
```

| 回调 | 中文功能 | Русский |
|---|---|---|
| lookup | 根据名称查找 inode | Поиск inode по имени |
| getattr | 获取文件属性 | Получение атрибутов |
| opendir | 打开目录 | Открытие каталога |
| readdir | 读取目录项 | Чтение записей каталога |
| releasedir | 释放目录句柄 | Освобождение дескриптора каталога |
| open | 打开文件 | Открытие файла |
| read | 读取文件数据 | Чтение данных |
| release | 释放文件句柄 | Освобождение файлового дескриптора |

**注意：**

实际调用顺序取决于内核缓存、命令参数和文件系统实现。

例如 `ls -l` 通常需要更多文件属性信息。上述流程不是每次执行都严格相同的固定顺序。

### 141. Что произойдёт, если пользовательский процесс FUSE завершится во время чтения файла, и как это повлияет на смонтированную файловую систему?

**如果 FUSE 用户空间进程在读取文件时退出，会发生什么？**

**中文：**

如果 FUSE 用户空间进程意外退出，内核将失去负责处理请求的文件系统服务。

尚未完成的读取请求可能失败，后续文件操作可能返回连接断开或 I/O 错误。

挂载点可能仍然存在，但无法正常访问，需要卸载或重新挂载。

**Русский：**

Если пользовательский процесс FUSE аварийно завершается во время чтения, ядро теряет связь с файловой системой.

Незавершённые запросы могут завершиться ошибкой, а дальнейший доступ к точке монтирования может стать невозможным.

Может потребоваться размонтирование и повторное монтирование файловой системы.

**常见错误：**

```text
Transport endpoint is not connected
```

**处理命令：**

```bash
fusermount3 -u /path/to/mount
```

必要时使用延迟卸载：

```bash
fusermount3 -uz /path/to/mount
```

**结合 MusicFS：**

MusicFS 处理 SIGINT 和 SIGTERM，以便正常退出、解除挂载和释放文件描述符。

SIGKILL 无法被捕获，因此强制退出后可能需要手动卸载。

MusicFS обрабатывает SIGINT и SIGTERM для корректного завершения работы.

SIGKILL нельзя перехватить, поэтому после принудительного завершения может потребоваться ручное размонтирование.

## 五、身份认证、授权与文件权限

### 142. Чем авторизация отличается от аутентификации?

**授权与身份认证有什么区别？**

**中文：**

身份认证（Authentication）用于确认用户是谁。

授权（Authorization）用于确定用户可以访问哪些资源，以及可以执行哪些操作。

**Русский：**

Аутентификация — это проверка личности пользователя.

Авторизация — это определение прав пользователя на доступ к ресурсам и выполнение определённых операций.

| 概念 | 核心问题 | 示例 |
|---|---|---|
| Authentication | 你是谁？ | 密码、SSH 密钥 |
| Authorization | 你能做什么？ | 文件读写权限、API 权限范围 |

**结合 MusicFS：**

Linux 文件权限主要属于授权机制。

Права доступа к файлам Linux относятся прежде всего к механизму авторизации.

---

### 143. Что такое API?

**什么是 API？**

**中文：**

API（Application Programming Interface）是应用程序编程接口，用于定义不同软件组件之间如何调用功能、交换数据和返回结果。

API 不一定是网络接口，也可以是本地库提供的函数接口。

**Русский：**

API — это программный интерфейс, определяющий способы взаимодействия между программными компонентами.

API может предоставлять функции локальной библиотеки или доступ к удалённому сервису через сеть.

| API 类型 | 示例 |
|---|---|
| Python API | os.pread() |
| FUSE API | pyfuse3.Operations |
| 系统调用接口 | Linux read |
| 网络 API | HTTP GET |

MusicFS 使用本地程序接口，但没有实现远程 HTTP API。

MusicFS использует локальные программные интерфейсы, но не реализует удалённый HTTP API.

---

### 144. Как FUSE обрабатывает права доступа?

**FUSE 如何处理访问权限？**

**中文：**

FUSE 文件系统通过文件属性提供权限、所有者 UID 和所属组 GID 等信息。

权限检查可以由 Linux 内核完成，也可以由用户空间文件系统程序实现。

使用 `default_permissions` 挂载选项时，内核会执行标准 Unix 文件权限检查。文件系统仍然可以实施额外限制。

**Русский：**

FUSE предоставляет информацию о правах доступа, владельце UID и группе GID через атрибуты файлов.

Проверка прав может выполняться ядром Linux или самой пользовательской файловой системой.

При использовании параметра `default_permissions` ядро выполняет стандартную проверку прав Unix.

**MusicFS 的权限设计：**

| 机制 | 作用 |
|---|---|
| ro | 禁止通过挂载点修改文件系统 |
| 0444 | 普通文件只读 |
| 0555 | 目录可读取和搜索 |
| O_RDONLY | 只读打开底层文件 |
| open() 检查 | 拒绝写入和截断等模式 |

**Linux 权限数字：**

| 数字 | 权限 | Русский |
|---|---|---|
| 4 | read，读取 | Чтение |
| 2 | write，写入 | Запись |
| 1 | execute，执行或目录搜索 | Выполнение или поиск |
| 0 | 无权限 | Нет доступа |

对于目录，执行权限表示允许搜索和访问其中的目录项，而不是执行目录本身。

Для каталога право выполнения означает возможность поиска и доступа к его записям.

---

### 145. Почему нельзя изменить права? Как изменить атрибуты файла?

**为什么不能修改权限？如何修改文件属性？**

**中文：**

MusicFS 是只读文件系统，并且没有实现用于修改文件属性的 `setattr()` 操作。

因此不能通过 chmod、chown 等命令修改其虚拟文件属性。

在支持属性修改的 FUSE 文件系统中，可以通过 setattr 处理权限、所有者、大小和时间戳等属性的变化。

**Русский：**

MusicFS работает в режиме только для чтения и не реализует операцию `setattr()`.

Поэтому изменение прав доступа, владельца и других атрибутов через команды `chmod` или `chown` не поддерживается.

Для изменения атрибутов необходимо реализовать обработчик `setattr()`.

| Linux 命令 | 修改内容 | FUSE 操作 |
|---|---|---|
| chmod | 权限 | setattr |
| chown | 所有者 | setattr |
| chgrp | 所属组 | setattr |
| touch | 时间戳或创建文件 | setattr / create |
| truncate | 文件大小 | setattr |
| setfattr | 扩展属性 | setxattr |

**getattr 与 setattr 的区别：**

- getattr：获取文件属性。
- setattr：修改文件属性。

- getattr — получение атрибутов файла.
- setattr — изменение атрибутов файла.

仅修改 getattr 返回的权限数值，并不能使 MusicFS 真正支持写入。

## 六、FUSE 性能与文件删除

### 146. Почему FUSE работает медленнее, чем ext4?

**为什么 FUSE 通常比 ext4 慢？**

**中文：**

FUSE 文件操作可能需要在内核空间和用户空间之间进行额外的请求传递、进程调度和数据复制。

ext4 的主要文件系统逻辑直接在内核中执行，因此通常具有更低的额外开销。

如果 FUSE 使用远程 API，还可能受到网络延迟影响。

**Русский：**

FUSE обычно работает медленнее ext4 из-за дополнительных расходов на передачу запросов между ядром и пространством пользователя, переключение контекста и копирование данных.

Основная логика ext4 выполняется непосредственно в ядре.

При использовании удалённого API также возникают сетевые задержки.

**路径对比：**

```text
ext4:

Application
    |
VFS
    |
ext4
    |
Storage
```

```text
MusicFS:

Application
    |
VFS
    |
FUSE kernel component
    |
Userspace MusicFS
    |
Underlying filesystem
    |
Storage
```

**主要性能开销：**

- Переключение контекста — 上下文切换。
- Передача запросов — 请求传递。
- Копирование данных — 数据复制。
- Планирование процессов — 进程调度。
- Сетевые задержки — 网络延迟（远程服务场景）。

**如何优化？**

- 缓存文件数据和元数据。
- 减少不必要的用户空间请求。
- 使用高效目录索引。
- 避免阻塞异步事件循环。
- 减少重复数据复制。
- 使用性能测试定位瓶颈。

**Русский：**

Для оптимизации можно использовать кэширование, эффективные индексы каталогов, асинхронную обработку и уменьшение количества лишних запросов и копирований данных.

注意，FUSE 并非在所有工作负载下都一定比 ext4 慢，实际性能取决于缓存和具体实现。

### 147. Чем отличаются unlink, rm и rmdir?

**unlink、rm 和 rmdir 有什么区别？**

**中文：**

unlink 是删除文件目录项的系统调用，也存在同名命令。

rm 是用户空间命令，用于删除文件，也可以递归删除目录。它内部可以调用 unlink、unlinkat 等系统接口。

rmdir 用于删除空目录，既有同名命令，也有对应的系统调用。

**Русский：**

`unlink` — это системный вызов, удаляющий запись каталога, связанную с файлом.

`rm` — это пользовательская команда для удаления файлов и, при использовании соответствующих параметров, каталогов.

`rmdir` — это команда и системный вызов для удаления пустых каталогов.

| 操作 | 类型 | 作用 |
|---|---|---|
| unlink() | 系统调用 | 删除文件目录项 |
| unlink | 命令 | 删除指定文件名 |
| rm | 命令 | 删除文件 |
| rm -r | 命令 | 递归删除目录及内容 |
| rmdir() | 系统调用 | 删除空目录 |
| rmdir | 命令 | 删除空目录 |

**FUSE 中的对应关系：**

```text
rm file.txt
    |
unlink / unlinkat
    |
VFS
    |
FUSE
    |
unlink callback
```

```text
rmdir directory
    |
rmdir / unlinkat
    |
VFS
    |
FUSE
    |
rmdir callback
```

**追问：删除硬链接后会发生什么？**

**中文：**

删除硬链接时，inode 的硬链接数量减少。

当硬链接数量变为 0，但文件仍然被进程打开时，已有文件描述符仍然可以访问文件数据。

当链接数量为 0，并且不再存在相关打开引用时，文件资源可以被回收。

**Русский：**

При удалении жёсткой ссылки количество ссылок на inode уменьшается.

Если количество ссылок становится равным нулю, но файл всё ещё открыт, его данные сохраняются.

Ресурсы файла могут быть освобождены после закрытия открытых дескрипторов и освобождения других необходимых ссылок.

**示例：**

```text
初始状态：

a.txt ----+
          +--> inode 100 --> Data
b.txt ----+

nlink = 2

删除 a.txt：

b.txt -------> inode 100 --> Data

nlink = 1

删除 b.txt，但文件仍被打开：

Open fd -----> inode 100 --> Data

nlink = 0

关闭最后一个 fd：

文件资源可以被回收。
```

**结合 MusicFS：**

MusicFS 没有实现 unlink 和 rmdir 回调，并且采用只读挂载，因此不能通过虚拟目录删除源音频文件。

MusicFS не реализует операции unlink и rmdir и работает в режиме только для чтения.

## 七、WSL 与挂载机制

### 148. Что такое /mnt/d в WSL? Является ли это виртуальной средой?

**WSL 中的 /mnt/d 是什么？它是虚拟环境吗？**

**中文：**

`/mnt/d` 不是虚拟环境，而是 Windows D 盘在 WSL 的 Linux 目录树中的挂载点。

WSL 通过 DrvFs 机制让 Linux 程序能够访问 Windows 文件系统中的文件。

执行 `cd /mnt/d` 只是切换当前工作目录，不会创建虚拟环境，也不会复制文件。

**Русский：**

`/mnt/d` — это точка монтирования диска D Windows в дереве каталогов Linux.

Это не виртуальная среда.

WSL использует механизм DrvFs для доступа к файлам Windows.

Команда `cd /mnt/d` только изменяет текущий рабочий каталог.

**路径对应关系：**

| Windows | WSL |
|---|---|
| C:\ | /mnt/c/ |
| D:\ | /mnt/d/ |
| E:\ | /mnt/e/ |
| D:\Study-Note | /mnt/d/Study-Note |

**进入实验项目：**

```bash
cd /mnt/d/Study-Note/OperatingSystem/Lab/lab2-fuse-musicfs
```

**查看挂载信息：**

```bash
findmnt /mnt/d

df -T /mnt/d

mount
```

**相关概念区别：**

| 概念 | 作用 | Русский |
|---|---|---|
| WSL2 | 基于轻量级虚拟机运行 Linux | Среда Linux на основе виртуальной машины |
| /mnt/d | Windows D 盘挂载点 | Точка монтирования диска D |
| venv | Python 依赖隔离环境 | Виртуальная среда Python |
| MusicFS | 用户空间文件系统 | Файловая система в userspace |
| cd | 切换当前工作目录 | Изменение текущего каталога |

**与 MusicFS 的关系：**

两者都涉及文件系统挂载，但使用不同的实现机制。

- /mnt/d：通过 WSL 的 DrvFs 访问 Windows 文件系统。
- MusicFS：通过 FUSE 提供自定义虚拟目录和文件。

Оба механизма связаны с монтированием файловых систем, но используют разные способы реализации.

DrvFs обеспечивает доступ к файлам Windows, а MusicFS предоставляет собственную файловую систему через FUSE.

### 2. 容易出现的概念错误

| 错误理解 | 正确理解 |
|---|---|
| FUSE 就是 VFS | FUSE 是实现机制，VFS 是内核抽象层 |
| FUSE 就是 libc | 两者功能和层次不同 |
| FUSE 完全不需要内核 | FUSE 仍依赖内核组件 |
| lsmod 没有 FUSE 就是不支持 | FUSE 可能直接编译进内核 |
| 同一目录不能挂载两次 | Linux 支持叠加挂载 |
| 叠加挂载会合并目录 | 上层挂载会遮蔽下层 |
| inode 保存文件名 | 文件名通常保存在目录项中 |
| 硬链接是文件副本 | 多个目录项引用同一 inode |
| 可以判断哪个是原始硬链接 | 通常无法区分 |
| 删除文件名立即删除数据 | 还需要考虑链接数量和打开引用 |
| TTL 就是 LRU | TTL 管理有效期，LRU 管理淘汰顺序 |
| 缓存越大越好 | 需要考虑内存和数据一致性 |
| read 每次都调用 FUSE | 可能直接命中内核缓存 |
| 异步一定是并行 | 异步可以实现并发，不一定并行 |
| 修改 0444 就能支持写入 | 还需要实现写入操作 |
| rm 是系统调用 | rm 是用户空间命令 |
| /mnt/d 是 Python 虚拟环境 | 它是 Windows D 盘的挂载点 |
| MusicFS 实现了远程 API | 当前使用本地 JSON 和音频文件 |
| MusicFS 实现了 LRU 缓存 | 当前没有应用层 LRU 缓存 |
