# MusicFS：代码导读与中俄答辩

## 先区分：音频、元数据和 API

音频文件（WAV、MP3）是实际数据；JSON 中的 BPM、调性、用途和相对路径才是本实验的分类元数据。当前实现不会从声音中识别 BPM/调性，也不会联网获取标签。

MusicFS 没有调用网络服务 API：没有音乐平台、HTTP 请求、账号或 API key。它确实使用了本地 API，包括 pyfuse3 的挂载/回调接口和操作系统的 open/pread/close。因此答辩应说“没有使用外部网络服务 API，完全基于本地数据”，不要笼统说“没有使用任何 API”。

RU: MusicFS не обращается к внешним сетевым сервисам. Метаданные читаются из локального JSON, а содержимое - из локальных аудиофайлов. Используются локальные API pyfuse3 и операционной системы. BPM и тональность автоматически не определяются.

本轮本机样例为 8 个、67.06 MiB：preset 中的 3 个旋律、2 个鼓采样、1 个 bass，以及 AUTUMN 中 I Know 的 WAV/MP3 两个版本。三条旋律的 BPM/调性按文件名填写，其他保持未知；没有把人工标签当作算法识别结果。两个编码版本是两个物理文件，各有自己的虚拟 inode；同一版本在三个分类入口中共享 inode。

## 先理解三个对象

`Node` 是一个虚拟文件或虚拟目录。`Catalog.nodes` 根据 inode 找到 Node；目录 Node 的 `children` 根据名字找到子节点 inode。真正的音频 Node 有 `path`，虚拟目录 Node 的 `path` 是 `None`。

例如读取 `by_bpm/120/s001__drum_loop.wav`，程序并没有创建对应的物理目录。`Catalog` 只在内存里建立如下关系：

```text
根目录 inode 1
  children[b"by_bpm"] -> 分类目录 inode
    children[b"120"] -> 分组目录 inode
      children[b"s001__drum_loop.wav"] -> 音频 inode
```

`by_key/A_minor` 和 `by_type/drum` 中的文件名也指向同一个音频 inode。因此源音频有三个虚拟入口，`st_nlink=3`，实际数据只有源库中的那一份。内核页缓存可能保存读过的内容，这是普通文件缓存，不是 MusicFS 复制了音频库。

## 一次操作如何贯穿三个模块

### 1. 启动

`__main__.py` 解析参数，构造 `Catalog`。`catalog.py` 用 Decimal 读取 JSON 中的小数，检查字段和源路径，建立目录树。然后启动入口校验挂载点，构造 `MusicFS`，以 `ro` 挂载，运行 Trio 请求循环。

这解释了为什么改 JSON 后不会立刻更新：`Catalog` 只在启动时创建一次。

### 2. 查找与列目录

应用程序访问文件 → Linux VFS → FUSE 内核接口 → libfuse3/pyfuse3 → `MusicFS` 回调。

`lookup(parent_inode, name)` 从父目录的 `children` 查出 inode，再调用 `getattr` 返回类型、权限、大小等属性。

`opendir` 返回目录 inode 作为目录句柄。`readdir` 按固定顺序列出子节点；位置编号从 1 开始，下一次调用只返回 `start_id` 后面的项目。`readdir_reply` 返回 False 说明本轮缓冲区已满，停止发送，等待内核续读。索引不可变，所以这些位置不会因 JSON 修改而漂移。

`lookup` 处理 `.` 和 `..`，分别返回当前目录和父目录；根目录的父目录仍是根目录。

### 3. 打开、读取、关闭

`open(inode, flags)` 根据 inode 找到源路径，只读打开源文件。得到的 Linux 文件描述符 fd 作为 `FileInfo.fh` 返回。`handles[fd]=inode` 记录打开的资源。

`read(fh, off, size)` 用 `os.pread(fd, size, off)` 返回指定范围的 bytes。它不修改 fd 的当前文件位置，所以多个读取请求不会相互改变 seek 位置。Trio 工作线程承担阻塞读取，FUSE 请求循环可以继续处理其他工作。

到文件末尾可以返回不足 size 的数据；偏移在 EOF 或之后返回空 bytes。`release` 在该打开句柄不再被引用时关闭 fd。退出时的 `close` 还会关闭剩余句柄。

注意两个编号不同：inode 表示“这是哪个虚拟文件”；fh 表示“这次打开使用哪个资源”。同一 inode 可以被多次打开，得到多个 fh。

### 4. 删除源文件时发生什么

源路径删除后，新的 `os.open` 返回 ENOENT。但已打开的 fd 仍引用 Linux 中的文件对象，因此旧句柄可继续读取。

真实挂载测试发现，内核可能在读取前重新请求属性。修复方式是：当源路径消失且该 inode 仍有打开的 fd 时，用 `fstat(fd)` 获取属性；新打开仍按源路径执行，因而失败。最后一个句柄释放后，属性查询也会返回 ENOENT。

这不是文件系统内实现了 unlink；MusicFS 本身禁止删除。测试删除的是临时音频库中的源文件。

### 5. 为什么代码里没有完整 inode 回收算法

元数据快照的节点从加载后一直保留到卸载，不会因目录修改而删除，也不复用 inode。因此 `forget` 不回收节点。内存规模取决于元数据条目数，与音频字节总量无关。

如果以后加入热重载、增删目录或回收 inode，就必须加入 lookup 引用计数、打开计数和内核缓存失效处理。这是明确的第一版边界。

### 1. 为什么同一个音频只创建一个节点？

实际实现中的关键部分是：

```python
node = self._new_node(1, name, path)
for category, group in zip(("by_bpm", "by_key", "by_type"), groups):
    parent = self._directory(1, category)
    directory = self._directory(parent, group)
    self.nodes[directory].children[name] = node.inode
    node.links += 1
```

`_new_node` 位于循环外，所以只有一个文件节点。循环内建立分类目录，并把三个目录项的值都设成 `node.inode`。`links` 记录虚拟目录入口数，而不是源文件原本的物理链接数。`node.parent=1` 对音频节点不用于路径遍历；只有目录节点的 parent 才用于处理 `..`，文件不能像目录那样执行 lookup。

RU: Узел файла создаётся до цикла. В цикле создаются только записи каталогов, которые ссылаются на один inode. Значение links описывает виртуальные ссылки MusicFS, а не физические ссылки исходного файла.

### 2. 为什么名字采用 bytes，而不是全部使用 str？

JSON 和 Python Path 使用文本字符串；pyfuse3 的目录项名字使用 bytes。因此目录索引在创建名字时统一编码 UTF-8，回调直接使用内核传入的 bytes 查表。这让中文、俄文、空格文件名保持一致。

### 3. 实际读取 real01 时，数据怎样流动？

1. JSON 的 real01 提供源路径、BPM=130、key=`D#_major`、type=`melody`。
2. `Catalog` 生成 `by_bpm/130`、`by_key/D#_major`、`by_type/melody` 三个入口。
3. 应用打开其中一个入口；内核通过 lookup 找到音频 inode。
4. `MusicFS.open` 根据 Node.path 打开 E 盘原文件，记录 `handles[fd]=inode`。
5. 若内核请求 offset=1024、size=4096，read 通过 `pread` 返回该范围的原始字节。
6. 应用关闭后，内核在该打开资源不再被引用时调用 release，释放 fd。

如果读的是 MP3，返回的是 MP3 文件中的编码字节，不是已经解码的 PCM。解码/播放由播放器负责，不属于本实验的读取回调。

### 4. 为什么 ro、0444 和 open 检查同时存在？

`ro` 在挂载层禁止修改；`0444` 告诉内核这是可读文件、没有写权限；open 中的标志检查保证处理器本身也拒绝写入。源文件以 O_RDONLY 打开，因此用户原有文件权限即使可写，MusicFS 也不使用写权限。只读不是修改 E 盘文件的权限或设置 Windows 只读属性。

### 5. 遇到异常，怎样把结果交回应用？

例如 `os.open` 找不到文件会抛出 OSError/ENOENT。回调转换为 `pyfuse3.FUSEError(exc.errno)`，内核再让应用的 open 返回错误。“程序崩溃”和“向应用返回文件不存在”是不同结果。启动时 JSON 格式错误则通过参数错误提示退出，因为尚未挂载。

### 6. 哪些东西在内存，哪些东西在磁盘？

- 内存：JSON 加载后的节点索引、分类目录项、打开句柄表、当前读取块。
- 磁盘：原始 WAV/MP3、JSON 清单、日志和验证结果。
- MusicFS 不把整首歌常驻内存；一次 read 只返回请求范围。Linux 页缓存可能缓存内容，这是内核行为。

### 7. 本轮真实文件验证证明什么？

`tools/check_local_audio.py` 读取本地清单，限制 8 个文件、100 MiB 和指定的两个源目录。它实际挂载 MusicFS，对每条记录比较三个入口与源文件的完整 SHA-256，检查随机范围与 EOF，尝试在挂载点创建文件，最后卸载。前后比较源文件哈希、大小、修改时间，确认源文件未被改变。

结果保存在 `local-data/validation.json`。本轮 8 条全部通过，且原来的 30 项测试再次通过。这证明真实 WAV/MP3 的文件访问和字节一致性；没有进行解码、听音检查或性能实验。8 条音频形成 24 个虚拟文件入口，不代表有 24 个物理音频。

## 答辩短问答 / Краткие ответы

### 1. 为什么 MusicFS 是文件系统？

中：应用通过普通路径、目录遍历、stat、open 和 read 使用它，请求由 FUSE 回调处理。分类目录是内存里的虚拟结构。

RU: MusicFS предоставляет обычный файловый интерфейс: каталоги, атрибуты, открытие и чтение. Запросы ядра обрабатываются в userspace через FUSE. Каталоги формируются из метаданных и не создаются в исходной библиотеке.

### 2. FUSE 和 libfuse 的区别？

中：FUSE 包含内核侧接口；libfuse 是与它通信的用户态库。本项目使用 Python 绑定 pyfuse3。

RU: FUSE включает интерфейс ядра, а libfuse обеспечивает взаимодействие с ним из пользовательского процесса. В работе используется pyfuse3, то есть Python-привязка к libfuse3.

### 3. 为什么选择 JSON？

中：把元数据准备与文件系统原理分开，格式小、可检查、便于测试；不需要识别算法或数据库。

RU: JSON отделяет подготовку музыкальных метаданных от реализации файловой системы. Формат прост для проверки и воспроизведения тестов. Автоматическое определение BPM и тональности в работу не входит.

### 4. 一个文件出现在三个目录中，为什么不复制数据？

中：三个目录项指向同一个虚拟 inode。read 使用该 inode 对应的原始路径，只读访问源文件。

RU: Три записи каталогов ссылаются на один виртуальный inode. Данные читаются из одного исходного файла. Физические копии и дополнительные жёсткие ссылки в исходной библиотеке не создаются.

### 5. inode 和 fh 有什么区别？

RU: Inode идентифицирует объект файловой системы, а fh идентифицирует конкретное открытие файла. Один inode может иметь несколько одновременно открытых дескрипторов.

### 6. 为什么使用 pread？

中：一次指定偏移，不依赖共享的 seek 位置；支持播放器读取不同位置和并发读取。

RU: pread читает данные по заданному смещению и не изменяет общую позицию файлового дескриптора. Поэтому параллельные чтения разных участков не мешают друг другу.

### 7. BPM 怎样归类？

RU: BPM округляется до ближайшего кратного десяти; при равном расстоянии выбирается большее значение. Например, 124,5 относится к 120, а 125 — к 130. Используется Decimal с ROUND_HALF_UP, а не стандартное округление round.

### 8. 如何保证只读？

中：挂载使用 ro；虚拟权限去掉写位；open 额外拒绝写入标志。集成测试实际尝试修改，并比较源文件内容哈希。

RU: Используется опция монтирования ro, у виртуальных файлов отсутствуют биты записи, а обработчик open дополнительно отклоняет режимы записи. В интеграционных тестах операции изменения завершаются ошибкой EROFS, хеши исходных данных не меняются.

### 9. JSON 改动何时生效？

RU: Метаданные загружаются один раз при запуске. Изменения становятся видимыми после размонтирования и повторного запуска. Это позволяет сохранить неизменяемые inode и позиции обхода каталогов.

### 10. 文件丢失怎样处理？

RU: Отсутствующий при запуске файл пропускается с предупреждением. После удаления исходного имени новое открытие завершается ENOENT. Ранее открытый дескриптор остаётся пригодным для чтения до закрытия.

### 11. 测试证明了什么，没证明什么？

RU: Повторно выполнены 30 тестов, включая 11 с реальным монтированием FUSE. Дополнительно проверены восемь локальных файлов WAV/MP3 общим объёмом около 67 МиБ: три виртуальных входа на файл, полные хеши и чтение по смещению. Исходные данные не изменились. Декодирование, воспроизведение, FLAC и производительность большой библиотеки не проверялись.

### 12. 如何停止进程？

RU: Обычное размонтирование выполняется через fusermount3 -u. SIGINT и SIGTERM завершают цикл запросов, затем выполняется очистка в finally. При SIGKILL обработчик выполнить невозможно, поэтому может потребоваться ручное размонтирование.
