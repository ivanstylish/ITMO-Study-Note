## 2. 文件系统与普通目录 / Файловая система и обычный каталог

**定义（中）：** 文件系统规定名称组织、属性和内容访问的规则。目录是名称到文件对象的映射，是文件系统中的一种对象。
**Определение (RU):** Файловая система задаёт организацию имён, атрибуты и доступ к содержимому. Каталог — объект, сопоставляющий имена файловым объектам.

**对比（中）：** 两者都能表现为目录树；目录只是一部分，文件系统还处理 stat、open、read 等操作。虚拟目录和实体目录都能被 ls 使用，但虚拟目录不必对应源盘上的真实文件夹。
**Сравнение (RU):** Оба видны через дерево каталогов. Каталог — лишь часть системы; файловая система также обрабатывает stat, open и read. Виртуальные и физические каталоги доступны через ls, но виртуальный каталог не обязан существовать на исходном диске.

**本实验（中）：** by_bpm、by_key、by_type 由内存索引提供。MusicFS 是可挂载的文件系统，不能理解成把音频复制到三个普通目录的脚本。
**В работе (RU):** by_bpm, by_key и by_type предоставляет индекс в памяти. MusicFS монтируется как файловая система, а не копирует аудио в три обычных каталога.

## 3. 用户态与内核态 / Пользовательский режим и режим ядра

**定义（中）：** 用户态运行普通进程，权限受限；内核态运行内核，管理硬件、内存和系统资源。系统调用是用户进程请求内核服务的受控入口。
**Определение (RU):** В пользовательском режиме работают процессы с ограниченными правами. Ядро управляет оборудованием, памятью и ресурсами. Системный вызов — контролируемый вход процесса в службу ядра.

**对比（中）：** 两者都执行程序指令，但权限和职责不同。用户态文件系统把主要业务放在普通进程中；内核文件系统把主要处理放在内核中。FUSE 依然需要内核侧支持。
**Сравнение (RU):** В обоих режимах исполняется код, но различаются полномочия и обязанности. В userspace основная логика ФС находится в процессе; у реализации в ядре — внутри ядра. FUSE всё равно требует поддержки со стороны ядра.

**本实验（中）：** Python 回调运行在用户态；os.pread 请求内核读取源文件。程序异常不等于内核崩溃，但可能导致挂载暂时不可访问。
**В работе (RU):** Python-обработчики работают в userspace; os.pread обращается к ядру за данными источника. Ошибка процесса не равна сбою ядра, но может сделать монтирование недоступным.

## 4. VFS 与 FUSE / VFS и FUSE

**定义（中）：** VFS 是 Linux 的统一文件系统抽象层；FUSE 是将文件系统请求传给用户态进程处理的机制。
**Определение (RU):** VFS — общий слой абстракции файловых систем Linux. FUSE — механизм передачи файловых запросов для обработки пользовательскому процессу.

**对比（中）：** 两者都参与文件访问。VFS 面向多种文件系统；FUSE 是其中一种通向用户态实现的路径。不能把 VFS、FUSE 和 MusicFS 当作同一个组件。
**Сравнение (RU):** Оба участвуют в доступе к файлам. VFS обслуживает разные файловые системы; FUSE предоставляет путь к реализации в userspace. VFS, FUSE и MusicFS — разные компоненты.

**本实验（中）：** 请求链如下；缓存和预读意味着一次系统调用不一定对应恰好一次 Python 回调。
**В работе (RU):** Ниже показан путь запроса. Из-за кеширования и упреждающего чтения одному системному вызову не обязательно соответствует ровно один Python-обработчик.

## 5. FUSE 驱动、libfuse 与 pyfuse3 / Драйвер FUSE, libfuse и pyfuse3

**定义（中）：** FUSE 内核驱动转发请求；libfuse 是与驱动通信并分派请求的用户态库；pyfuse3 是 libfuse3 的 Python 绑定，即把库的能力暴露给 Python 的适配层。
**Определение (RU):** Драйвер FUSE передаёт запросы. libfuse — пользовательская библиотека для связи с драйвером и диспетчеризации. pyfuse3 — Python-привязка к libfuse3, адаптирующая возможности библиотеки для Python.

**对比（中）：** 三者都参与同一请求链，但所在层和接口不同。libfuse 是基础设施，MusicFS 是自己编写的业务逻辑；pyfuse3 不负责自动推断音乐分类。
**Сравнение (RU):** Все три компонента участвуют в одной цепочке, но находятся на разных уровнях. libfuse — инфраструктура, MusicFS — собственная логика. pyfuse3 не определяет музыкальные категории автоматически.

**本实验（中）：** fs.py 继承 pyfuse3.Operations。使用 Python 不意味着没有使用 libfuse，也无需为运行实验重新编写或手工构建 libfuse。
**В работе (RU):** Класс в fs.py наследуется от pyfuse3.Operations. Реализация на Python использует libfuse; переписывать или вручную собирать саму библиотеку для этого не требуется.

## 6. 高层与低层 API / Высокоуровневый и низкоуровневый API

**定义（中）：** 高层 API 通常用路径标识操作对象；低层 API 用 inode、父 inode 和名字标识对象。API 是组件间调用的约定，包括参数、结果和错误方式。
**Определение (RU):** Высокоуровневый API обычно адресует объекты путями. Низкоуровневый — через inode, родительский inode и имя. API задаёт параметры, результаты и способы сообщения об ошибках.

**对比（中）：** 两者都以回调处理文件请求。C 高层主要见 fuse.h，回调通过返回值回复；C 低层见 fuse_lowlevel.h，用 fuse_reply_* 显式回复。pyfuse3 基于低层接口，但用 Python 返回值/异常表达结果，由绑定转换回复。
**Сравнение (RU):** Оба API используют обработчики запросов. Высокий уровень C описан в fuse.h и обычно отвечает возвратом результата; низкий — в fuse_lowlevel.h, с явными fuse_reply_*. pyfuse3 использует низкий уровень, но преобразует Python-результаты и исключения в ответы.

**本实验（中）：** lookup(parent_inode, name) 不是按完整路径查询。应读懂 hello.c 与 hello_ll.c 的区别，但不能把 C 高层签名直接复制成 MusicFS 方法。
**В работе (RU):** lookup(parent_inode, name) не получает полный путь. Нужно понимать различия hello.c и hello_ll.c, но сигнатуры C высокого уровня нельзя непосредственно переносить в MusicFS.

## 7. 本地 API 与网络 API / Локальный и сетевой API

**定义（中）：** 本地 API 调用库或操作系统服务；网络 API 通过网络协议请求外部服务。两者都是 API，而 API 不等于 HTTP。
**Определение (RU):** Локальный API обращается к библиотеке или ОС; сетевой API запрашивает внешний сервис по сетевому протоколу. Оба являются API; API не означает обязательно HTTP.

**对比（中）：** 共同点是有明确的输入、输出和错误约定。区别在通信边界：本地调用通常不需要远端地址、令牌和网络连接；网络服务还涉及超时、认证等。
**Сравнение (RU):** Общее — контракты входов, результатов и ошибок. Отличается граница взаимодействия: локальному вызову обычно не нужны удалённый адрес, токен и сеть; сетевой сервис требует обработки соединений, таймаутов и аутентификации.

**本实验（中）：** MusicFS 调用 pyfuse3 和 os 模块的本地接口，不调用音乐平台 API，不需要 API key。元数据来自本地 JSON。
**В работе (RU):** MusicFS использует локальные интерфейсы pyfuse3 и os, не обращается к музыкальным платформам и не требует API key. Метаданные читаются из локального JSON.

## 8. 挂载与格式化 / Монтирование и форматирование

**定义（中）：** 挂载把文件系统接入某个路径，即挂载点；格式化建立存储介质上的文件系统结构。
**Определение (RU):** Монтирование подключает файловую систему к пути — точке монтирования. Форматирование создаёт структуру файловой системы на носителе.

**对比（中）：** 两者都与使用文件系统有关，但挂载不要求重建或擦除原始音频。挂载可能遮住挂载点原有内容，所以要求独立空目录。
**Сравнение (RU):** Оба действия связаны с файловыми системами, но монтирование не требует пересоздания или удаления исходного аудио. Оно может скрыть содержимое точки монтирования, поэтому используется отдельный пустой каталог.

**本实验（中）：** validate_mountpoint 检查空目录和嵌套关系；pyfuse3.init 挂载，fusermount3 -u 或正常退出卸载。
**В работе (RU):** validate_mountpoint проверяет пустоту и вложенность каталогов. pyfuse3.init монтирует, fusermount3 -u или штатное завершение размонтирует систему.

## 9. 元数据与音频数据 / Метаданные и аудиоданные

**定义（中）：** 数据是文件内容；元数据描述内容、位置或属性。JSON 是组织文本数据的格式，不是音频解码器。
**Определение (RU):** Данные — содержимое файла. Метаданные описывают содержимое, расположение или атрибуты. JSON — текстовый формат данных, а не аудиодекодер.

**对比（中）：** 两者都保存信息，但用途不同。BPM/key/type 是音乐标签，stat 的大小/权限是文件系统属性；它们都属于描述信息，但不能互相替代。
**Сравнение (RU):** Оба вида содержат информацию, но служат разным целям. BPM/key/type — музыкальные метки; размер и права stat — атрибуты ФС. Это описательная информация разных видов, не взаимозаменяемая.

**本实验（中）：** Catalog 读 JSON 并建索引，read 读音频 bytes。三个旋律的 BPM/调性来自文件名，未测量；其他填 null，分类显示 unknown。
**В работе (RU):** Catalog читает JSON и строит индекс; read возвращает байты аудио. BPM и тональность трёх мелодий взяты из имён, не измерены. Для остальных null отображается как unknown.

## 10. inode 与目录项 / Inode и запись каталога

**定义（中）：** inode 标识文件系统中的对象；目录项是某个目录中的名字到对象的关联。inode 值只有在所属文件系统中才有意义。
**Определение (RU):** Inode идентифицирует объект файловой системы. Запись каталога связывает имя в конкретном каталоге с объектом. Значение inode имеет смысл в контексте своей ФС.

**对比（中）：** 两者都参与定位文件。一个对象可有多个目录项，因此 inode 不等于路径。源文件 inode 和虚拟 inode 属于不同文件系统，不要求数值相同。
**Сравнение (RU):** Оба используются для поиска файла. Один объект может иметь несколько записей, поэтому inode не равен пути. Исходный и виртуальный inode относятся к разным ФС и не обязаны совпадать численно.

**本实验（中）：** Catalog.nodes[inode] 找对象，Node.children[name] 找子 inode；根 inode 为 1，根的父目录是自己。
**В работе (RU):** Catalog.nodes[inode] находит объект, Node.children[name] — inode потомка. Корневой inode равен 1, а его родитель — он сам.

## 11. 多入口、硬链接、符号链接与复制 / Несколько входов, ссылки и копии

**定义（中）：** 硬链接是另一目录项直接引用同一文件对象；符号链接是保存目标路径的特殊文件；复制创建独立数据副本。
**Определение (RU):** Жёсткая ссылка — ещё одна запись, непосредственно ссылающаяся на тот же объект. Символическая ссылка — специальный файл с путём цели. Копирование создаёт отдельные данные.

**对比（中）：** 都可让用户从不同名字访问相关内容。硬链接共享对象，符号链接需解析目标路径，复制则可独立修改。MusicFS 的虚拟入口类似硬链接关系，但没有在 E 盘执行 os.link。
**Сравнение (RU):** Все способы дают доступ к связанному содержимому по разным именам. Жёсткие ссылки разделяют объект, символические требуют разрешения пути, копии изменяются независимо. Виртуальные входы MusicFS похожи на жёсткие ссылки, но os.link на диске E не вызывается.

**本实验（中）：** 文件节点在三分类循环前创建一次，三个目录项都指向 node.inode。12 个文件形成 36 个入口；WAV/MP3 两个编码版本仍是两个对象。
**В работе (RU):** Узел файла создаётся один раз перед циклом категорий; три записи ссылаются на node.inode. Двенадцать файлов дают 36 входов. Версии WAV и MP3 остаются разными объектами.

## 12. fd、fh 与 inode / fd, fh и inode

**定义（中）：** fd 是某个进程的打开文件描述符；fh 是文件系统返回给 FUSE、用于后续操作的句柄；inode 标识文件对象而不是一次打开。
**Определение (RU):** fd — дескриптор открытого файла в конкретном процессе. fh — возвращаемый FUSE идентификатор открытия. Inode идентифицирует объект, а не отдельное открытие.

**对比（中）：** 三者都是标识，但生命周期不同。一个 inode 可有多个 fh；应用进程的 fd 与 MusicFS 进程的 fd 不必相同。整数值偶然相同不代表职责相同。
**Сравнение (RU):** Все три — идентификаторы, но с разным временем жизни. У inode может быть несколько fh. fd приложения и fd процесса MusicFS не обязаны совпадать; совпадение чисел не означает одинаковую роль.

**本实验（中）：** os.open 得到源 fd，FileInfo(fh=fd) 将它作为 fh，handles[fd]=inode 记录资源归属。目录 fh 直接使用目录 inode，因为不打开底层目录。
**В работе (RU):** os.open получает исходный fd, FileInfo(fh=fd) использует его как fh, а handles[fd]=inode хранит принадлежность ресурса. Для каталога fh равен inode: нижележащий каталог не открывается.

## 13. 系统调用与回调 / Системный вызов и обработчик

**定义（中）：** 系统调用是应用请求内核服务的入口；回调是框架在收到事件或请求后调用的业务函数。
**Определение (RU):** Системный вызов — вход приложения в службу ядра. Обработчик вызывается инфраструктурой при поступлении события или запроса.

**对比（中）：** 都有参数和结果，但调用方不同。应用调用 open 系统接口；FUSE 框架调用 MusicFS.open。名称相似，不意味着它们是同一层函数。
**Сравнение (RU):** У обоих есть параметры и результат, но разные вызывающие стороны. Приложение вызывает системный open; FUSE вызывает MusicFS.open. Сходные имена не делают их функциями одного уровня.

**本实验（中）：** pyfuse3.Operations 定义回调约定。我们重写读取相关方法，修改操作由 ro 挂载拒绝，不必为凑数量实现全部回调。
**В работе (RU):** pyfuse3.Operations определяет контракт обработчиков. Переопределены методы чтения; изменения отклоняются режимом ro. Реализовывать все методы ради количества не требуется.

## 14. lookup 与 getattr / lookup и getattr

**定义（中）：** lookup 用父 inode 和名字解析目录项；getattr 获取已知 inode 的属性。EntryAttributes 是向内核回复属性的数据结构。
**Определение (RU):** lookup разрешает имя в родительском inode. getattr получает атрибуты известного inode. EntryAttributes — структура ответа с атрибутами для ядра.

**对比（中）：** 两者都会返回属性，但 lookup 先解决“名字指向谁”，getattr 解决“这个对象是什么状态”。它们都不返回音频内容。
**Сравнение (RU):** Оба возвращают атрибуты. lookup сначала определяет объект по имени, а getattr сообщает состояние уже известного объекта. Аудиосодержимое не возвращает ни один из них.

**本实验（中）：** lookup 查 children，并处理 . 与 ..；getattr 合成目录属性或 stat 源音频。st_mode 包含对象类型和权限，st_size 是字节数，st_nlink 是虚拟链接数，时间使用纳秒字段。
**В работе (RU):** lookup ищет в children и обрабатывает . и ... getattr синтезирует атрибуты каталога или вызывает stat источника. st_mode содержит тип и права, st_size — байты, st_nlink — виртуальные ссылки; время задаётся в наносекундах.

## 15. opendir、readdir 与目录续读 / opendir, readdir и продолжение обхода

**定义（中）：** opendir 建立目录遍历句柄；readdir 返回目录项。目录 cookie 是下一轮遍历的位置标记。
**Определение (RU):** opendir создаёт идентификатор обхода каталога; readdir возвращает его записи. Cookie каталога обозначает позицию продолжения обхода.

**对比（中）：** 与 open/read 类似，都是先建立访问资源再取结果；目录读取返回名字和属性，文件读取返回 bytes。start_id 是目录位置，不是音频 off。
**Сравнение (RU):** Как open/read, эта пара сначала открывает доступ, затем получает результат. Для каталога результат — имена и атрибуты, для файла — байты. start_id обозначает запись, а не байтовое смещение off.

**本实验（中）：** position 从 1 编号，跳过已返回位置；readdir_reply 返回 False 表示缓冲区满，等待续读。固定排序避免重发或遗漏。1,200 项真实目录测试已覆盖分页。
**В работе (RU):** position нумеруется с 1; ранее возвращённые позиции пропускаются. False от readdir_reply означает заполнение буфера. Фиксированный порядок предотвращает повторы и пропуски; проверен каталог из 1200 элементов.

## 16. open、read、release 与 flush / open, read, release и flush

**定义（中）：** open 创建一次打开资源；read 读取数据；release 在该打开资源不再被引用时释放它。flush 是与描述符关闭相关的请求，可能对一次打开发生多次。
**Определение (RU):** open создаёт ресурс открытия, read читает данные, release освобождает ресурс после исчезновения ссылок на него. flush связан с закрытием дескрипторов и может вызываться несколько раз для одного открытия.

**对比（中）：** release 和 flush 都与关闭有关，但不能把 flush 当成“最后一次关闭”，也不能在每次 flush 中关闭共享源 fd。修改数据的 fsync 语义也不同于释放句柄。
**Сравнение (RU):** release и flush связаны с закрытием, но flush не означает последнее закрытие. Нельзя закрывать общий исходный fd при каждом flush. Синхронизация fsync также отличается от освобождения ресурса.

**本实验（中）：** 只读 open 后，用同一 fh 多次 read，最终 release 关闭源 fd。close 在退出时兜底清理所有未释放句柄，没有用户态待写缓冲。
**В работе (RU):** После открытия для чтения один fh используется многими read; release закрывает исходный fd. При завершении close освобождает оставшиеся ресурсы. Буфера ожидающих записи данных в MusicFS нет.

## 17. read、pread、偏移与 EOF / read, pread, смещение и EOF

**定义（中）：** 文件偏移是字节位置；size 是请求长度。普通 read 使用当前文件位置；pread 显式指定偏移且不改变共享位置。EOF 是文件末尾。
**Определение (RU):** Смещение — позиция в байтах, size — запрашиваемая длина. read использует текущую позицию, pread задаёт смещение явно, не изменяя общую позицию. EOF — конец файла.

**对比（中）：** 两种读取都返回字节；并发 seek/read 可能相互改变位置，pread 避免这种干扰。EOF 返回短结果或空 bytes，不等于 ENOENT；后者表示对象不存在。
**Сравнение (RU):** Оба способа возвращают байты. Конкурентные seek/read могут менять общую позицию; pread устраняет эту помеху. Короткий или пустой ответ на EOF отличается от ENOENT, означающего отсутствие объекта.

**本实验（中）：** read 使用下面的循环，补齐底层在 EOF 前的短读；只有真正 EOF 才返回短结果。正式组曾出现请求 131072 字节但一次 pread 只返回 65512 字节，原回调直接返回会让内容不一致。MP3 返回编码字节，不在此解码成声音。
**В работе (RU):** read повторяет pread при коротком чтении до EOF. На основной выборке запрос 131072 байт однажды вернул только 65512; возврат такого результата без дополнения нарушал содержимое. Цикл заполняет запрос или достигает EOF. Для MP3 возвращаются закодированные байты без декодирования.

```python
data = bytearray()
while len(data) < size:
    chunk = await trio.to_thread.run_sync(
        os.pread, fh, size - len(data), off + len(data))
    if not chunk:
        break
    data.extend(chunk)
```

## 18. Trio、协程、并发与并行 / Trio, корутины, конкурентность и параллелизм

**定义（中）：** 协程是可在等待点暂停的任务；并发让多个任务在时间上交错推进；并行是任务实际同时执行。Trio 是组织异步任务和取消的运行库。
**Определение (RU):** Корутина может приостанавливаться в точках ожидания. Конкурентность — перекрывающееся продвижение задач; параллелизм — одновременное выполнение. Trio организует асинхронные задачи и отмену.

**对比（中）：** 都有助于处理多个请求，但 async 声明本身不会把同步磁盘操作变成非阻塞操作。协程不是线程；工作线程适合承担阻塞 I/O。
**Сравнение (RU):** Эти средства помогают обслуживать много запросов, но async сам по себе не делает синхронное дисковое действие неблокирующим. Корутина не является потоком; блокирующее I/O переносится в рабочий поток.

**本实验（中）：** read 用 to_thread 执行 pread；serve 的 nursery 同时组织请求循环与信号任务。启动和 getattr 中仍有同步 stat/open，未做慢盘吞吐优化。
**В работе (RU):** read переносит pread через to_thread. Nursery в serve организует цикл запросов и задачу сигналов. В запуске и getattr остаются синхронные stat/open; оптимизация медленных дисков не выполнялась.

## 19. 只读挂载与权限位 / Монтирование только для чтения и биты прав

**定义（中）：** ro 是挂载的只读策略；权限位表示用户对对象的读写执行权。文件 0444 可读，目录 0555 可读和遍历。
**Определение (RU):** ro задаёт политику монтирования только для чтения. Биты прав задают доступ к объекту. Файл 0444 доступен для чтения; каталог 0555 — для чтения и прохода.

**对比（中）：** 两者都限制修改，但控制层次不同。default_permissions 让内核按权限检查，open 还检查写标志；源文件本来可写，不代表 MusicFS 必须以可写方式打开。
**Сравнение (RU):** Оба механизма ограничивают изменения, но на разных уровнях. default_permissions включает проверку прав ядром; open дополнительно проверяет флаги записи. Возможность записи в источник не требует открытия его на запись в MusicFS.

**本实验（中）：** ro＋只读权限＋O_RDONLY 共同保证只读；测试尝试创建、写入、删除、改名、截断、chmod、mkdir，并验证源内容未变。没有开启 allow_other。
**В работе (RU):** ro, биты чтения и O_RDONLY совместно обеспечивают защиту. Проверены создание, запись, удаление, переименование, усечение, chmod и mkdir; данные источника не изменились. allow_other не включён.

## 20. errno 与 Python 异常 / errno и исключения Python

**定义（中）：** errno 是操作系统错误编号；异常是 Python 中传递失败信息的机制。FUSEError 把指定 errno 交回内核。
**Определение (RU):** errno — номер ошибки ОС, исключение — механизм передачи ошибки в Python. FUSEError возвращает указанный errno ядру.

**对比（中）：** 两者都说明失败，但不在同一接口层。pyfuse3 使用抛异常，不照搬 C 高层的负 errno 返回方式；返回空 bytes 只适合 EOF 等正常读取结果，不能掩盖权限错误。
**Сравнение (RU):** Оба сообщают об ошибке, но на разных уровнях. pyfuse3 использует исключения, а не отрицательный errno высокого C API. Пустой bytes допустим для EOF, но не для сокрытия ошибки доступа.

**本实验（中）：** ENOENT 表示不存在；ENOTDIR/EISDIR 表示类型不符；EROFS 表示只读；EACCES 表示拒绝访问；EBADF 表示无效句柄；EINVAL 表示参数不合适。代码将 OSError 的 errno 转成 FUSEError。
**В работе (RU):** ENOENT — отсутствие объекта, ENOTDIR/EISDIR — неверный тип, EROFS — режим чтения, EACCES — отказ доступа, EBADF — неверный дескриптор, EINVAL — неверный аргумент. Код преобразует errno из OSError в FUSEError.

## 21. 快照与缓存 / Снимок и кеш

**定义（中）：** 快照固定某一时刻的数据视图；缓存保留先前结果以减少重复访问。目录项、属性和文件内容可以分别缓存。
**Определение (RU):** Снимок фиксирует представление данных на определённый момент. Кеш сохраняет результаты для сокращения повторной работы. Записи каталогов, атрибуты и содержимое могут кешироваться отдельно.

**对比（中）：** 两者都复用已有信息；快照规定看到什么，缓存影响何时重新查询。entry_timeout/attr_timeout=0 不等于关闭内容页缓存，也不意味着 JSON 会重新加载。
**Сравнение (RU):** Оба повторно используют информацию, но снимок задаёт видимость данных, а кеш — повторное обращение за результатом. Нулевые таймауты записей и атрибутов не отключают кеш содержимого и не перезагружают JSON.

**本实验（中）：** Catalog 固定到卸载，JSON 改动后需重新挂载；getattr 每次重查属性，写回缓存关闭，内容缓存仍可存在。
**В работе (RU):** Catalog сохраняется до размонтирования; изменение JSON требует повторного запуска. Атрибуты запрашиваются заново, кеш записи отключён, но кеш содержимого может использоваться.

## 22. lookup 引用、链接数与 forget / Ссылки lookup, число ссылок и forget

**定义（中）：** lookup 计数反映内核持有 inode 的引用；st_nlink 是名称空间中的链接数；打开引用反映活跃的打开资源。内核通过 forget 通知文件系统减少 lookup 引用。
**Определение (RU):** Счётчик lookup отражает ссылки ядра на inode. st_nlink — число ссылок в пространстве имён. Открытые ресурсы учитываются отдельно. forget сообщает об уменьшении ссылок lookup.

**对比（中）：** 都与对象生命周期有关，但 st_nlink=3 不表示文件正被打开三次。forget 不等于删除，也不等于 release；有打开资源时不能仅因名字消失而销毁内容。
**Сравнение (RU):** Все понятия связаны со временем жизни объекта, но st_nlink=3 не означает три открытия. forget не равен удалению или release. При наличии открытого ресурса исчезновение имени не означает уничтожение доступных данных.

**本实验（中）：** 固定索引不删除或复用节点，所以 forget 暂不回收。若加热更新，就必须维护计数和缓存失效。源名字删除后，getattr 可用已有 fd 做 fstat；新 open 仍返回 ENOENT。
**В работе (RU):** Фиксированный индекс не удаляет и не переиспользует узлы, поэтому forget не освобождает их. Для горячего обновления потребуются счётчики и инвалидация. После удаления имени getattr использует fstat открытого fd; новый open возвращает ENOENT.

**问题：** 虚拟索引节点（inode）标识符未必与底层文件系统中的索引节点相对应。 这是为什么？  
В FUSE inode является логическим идентификатором, который назначается файловой системой в пространстве пользователя. Он не обязан совпадать с inode реального файла, потому что виртуальная файловая система может создавать собственные объекты и отображать данные из разных источников.  
真实 inode 标识底层文件系统中的对象，虚拟 inode 标识 FUSE 向内核呈现的对象，两者可以不同。  

## 23. BPM 分组与标签正确性 / Группировка BPM и достоверность меток

**定义（中）：** BPM 是每分钟节拍数；分组是把数值映射到分类点。Decimal 表示十进制数；ROUND_HALF_UP 表示中点向上取整。
**Определение (RU):** BPM — число долей в минуту. Группировка отображает значение в центр категории. Decimal представляет десятичное число, ROUND_HALF_UP задаёт округление середины вверх для положительных значений.

**对比（中）：** 浮点和 Decimal 都能计算，但十进制边界表示不同；Python round 的中点取偶不同于当前规则。分组正确不能证明原始 BPM 测量正确，也不会修改原值。
**Сравнение (RU):** Float и Decimal применимы к вычислениям, но различаются представлением десятичных границ. Округление round к чётному отличается от выбранного правила. Правильная группировка не подтверждает измерение BPM и не меняет исходную метку.

**本实验（中）：** 124.5→120、125→130、128→130，null→unknown。极大的 BPM 在挂载前被拒绝，错误会指出 JSON 记录编号。信息文件显示分组前的 BPM 原值。
**В работе (RU):** 124,5→120, 125→130, 128→130, null→unknown. Чрезвычайно большой BPM отклоняется до монтирования с указанием номера записи. В файле информации отображается BPM до группировки.

## 24. 路径解析与边界检查 / Разрешение пути и проверка границ

**定义（中）：** 相对路径以 source-root 为起点；绝对路径从系统根开始。resolve 解析链接并规范化路径；边界检查验证结果仍属于允许根目录。
**Определение (RU):** Относительный путь отсчитывается от source-root, абсолютный — от корня системы. resolve разрешает ссылки и нормализует путь. Проверка границ подтверждает принадлежность разрешённому корню.

**对比（中）：** 都定位文件，但不能只看字符串前缀，因为相似前缀不等于子目录，链接也可能逃出根目录。路径检查与抵御恶意进程并发替换目录的完整安全隔离不同。
**Сравнение (RU):** Оба пути находят файл, но строкового префикса недостаточно: похожий префикс не означает вложенность, а ссылка может выйти за корень. Проверка пути не равна полной защите от злонамеренной конкурентной замены каталогов.

**本实验（中）：** checked_path 用 resolve 和 is_relative_to；拒绝绝对路径、.. 和越界链接。音频库按本地受信任数据处理，源内容变化后重新挂载。
**В работе (RU):** checked_path использует resolve и is_relative_to; абсолютные пути, .. и выходящие ссылки отклоняются. Библиотека считается доверенной локальной; после изменения источника требуется повторное монтирование.

## 25. 哈希、解码与播放 / Хеш, декодирование и воспроизведение

**定义（中）：** SHA-256 是内容摘要；解码将编码音频还原为音频采样；播放将音频交给输出设备。测试证据是具体输入和操作产生的可核对结果。
**Определение (RU):** SHA-256 — дайджест содержимого. Декодирование восстанавливает аудиосэмплы из кодированного файла, воспроизведение передаёт звук устройству. Доказательство теста относится к конкретным входам и операциям.

**对比（中）：** 哈希验证的是字节一致性，解码和播放验证的是音频能否还原和输出。标签的正确性取决于元数据来源。
**Сравнение (RU):** Хеш подтверждает совпадение байтов. Декодирование и воспроизведение проверяют восстановление и вывод звука. Точность меток зависит от источника метаданных.

**本实验（中）：** 34 项测试通过，其中 12 项真实挂载。另对正式组 12 个 WAV/MP3 检查了三个音频入口和对应的 `.info` 文件。
**В работе (RU):** Пройдены 34 теста, из них 12 с монтированием. Для 12 реальных WAV/MP3 дополнительно проверены три входа к аудио и соответствующие файлы `.info`.

## 26. 资源清理与强制终止 / Очистка ресурсов и принудительное завершение

**定义（中）：** 资源清理释放 fd、任务和挂载；finally 是退出代码路径上的兜底。SIGINT/SIGTERM 可被处理，SIGKILL 不能被进程捕获。
**Определение (RU):** Очистка освобождает fd, задачи и монтирование; finally обеспечивает завершение при выходе из блока. SIGINT/SIGTERM обрабатываются, SIGKILL не перехватывается процессом.

**对比（中）：** 都会停止服务，但正常退出能清理，强杀不保证执行 Python 清理代码。关闭应用 fd 不等于立即卸载整个文件系统。
**Сравнение (RU):** Оба варианта прекращают службу, но штатное завершение выполняет очистку, а принудительное не гарантирует выполнение Python-кода. Закрытие fd приложения не означает размонтирование всей системы.

**本实验（中）：** main 的 finally 依次执行 pyfuse3.close 和 filesystem.close；必要时手工 fusermount3 -u。清理项目临时目录前先确认它不是挂载点。
**В работе (RU):** finally в main вызывает pyfuse3.close и filesystem.close. При необходимости используется fusermount3 -u. Перед удалением временного каталога нужно убедиться, что он не является точкой монтирования.
