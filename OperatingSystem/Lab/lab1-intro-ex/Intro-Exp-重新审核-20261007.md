## 2. 本次实测的运行条件

- Ubuntu 22.04.5 LTS，WSL2，内核6.6.87.2-microsoft-standard-WSL2。
- 工作目录 `/home/ivanstylish/course-code/lab/intro-exp`，ext4。D盘是整理材料用的副本，正式测量路径不是 `/mnt/d`。
- 初始短检查中，WSL约7.7GiB RAM，可用约6.9GiB，swap使用0；load average约0.24/0.05/0.02。这是当前快照，不能证明9月28日或之后每个时刻都处于空闲。
- 逻辑CPU 2可以绑定；Windows报告14个物理核心、20个逻辑处理器。WSL报告10×2的虚拟拓扑，不应当作宿主机物理拓扑。
- Windows电源计划名为“野兽模式”，电池信息显示外接供电、100%。计划名称不足以证明锁频或关闭Turbo。
- 短时宿主机CPU采样中，微信、ChatGPT、代理进程、OneDrive等仍有少量活动。负载不高，但它们与WSL共享物理资源，可能影响测量。
- 宿主机有两个SSD/NVMe。尚未确定Ubuntu虚拟磁盘文件位于哪一个设备上。
- WSL governor未提供；不需要为了这项实验再创建一台Windows内的虚拟机。课程明确讨论WSL，要求写明无法控制的条件。

正式测量前建议插电，关闭下载、视频、游戏、同步和更新任务，减少Windows与Ubuntu的背景任务。可以保留轻量的静态说明页面；关键是活动负载。进入WSL后稍等启动任务稳定，用快照确认。测量期间避免睡眠、切换电源状态或调整时间。

## 3. 运行很久的那一组

原来的strace诊断，一个遍历约4.35秒（read）和8.87秒（write），而未跟踪时约0.104秒和0.250秒。跟踪的系统调用分别约87万和175万次，耗时明显增长符合本程序行为。

若诊断时也设置20遍，仅这两组的跟踪就可能合计约260秒，再叠加重复、负载、准备与其他工具，整套接近10分钟是可能的。这只是根据已有数据的粗略估计，不保证按遍历次数严格线性缩放。

正式主测量总耗时为各组时间相加，还包括预热、生成数据与cp/sync/cat。单次运行超出预算时应检查它是否在使用strace、no-cache、Windows挂载路径或磁盘压力，以及是否超时/未完成；不能仅凭“长”判错，也不能仅凭“正常长”忽略错误。

本次工具补测使用1遍、每工具3次，保留CPU竞争数据的原协议，约61秒完成。缩短诊断遍数合理，因为诊断用于观察行为；必须对同一工具比较保持同样的遍数、文件和准备方法。

## 4. 简短脚本的边界

原来的简短脚本没有减少四组主系列的N=30，也没有改变10MiB/Seq/Cache。主系列的统计内容并未因此缺失。

但工具对照原先N=1，无法提供工具开销均值的可靠区间；之前把它描述为“覆盖完整要求”表述过宽。本次将诊断脚本扩展为可选TOOLS_REPS参数，默认仍是1，设置3时取得重复样本和区间。REPS只控制背景负载对照，**不控制run_series.sh的主系列N，也不控制工具次数**。

重新执行工具补测的命令如下，需在Ubuntu课程目录中运行：

```bash
cd ~/course-code/lab/intro-exp
CORE=2 ITER=20 STAGE=tools TOOLS_REPS=3 \
PERF_BIN=/usr/lib/linux-tools-5.15.0-194/perf bash run_diagnostics.sh
```

本次已执行，不需要为了复制同一结果再次运行。默认单次诊断的意义是快速了解程序行为；每组3次仍是小样本，只足够用于本次明显侵入性的描述，不能承诺所有工具微小开销都测得精确。

脚本继续使用少量内嵌Python计时，没有新增独立Python助手文件。官方图生成器graphgen.py仍是课程代码的一部分。诊断的统计汇总在AWK中完成；未覆盖的样本量会用NA表示区间，不冒充有区间。

新补测依然出现秒级两钟差异。一次Windows外部计时对照为9.1498秒，WSL单调计时8.9873秒；外部区间包括启动WSL和准备。它支持一个运行的时间尺度合理，但不能据此保证全体历史样本无误，也不能确诊跳变原因。报告没有修改或删除这些计时记录。
