1. Цель, вариант и гипотеза
Цель — оценить, как изменение данных влияет на время последовательного обхода графа разме­
ром 10 МиБ с использованием файлового кеша ОС. Рассматриваются две реализации: read/lseek 
и mmap. В каждой реализации сравниваются чтение и чтение с обновлением поля value.
Группа Реализация Нагрузка Аргументы
A read/lseek Чтение Без флагов
B read/lseek Чтение и обновление --write
C mmap Чтение Без флагов
D mmap Чтение и обновление --write
Во всех четырёх группах основного эксперимента фиксированы Cache, 10 МиБ и Seq. Флаг --
no-cache отсутствует; A/C соответствуют (-,-), B/D — (WR,-). Вариант Read vs Write означает 
изменение одного фактора внутри каждого API. Сравнение API дополнительно объясняет меха­
низмы доступа.
Гипотеза, сохранённая до пилота:  обновление увеличит среднее время нормированного 
обхода для обеих реализаций. В read/lseek оно добавляет позиционирование и запись через 
системные вызовы. В mmap изменяются страницы общего отображения, что требует дополнитель­
ной работы с памятью и страницами. В режиме Cache обязательный синхронный сброс каждой 
записи на физический носитель отсутствует.
Для каждого API отдельно обозначим Δ = 𝜇Write − 𝜇Read. Проверяются 𝐻0 : Δ ≤ 0 и 𝐻1 : Δ > 0. 
Принятый заранее критерий — положительная нижняя граница двустороннего 95% доверитель ­
ного интервала парной разности по раундам.
Материалы работы: ivanstylish/xv6­riscv — course­code/lab/intro­exp.

3. Подготовка данных и ознакомительные запуски
Использованы исходные программы курса и штатный генератор. Сборка выполняется GCC с -O2 
-Wall. Два графа имеют одинаковые размер 10 МиБ и seed 427:
python3 ../util/graphgen.py -s 10M --seed 427 --topology sequential --verify -o graph-
seq.bin
python3 ../util/graphgen.py -s 10M --seed 427 --topology chain -b 0.5 --min-step-pages 2 
--verify -o graph-rand.bin
У Seq физический порядок обхода совпадает с порядком записей. У Rand сохраняется форма 
цепи, но путь переставлен по физическим смещениям. Заголовок занимает 40 байт, запись — 
24 байта; граф содержит 436 905 вершин . Проверка подтверждает достижимость всех вершин 
и отсутствие циклов. В основной серии дополнительно проверены последовательные связи 𝑖→
𝑖+ 1 и отсутствие потомка у последней вершины.
3.1. Baseline: топология и переключатели
Ознакомительные запуски предусмотрены шагом 4.3 задания для read/lseek; этап 2 повторяет эти 
шаги для mmap. Поэтому baseline охватывает оба графа и все сочетания двух флагов. Основной 
эксперимент варианта при этом фиксирует Seq, Cache и 10 МиБ: статистические выборки соби­
раются только для четырёх групп A–D. Значения baseline не входят ни в пилот, ни в основное N.
До планирования основной серии выполнены 16 функциональных запусков: Seq/Rand × два 
API × Read/Write × Cache/NoCache, по одному обходу. Все завершились с кодом 0 и обработали 436 
905 вершин. Перед каждым запуском выполнены восстановление, sync и cat; глобальный сброс 
кеша не применялся. Таблица содержит elapsed GNU time в секундах; её разрешение — 0,01 с.

округление, а не нулевую длительность. Два прогретых запуска всё же имеют большие ошибки 
страниц (1 и 3); прогрев не гарантирует их полного отсутствия. Baseline с N=1 предназначен 
для знакомства и проверки работоспособности; он не используется для оценки дисперсии или 
выбора N.

4. План, пилот и выбор числа измерений
Выполнена подтверждающая серия по заранее сохранённому плану. До пилота зафиксированы 
гипотеза, цель точности, метрика, прогревы, обработка выбросов и порядок запуска. После 
отдельного пилота вычислено и зафиксировано N, затем собрана основная серия.
4.1. Заранее заданные правила
Статистическая единица — один запуск процесса с ITER=20 полными обходами. Время процесса 
𝑇𝑖 переводится в 𝑥𝑖 = 1000 𝑇𝑖
20  мс/обход. Это нормированное время процесса, а не 20 независимых 
инструментальных отсчётов. Для каждой конфигурации выполняются два отдельных прогревоч­
ных запуска, они сохраняются в журналах и не входят в CSV измерений. Выбор WARMUP=2 
сделан заранее для исключения начального запуска.
Перед процессом граф восстанавливается; между его 20 обходами восстановления нет. В Write 
значение каждой посещённой вершины увеличивается на единицу при каждом обходе, связи 
не меняются. Файловый кеш прогревается перед каждым процессом, включая измеряемые. Все 
корректные наблюдения сохраняются независимо от времени. Критерий 1,5× IQR применяется 
только для описания отклоняющихся точек.
Порядок четырёх конфигураций по раундам: A–B–C–D, B–C–D–A, C–D–A–B, D–A–B–C, затем 
повтор. Это уменьшает смешение эффекта режима с общим дрейфом. В 30 раундах каждая группа 
занимает каждую позицию 7 или 8 раз.

4.4. Метрика и разделение измерения с мониторингом
Основная длительность измеряется заранее выбранным time.monotonic_ns(), то есть 
CLOCK_MONOTONIC, вокруг цепочки /usr/bin/time → taskset → программа. Интервал включает 
запуск служебных процессов, открытие/закрытие или отображение файла, выполнение обходов 
и вывод в журнал. Запуск Python, компиляция, генерация, восстановление и прогрев файла 
происходят вне этого интервала.
GNU time дополнительно даёт user/sys, переключения контекста и ошибки страниц. strace и perf 
не используются внутри основной серии. В каждом журнале сохранены MONOTONIC, REALTIME 
и MONOTONIC_RAW для контроля таймера. Ресурсный мониторинг не заменяет wall и не увели­
чивает число независимых наблюдений.
Проверка инструмента выполнена в отдельной диагностике. Количество обходов там равно 
одному, поэтому диагностические длительности не добавляются к выборке основной серии с 
ITER=20. Данные background также предназначены для отдельного опыта конкуренции за CPU.

7. Объяснение через работу ОС
7.1. read/lseek и mmap
lseek задаёт позицию в открытом файле, read копирует данные из файлового пути ОС в пользо­
вательский буфер. Программа читает запись вершины одним блоком размером 24 байта, затем 
извлекает её поля из буфера. В Write дополнительно выполняются позиционирование и write 
нового значения. Большое число обращений к ядру сохраняется даже при прогретом page cache.
mmap создаёт отображение файла в виртуальное адресное пространство. После отображения код 
читает поля через адреса памяти; при записи меняет общее отображение MAP_SHARED. Обычный 
доступ к вершине не вызывает отдельный read или write, но обращение к странице может потре­
бовать обработчика ошибки страницы. Малые ошибки означают установление или обновление 
отображения без обязательного чтения данных с диска.
Отношение средних read/lseek к mmap составляет 61,9100 для чтения и 70,3944 для обновления. 
Это результат конкретных программ, графа и протокола; он не является универсальным преиму­
ществом mmap. В коротких C/D относительная доля запуска, открытия и вывода заметнее. Cache 
не означает отсутствие всех обращений к накопителю: изменённые страницы могут записывать­
ся позднее, вне рассматриваемого интервала.

10. Выводы и границы применимости
1. Для Seq, 10 МиБ, Cache обновление значений увеличило зарегистрированное среднее время 
обхода в 2,449140 раза у read/lseek и 2,153954 раза у mmap. Положительные интервалы 
парной разности поддерживают гипотезу для обеих реализаций, направление сохраняется при 
вспомогательном анализе RAW тех же процессов.
2. Гипотеза и правила обработки зафиксированы до пилота. По отдельному пилоту вычислено 
N=30, 120 основных наблюдений и 2400 обходов прошли проверки полноты. Пилот и заранее 
исключённые прогревы не добавлены к основной выборке, медленные корректные точки 
сохранены.
3. Фактические полуширины интервалов средних меньше заранее выбранных 5% пилотного 
среднего. Это достаточность для большого эффекта данного протокола по случайной неопре ­
делённости, а не обещание 5% абсолютной точности часов. Увеличение N сужает случайный 
интервал, но не устраняет систематические ограничения.
4. Структура системных вызовов и ресурсные показатели согласуются с дополнительной работой 
записи. mmap быстрее для этих программ за счёт доступа к отображению вместо множества 
отдельных вызовов на вершину. Результат не распространяется на произвольные размеры, 
топологии и режимы синхронизации.
5. Baseline охватывает случайный и последовательный графы и оба флага. Диагностика пока ­
зывает сильное вмешательство strace в read/lseek, опыт с конкурирующей CPU­нагрузкой 
показывает рост длительности и переключений.
