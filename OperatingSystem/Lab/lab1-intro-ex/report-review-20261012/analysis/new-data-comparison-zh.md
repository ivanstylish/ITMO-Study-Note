# 10 月 12 日诊断与最新版报告的独立比较

本说明不改写报告数据。比较对象是 11 页的《Intro-Exp-实验报告-复核版.pdf》，其中正式数据为 `series-20260928-235347-14706`，CPU 负载对照为 `diag-short-20260928-235755-16397`，附加工具复测为 `diag-short-20261007-162239-485`。本次数据来自 `diag-20261012-173446`，没有并入原报告的任何统计样本。

## 1. 两种 C 不是同一个实验条件

诊断 A/B/C 与正式四组 A/B/C/D 是两套命名。这里的 C 指背景负载对照，不是正式四组中 mmap/read 的 C。

| 条件 | 原报告第 8.2 节 | 本次历史脚本 |
|---|---|---|
| 负载 | 一个同核 Bash CPU 忙循环 | stress-ng：CPU workers 2、I/O worker 1、VM worker 1，256M |
| 负载启动位置 | 文件恢复、sync、cat 之后 | 文件恢复、sync、cat 之前 |
| 重复次数 | 每种实现每种条件 3 次 | quiet/stress 各 10 次 |
| 每次遍历数 | 20 | 20 |
| 对照顺序 | 随轮次交替 | 每轮固定 quiet 后 stress |
| 实现覆盖 | read/lseek 与 mmap | 按默认 LOAD_API 和资源特征，为 read/lseek；本目录没有 mmap 的 C |
| 逐次日志与时钟 | 保存每次日志及双时钟 | B/C 每次日志覆盖，只保留最后一份；无双时钟审核 |

新旧结果可以说明不同条件下的表现，不能把它们合并计算同一个平均值或归因于单一脚本修改。历史脚本没有把 LOAD_API 写入 load.csv 或快照；默认参数和约 134 次 minor faults/进程的特征支持 read/lseek 判断，完整的命令环境未留存。

## 2. C 的统计结果

单位是一次进程运行的秒数，每次运行包含 20 遍历。N 是进程启动次数。95% 区间使用样本标准差与 Student t；旧 N=3 的 t=4.302652730，新 N=10 的 t=2.262157163。正确完成的记录未删除。

| read/lseek 对照 | N | 平均 wall，秒 | s，秒 | 95% 均值置信区间，秒 |
|---|---:|---:|---:|---|
| 原报告：quiet | 3 | 1.956309 | 0.013403 | [1.923013, 1.989604] |
| 原报告：CPU 负载 | 3 | 4.281070 | 0.039363 | [4.183286, 4.378854] |
| 本次：quiet | 10 | 1.915281 | 0.028195 | [1.895112, 1.935451] |
| 本次：混合负载 | 10 | 7.804988 | 0.092202 | [7.739031, 7.870946] |

原报告负载/quiet 比值为 **2.188341**，本次为 **4.075113**。本次按同轮次配对的 stress−quiet 平均差为 **5.889707 秒**，95% 区间为 **[5.836502, 5.942912] 秒**。两者都是读取条件下的背景负载对照，不能用于替代正式的 Read/Write 比较。

本次 user+sys 平均约为 quiet 1.775 秒、stress 1.809 秒，实际 CPU 工作量相近，而 wall 明显增大；平均被动切换从 7.7 增至 528.8。这支持调度竞争和等待增加的解释。混合负载还改变了 I/O 与内存条件，不能把全部差异只归因于 CPU。

## 3. 为什么 C 等待一小时多

数据中 quiet 的十次计时合计 **19.152813 秒**，stress 合计 **78.049884 秒**，全部二十次被测运行合计 **97.202697 秒**。

文件记录的首个 stress 快照时间为莫斯科时间 17:45:00，load.csv 最后修改时间为 19:09:39，相隔约 **84.65 分钟**。这是文件的日历时间标签，不能当作经过外部验证的单调总耗时；这次未保存全 C 的单调计时或准备步骤分段计时。

历史脚本的实际顺序为：

```text
start stress-ng -> sleep 2 -> cp -> sync -> cat -> start timer -> program -> stop timer -> stop stress-ng
```

因此 cp/sync/cat、启动等待和进程清理都不在 load.csv 的 wall 内。`--io 1` 持续调用 sync(2)，与准备阶段的全局 sync 同时施加同步压力。负载下准备及同步等待是耗时很长的主要候选解释；现有日志不能给每一条准备命令分配确切秒数。[stress-ng 手册](https://manpages.ubuntu.com/manpages/noble/man1/stress-ng.1.html)

`--timeout 600s` 是单次后台负载的退出上限，不是要求每次等待十分钟。旧脚本没有保存每轮负载存活状态和所有程序日志，不能补称这二十条都已逐条验证。最后一份 C 日志包含 20 次成功遍历；CSV 的十对记录齐全。

top 显示全机约 5% CPU 忙碌与本实验并不矛盾：20 个逻辑 CPU 的统计被平均，所有负载及被测进程被限制在同一个 CPU 2。该快照显示多个 stress-ng worker 正在运行，只代表首次采样瞬间。

结论是：本次整段流程很慢，CSV 中被测程序总时间约 97 秒。没有证据证明“遍历这个 10M 图本身需要一个多小时”。再次等待一小时不是课程验收条件，也不是本变体主要结论所需的额外样本量。

## 4. B 与原报告附加工具复测的区别

下表比较同为 Read、单遍历的工具测量。原报告附录是 07.10，N=3；本次 N=10。不同日期、启动链和平台状态使其不能成为控制变量严格相同的因果比较。

| API | 工具 | 报告附录平均，秒 | 本次平均，秒 |
|---|---|---:|---:|
| read/lseek | bare | 0.095819 | 0.097182 |
| read/lseek | strace | 4.269392 | 49.255672 |
| mmap | bare | 0.003561 | 0.002927 |
| mmap | strace | 0.005370 | 0.009163 |

本次 read/lseek 的 strace/bare 比约 **506.84**，mmap 约 **3.13**。read/lseek 十次 strace 的计时累计 **492.556724 秒（8.21 分钟）**，这解释了 B 也较慢。它们支持原报告“strace 对大量系统调用程序有很强侵入性”的定性解释；具体倍数变化的原因未由这些数据单独确定，不能归结为减少或增加 N。

本次 A 有四组 time-v/strace 文件；B 有四十条 bare/strace 记录；C 有二十条 quiet/stress 记录。没有 perf 记录、也没有 Write 的 B 重复工具对照。原报告 07.10 使用单独的 perf 二进制获得软件事件，这与本次未使用 perf 不矛盾；不能据此删除报告中的真实旧事件数据。

## 5. 对原报告结论的影响

原报告正式四组的 N=30、ITER=20、Read/Write 平均值与置信区间都保持原样。新 C 不改变其主要比较，也不能修复其缺少事前 pilot 记录或日历时钟不一致的限制。旧 CPU 对照和新混合负载对照分别对应不同问题。按照本次要求，修订 PDF 只调整措辞和材料链接；本次数据与比较只在此说明和对应 CSV/JSON 中保存。
